# Luna Delegation

상위 모델이 판단·분해하고 `gpt-5.6-luna` 서브에이전트가 실행하는 위임 규칙이다. 판단은 위임하지 않는다. 위임하는 것은 **경계가 이미 정해진 실행**뿐이다.

## 절대 규칙

- **동시 실행은 최대 4개.** 5개째가 필요하면 먼저 띄운 것이 끝나 `close_agent`로 닫힐 때까지 기다린다. 상한을 늘리는 우회는 금지한다.
  플랫폼은 이 상한을 막아주지 않는다. 2026-07-26 실측에서 5개째 `spawn_agent`도 그대로 성공했다. 따라서 세는 것은 상위 모델의 책임이다. `spawn_agent`를 호출하기 전에 **닫지 않은 에이전트 수를 먼저 센다.** 완료 상태로 열려 있는 것도 포함해서 센다.
- **재귀 위임 금지.** 서브에이전트에게 넘기는 프롬프트에는 항상 "너는 서브에이전트를 생성하지 마라"를 포함한다. luna가 다시 luna를 부르면 비용과 실패 지점이 통제 범위를 벗어난다.
  이 한 줄은 프롬프트에서 생략할 수 없다. 재귀를 막는 장치가 이것뿐이기 때문이다. 서브에이전트도 `spawn_agent`를 쓸 수 있으므로, 지시하지 않으면 스스로 자를 이유가 없다.
- **위임은 실행만.** 아키텍처 결정, 계약 변경, 규칙 파라미터 승인, 병합 판단은 상위 모델이 직접 한다.
- **쓰기 범위는 서로 겹치지 않게 자른다.** 두 에이전트가 같은 파일을 쓰면 결과를 신뢰할 수 없다.
- **결과는 반드시 검수한다.** luna가 "완료"라고 답한 것과 실제로 통과하는 것은 다르다. effort를 올려도 이 단계는 생략하지 않는다.

## effort 선택

effort는 과제 종류로 정한다. 매번 고민하지 않는다.

| 과제 종류 | effort | 예시 |
|---|---|---|
| **코드 작성** | `xhigh` | 규칙 엔진 수정, `Decimal` 계산, 테스트 작성, 버그 수정, 리팩터링 |
| **수치·사실 조회** | `medium` | 상수값·파일 위치·버전·enum 조회, grep 요약, 문서 갱신 |

두 종류에 걸치면 코드 작성으로 본다. 파일을 하나라도 수정시키면 `xhigh`다.

`low`는 쓰지 않는다. 조회 정확도가 `medium`과 같더라도 분기를 둘로 유지하는 편이 선택 비용이 낮다.

### 근거

[공식 문서](https://developers.openai.com/api/docs/guides/reasoning)의 effort 표는 `xhigh`를 "security and code review, challenging coding workflows"에 배정하고, 쓰기 조건을 이렇게 단다.

> Only use when your evals show a clear benefit that justifies the extra latency and cost.

이 저장소의 코드 작성은 그 조건에 해당한다고 본다. 규칙 엔진은 `Decimal` 결정론과 계좌별 한도가 걸려 있어 틀린 코드를 검수하는 비용이 지연·토큰 비용보다 크다. 2026-07-26 실측에서 `medium`은 테스트 작성 단언 7/9, `high`는 9/9였다. `medium`이 코드에서 실제로 틀린다는 것까지는 측정됐다.

`xhigh`가 `high`보다 나은지는 이 저장소에서 아직 측정하지 않았다. 총괄 방침으로 고정한 값이다. 측정 결과가 나오면 이 절을 근거와 함께 갱신한다.

조회를 `medium`으로 두는 근거는 다르다. 같은 실측에서 `low`·`medium`·`high` 모두 단순 조회에 만점이었고(4건 병렬 조회에서 줄 번호까지 4/4), 공식 문서도 조회·요약을 낮은 effort 구간에 배정한다. 조회는 답이 이미 입력에 들어 있어 추론을 더 태울 대상이 없다. 여기에 `xhigh`를 쓰면 비용만 오른다.

`reasoning.effort`는 상한을 정할 뿐 토큰을 강제로 태우지 않는다. 공식 문서가 "reason adaptively... using fewer tokens for simpler tasks"라고 명시한다. 따라서 `xhigh` 고정이 모든 호출에서 최대 비용을 뜻하지는 않는다.

비용을 실제로 확인할 때는 추정하지 말고 응답 `usage.output_tokens_details.reasoning_tokens`를 읽는다. 추론 토큰은 출력 토큰으로 과금된다(공식 문서).

## 위임 프롬프트 계약

서브에이전트는 이 저장소의 `AGENTS.md`를 자동으로 읽지 않는다. 규칙을 모르는 상태로 출발하므로 매번 아래를 명시한다. 이 계약을 빠뜨리면 `float` 사용이나 금지 표현 노출 같은 회귀가 조용히 들어온다.

```text
작업 디렉토리: <워크트리 절대경로>

먼저 읽어라: 작업 대상 폴더의 AGENTS.md, docs/30_스펙/코드베이스_지도.md의 관련 절, 수정할 파일과 그 테스트

제약:
- 계산·판단은 규칙 엔진이 한다. 직접 수치를 지어내지 마라.
- Decimal + ROUND_HALF_UP을 쓴다. float 금지.
- 계좌 규칙을 섞지 마라. DC·IRP는 위험자산 70% 한도, 연금저축은 별도 적격성 규칙이다.
- 사용자 노출 문구에 다음을 쓰지 마라: 교육용, 목데이터, Mock, 가상, 샘플 데이터, 테스트용, 데모용, 시연용
- 한국어 .md는 UTF-8 편집도구로만 수정한다. PowerShell·sed 일괄치환 금지.
- 너는 서브에이전트를 생성하지 마라.
- claim 범위 밖의 파일을 수정하지 마라. 네가 만들지 않은 변경을 되돌리지 마라.

완료 조건: <검증 명령>을 직접 실행하고 결과를 그대로 붙여라. 수정한 파일 경로를 전부 나열하라.
```

**완료 조건 줄이 이 계약의 핵심이다.** 테스트를 직접 돌리게 하고 출력을 요구하면 잘못된 단언을 스스로 잡는다. 읽기 전용으로 묶어 검증을 막으면 오류가 그대로 올라온다.

검증 명령은 `docs/30_스펙/코드베이스_지도.md`의 영역별 "검증 명령" 절에서 가져온다. 엔진은 `uv run pytest tests/test_engine.py ...`, 프론트는 `npm run build`와 `npm test`다.

## 작업 절차

### 1. 분해

과제를 쓰기 범위가 겹치지 않는 조각으로 자른다. 자를 수 없으면 위임하지 않고 직접 한다.

위임에 적합한 것: 독립 모듈의 테스트 추가, 정해진 패턴의 반복 구현, 여러 파일에 걸친 동일 조사, 서로 다른 영역의 병렬 조사.

위임하면 안 되는 것: 다음 단계가 그 결과에 막혀 있는 작업(직접 하는 편이 빠르다), 계약·스키마 설계, 병합 순서 판단, 범위가 흐릿해 "적당히 알아서" 해야 하는 일.

### 2. 쓰기 격리

코드를 수정시킬 때는 상위 모델이 먼저 워크트리를 만들고 그 경로를 넘긴다. 루트 `main` 워크트리는 관제 전용이라 서브에이전트에게 넘기지 않는다.

```powershell
uv run python scripts/git_session_manager.py start --tool codex --worker <실명> --task <slug> --path <경로>
```

조사만 시킬 때는 워크트리 없이 저장소 경로를 주고 "파일을 수정하지 마라"를 명시한다.

### 3. 실행

`spawn_agent` 전에 닫지 않은 에이전트를 센다. 이미 4개면 띄우지 않는다.

```text
코드 작성: spawn_agent(model="gpt-5.6-luna", reasoning_effort="xhigh", message="<계약 + 과제>")
수치 조회: spawn_agent(model="gpt-5.6-luna", reasoning_effort="medium", message="<계약 + 과제>")
```

독립 과제는 같은 블록에서 함께 띄운다. 한 블록에서 4개를 넘겨 호출하지 않는다.

`model`을 빠뜨리면 부모 모델(opus·sol)을 상속해 비용이 몇 배로 뛴다. 위임의 이유가 사라지므로 매번 명시한다.

띄운 뒤에는 `wait_agent`로 붙잡고 기다리지 말고 겹치지 않는 다른 일을 한다. 결과가 즉시 필요한 임계 경로면 애초에 위임 대상이 아니다.

### 4. 검수

반환된 답을 그대로 믿지 않는다. 최소한 이 세 가지를 확인한다.

1. 주장한 검증 명령을 상위 모델이 다시 실행해 통과를 확인한다.
2. `git diff`로 claim 범위 밖 수정이 없는지 본다.
3. 사용자 노출 문구를 바꿨다면 금지 표현을 검색한다.

```powershell
rg -n "교육용|목데이터|목 데이터|Mock|mock|가상|샘플 데이터|테스트용|데모용|시연용" <변경 파일>
```

실패한 결과는 같은 에이전트에 `send_input`으로 실패 로그를 붙여 되돌린다. 새로 띄우면 맥락을 다시 쌓아야 한다.

### 5. 정리

끝난 에이전트는 `close_agent`로 닫는다. 완료 상태로 열려 있어도 동시 4개 상한을 차지한다.

## 에러 핸들링

- 4개가 이미 돌고 있다: 새로 띄우지 말고 `wait_agent`로 하나가 끝나기를 기다린 뒤 닫고 채운다. 플랫폼이 거절하지 않아도 스스로 멈춘다.
- `agent thread limit reached`가 뜬다: 완료 상태로 열어둔 에이전트가 자리를 차지하고 있다는 뜻이다. 결과를 이미 받은 것부터 `close_agent`로 닫는다. 실측에서 이 방법으로 해소했다.
- 결과가 검증에 실패한다: 1회 재시도한다. 두 번째도 실패하면 위임을 접고 직접 처리한다. 분해가 잘못됐다는 신호다.
- 두 에이전트가 같은 파일을 건드렸다: 둘 다 버리고 범위를 다시 자른다. 수동 병합하지 않는다.
- 자기 모델을 묻는 답이 이상하다: 서브에이전트는 부모의 지침을 상속받아 모델명을 잘못 답한다. 실제 값은 세션 로그의 `turn_context.model`에 있다. 무시해도 된다.

## 테스트 시나리오

**정상 흐름**: 서로 다른 엔진 모듈 3개에 테스트를 추가한다. 코드 작성이므로 워크트리 3개를 만들고 `xhigh`로 3개를 동시에 띄운다. 각자 `uv run pytest`를 돌려 결과를 붙여 온다. 상위 모델이 재실행으로 확인하고 닫는다.

**충돌 흐름**: 4개를 띄웠는데 5번째 과제가 생긴다. 대기 후 하나를 닫고 진행한다. 그중 둘이 같은 파일을 수정한 것이 드러나면 둘 다 버리고 범위를 다시 자른다.
