살아 있으면서 옛 코드를 돌려주기 때문에 오진을 유발한다. 이 주소로 상태를 확인하지 않는다.

## 2. Vercel 설정

### 프로젝트 빌드

| 항목 | 값 |
|---|---|
| Project | `kda-securities-lzix` |
| Root Directory | `frontend` |
| Framework Preset | `Vite` |
| Install Command | `npm install` |
| Build Command | `npm run build` |
| Output Directory | `dist` |

### Production·Preview 환경변수

```text
VITE_API_BASE_URL=https://kda-securities.onrender.com
VITE_SUPABASE_URL=<Supabase project URL>
VITE_SUPABASE_PUBLISHABLE_KEY=<Supabase publishable key>
```

- `VITE_API_BASE_URL`은 비어 있으면 안 되며 후행 `/`는 생략한다.
- Vite의 `VITE_` 변수는 build 시 번들에 들어가므로 값 변경 뒤 Vercel을 반드시 다시 배포한다.
- `SUPABASE_SECRET_KEY`, `DATABASE_URL` 등 서버 비밀값은 Vercel에 넣지 않는다.
- Production을 외부에 공유하려면 Vercel Deployment Protection이 로그인 없이 접근 가능한 정책인지 확인한다.

## 3. Render 설정

운영 서비스명은 Render 대시보드 기준 `KDA-securities`(Service ID `srv-d9hee07lk1mc73dqomf0`), health check는 `/health`다. `render.yaml`의 `name: pension-copilot-api`는 초기 blueprint 값이며 실제 대시보드 서비스명과 다르다. 상태 확인은 반드시 위 표의 실제 주소로 한다. Render 대시보드에는 서버 비밀값과 함께 다음 CORS 값을 설정한다.

```text
CORS_ORIGINS=["https://kda-securities-lzix-kda4.vercel.app","https://kda-securities-lzix-zeta.vercel.app"]
```

- 사용자가 실제 접속하는 모든 안정 alias를 JSON 배열에 정확히 넣는다.
- 값은 **JSON 배열 문자열**이어야 한다. 쉼표 나열·단일 URL·빈 문자열은 pydantic 파싱에 실패해 서버가 기동조차 하지 못한다.
- 임시 Preview URL은 매번 바뀌므로 원격 골든패스는 위 Production alias에서 검증한다.
- `render.yaml`이 `autoDeploy: false`이므로 `main` push만으로는 코드가 갱신되지 않는다. 코드 변경은 **Manual Deploy → Deploy latest commit**으로 반영한다. 환경변수 저장에 따른 자동 재시작은 기존 빌드를 그대로 쓴다.
- 대시보드 상단의 배포 커밋 해시가 최신 `main` HEAD와 같은지 확인한다.
- 무료 인스턴스는 유휴 뒤 첫 요청이 느릴 수 있다. 2026-07-24 실측에서는 첫 health/API 확인에 약 54초가 걸렸다.
- 시연 전에는 `/health`를 한 번 호출해 인스턴스를 미리 깨운다.

## 4. 2026-07-25 실측

### 해결된 항목

1. Render `KDA-securities`는 최신 `main`(`bd21abf`)으로 Manual 배포됐고 Live다. `/openapi.json` 경로 42개가 로컬 `main`과 일치한다.
2. `https://kda-securities.onrender.com/accounts/link-options` CORS preflight는 zeta·kda4·로컬 세 오리진 모두 HTTP 200이고 `access-control-allow-origin` 헤더가 정상 반환된다.

### 남은 항목

3. Vercel `zeta` alias의 배포 번들이 아직 폐기된 `https://pension-copilot-api.onrender.com`을 호출한다. 번들에서 문자열을 직접 확인했다. Vercel Production `VITE_API_BASE_URL`을 `https://kda-securities.onrender.com`으로 바꾸고 다시 배포해야 한다.
4. 이 상태에서는 프론트가 옛 서비스로 요청하므로, 옛 서비스에 없는 신규 API(`/me/rebalancing-reminder` 등)가 404가 되고 CORS도 거부된다.
5. Vercel `kda-securities`는 Root Directory 오류로 `vite: command not found`가 발생하는 중복 프로젝트다.

따라서 현재 원격 배포 상태는 **백엔드 정상 / 프론트 API 주소 교체·재배포 대기**다.

## 5. 복구·배포 순서

1. Vercel 운영 프로젝트를 `kda-securities-lzix`로 통일한다.
2. Vercel Production·Preview의 `VITE_API_BASE_URL`을 `https://kda-securities.onrender.com`으로 설정한다.
3. Render `CORS_ORIGINS`에 두 Production alias를 설정한다. (2026-07-25 완료)
4. Render를 Manual Deploy로 재배포하고 `/health`와 CORS preflight를 확인한다. (2026-07-25 완료)
5. Vercel을 최신 `main`으로 재배포하고, 배포 번들에서 API 주소 문자열을 직접 확인한다.
6. 브라우저에서 로그인 → 계좌 정보 확인 → 투자성향 → 홈 → 챗봇 → 계산기 → 전략 → User Pick 순으로 원격 골든패스를 검증한다.

## 6. 검증 명령

### Render 상태

```powershell
curl.exe -sS https://kda-securities.onrender.com/health
curl.exe -sS https://kda-securities.onrender.com/accounts/link-options
```

둘 다 HTTP 200이어야 한다.

### 배포 코드가 최신인지 확인

```powershell
curl.exe -sS https://kda-securities.onrender.com/openapi.json | `
  ConvertFrom-Json | ForEach-Object { $_.paths.PSObject.Properties.Name.Count }
```

대시보드의 배포 커밋 해시가 최신 `main` HEAD와 같은지도 함께 본다. 옛 서비스와 구분하는 가장 빠른 방법은 `/me/rebalancing-reminder` 경로 존재 여부다.

### CORS preflight

```powershell
curl.exe -sS -o NUL -D - -X OPTIONS `
  https://kda-securities.onrender.com/accounts/link-options `
  -H "Origin: https://kda-securities-lzix-zeta.vercel.app" `
  -H "Access-Control-Request-Method: GET" `
  -H "Access-Control-Request-Headers: content-type"
```

응답에 아래 헤더가 있어야 한다.

```text
access-control-allow-origin: https://kda-securities-lzix-zeta.vercel.app
```

### 프론트 확인

- 공유 주소가 Vercel 로그인 화면으로 이동하지 않는다.
- 계좌 정보 화면에 재시도 오류가 나타나지 않는다.
- 브라우저 Network에서 `/accounts/link-options` 요청 host가 `kda-securities.onrender.com`이다.
- API·SSE 요청에 CORS 오류가 없다.

배포 번들에서 직접 확인하려면 `index.html`이 참조하는 `/assets/index-*.js`를 내려받아 API 주소 문자열을 검색한다. `pension-copilot-api`가 남아 있으면 옛 환경변수로 빌드된 번들이다.
