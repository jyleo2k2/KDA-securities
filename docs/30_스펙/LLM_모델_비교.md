# LLM 모델 선택 근거 — 5개 모델 실측 비교

> 측정일 2026-07-27 · 재현 스크립트 `scripts/benchmark_narration_models.py`
> 원자료: `scripts/data/vendor_benchmark.json`(지표) · `scripts/data/vendor_answers.md`(모델별 답변 원문)

## 1. 왜 측정했나

내레이터 기본 모델이 `claude-haiku-4-5`인 근거가 문서에 문장으로만 남아 있었다.
"왜 Sonnet이 아닌가"도, "왜 OpenAI·Gemini가 아닌가"도 재현 가능한 자료가 없었다.

이전 문서가 인용하던 `검증 통과율 Haiku 60% vs Sonnet 20%`는 **쓸 수 없는 수치**다.
모델과 thinking 옵션을 동시에 바꾼 비교여서 어느 쪽이 원인인지 분리되지 않고,
측정 스크립트도 남아 있지 않아 재현이 불가능했다. 이 수치는 문서에서 제거했다.

## 2. 측정 설계

우리 구조에서 LLM의 역할은 좁다. 계산·판단은 규칙 엔진이 끝내고, LLM은 **이미 검증된
답변을 다시 서술**하기만 한다. 그래서 모델 간 비교는 "누가 더 똑똑한가"가 아니라
**"같은 안전성을 유지하면서 누가 더 싸고 빠른가"** 가 되어야 한다.

고정한 것 — 모델만 바꾸고 나머지는 전부 동일하게 뒀다.

- 운영 내레이터와 같은 `SYSTEM_PROMPT` 문자열
- 같은 입력(규칙 엔진의 검증 답변)
- 같은 판정 함수(`_adds_unverified_content`, `contains_unsafe_financial_claim`)
- thinking 등 벤더 고유 옵션 미사용(Gemini는 기본이 thinking on이라 명시적으로 끈다)

측정 대상은 운영 내레이터가 실제로 재서술하는 4개 인텐트에서 뽑은 **대표질문 10개**다.

| 인텐트 | 질문 수 | 질문 |
|---|---|---|
| `account_rule` | 3 | DC 위험자산 한도 / 연금저축 한도 유무 / IRP·DC 차이 |
| `pension_tax` | 4 | 세액공제 한도 / 공제율 구간 / 중도 인출 과세 / 수령 시 연령별 세율 |
| `mock_portfolio` | 2 | 현금성 편중 진단 / 단일 자산군 쏠림 진단 |
| `provider_disclosure` | 1 | DC형 사업자 수 |

모델당 10응답(케이스 10 × 반복 1), 5개 모델 총 50회 호출이다.

## 3. 실측 결과

| 모델 | p50 | p95 | 가드 통과 | 입력 토큰 | 출력 토큰 | $/응답 | 1,000응답 환산 |
|---|---|---|---|---|---|---|---|
| `google:gemini-3.5-flash-lite` | **1.16초** | **1.28초** | 80% | 575 | 82 | **$0.00038** | $0.38 |
| `anthropic:claude-haiku-4-5` | 1.21초 | 2.13초 | 80% | 1,068 | **69** | $0.00141 | $1.41 |
| `google:gemini-3.6-flash` | 5.25초 | 7.05초 | 80% | 575 | 84 | $0.00149 | $1.49 |
| `openai:gpt-5.6-luna` | 1.70초 | 4.28초 | 80% | 630 | 155 | $0.00156 | $1.56 |
| `anthropic:claude-sonnet-5` | 2.62초 | 4.01초 | 80% | 1,103 | 120 | $0.00511 | $5.11 |

`1,000응답 환산`은 자릿수 비교를 쉽게 하려고 곱한 **계산값**이지 실제 호출 횟수가 아니다.
이번 측정 50회의 실지출은 **$0.10**이다.

단가는 `scripts/data/model_pricing.json`에 분리해 뒀다(2026-07-27 벤더 공식 페이지 확인).
하드코딩하지 않는 이유는 가격이 개정되면 코드가 조용히 틀린 값을 내기 때문이다.

### 읽는 법

- **가드 통과율이 5개 모델 전부 80%로 같다.** 이게 이 측정의 핵심 결과다. 아래 §5에서 따로 다룬다.
- 입력 토큰이 Claude만 1,068~1,103으로 큰 것은 같은 프롬프트에 대한 **토크나이저 차이**다.
  한국어 시스템 프롬프트를 Claude가 더 잘게 쪼갠다. 프롬프트가 더 긴 게 아니다.
- `gemini-3.6-flash`는 thinking을 끄면 출력 토큰이 84로 내려오지만 **지연은 5.25초로 가장 느리다.**
  같은 벤더의 `3.5-flash-lite`(1.16초)보다 4.5배 느리다. 상위 모델이 항상 나은 게 아니라는
  가장 선명한 사례다.

## 4. 답변 품질 — 모델별 실제 응답

전문은 `scripts/data/vendor_answers.md`에 질문별로 5개 모델 답변을 나란히 저장했다.
숫자만으로 보이지 않는 문체·길이 차이를 사람이 직접 읽고 판단하기 위한 산출물이다.

### 숫자 정확도

10개 질문 전부에서 **5개 모델 모두 숫자 왜곡이 0건**이다. 세율(5.5/4.4/3.3%), 한도(600/900만원),
공제율(16.5/13.2%), 진단 임계값(80/50%), 사업자 수(42개사)가 전부 원문과 일치했다.

이건 모델이 훌륭해서가 아니라 **애초에 계산을 시키지 않았기 때문**이다. 규칙 엔진이 확정한
문장을 주고 다시 쓰라고만 했다. 우리 아키텍처가 의도한 결과가 그대로 나온 것이다.

### 문체 차이 (같은 질문, q05 공제율)

| 모델 | 답변 |
|---|---|
| `claude-haiku-4-5` | 총급여 5,500만원을 넘으면 세액공제율이 16.5%에서 13.2%로 낮아져요. |
| `claude-sonnet-5` | 총급여가 5,500만원을 넘으면 세액공제율(납입액 중 세금에서 공제받을 수 있는 비율)이 13.2%로 적용돼요, 이는 5,500만원 이하일 때 적용되는 16.5%보다 낮은 비율이에요. |
| `gpt-5.6-luna` | 총급여 5,500만원을 넘으면 연금계좌 납입액에서 세금을 공제받는 세액공제율이 13.2%로 적용돼요. 총급여 5,500만원 이하일 때의 16.5%보다 낮아요. |
| `gemini-3.6-flash` | 총급여가 5,500만 원을 넘으면 세액공제율(납부할 세금에서 직접 차감하는 비율)은 13.2%가 적용돼요. 이는 총급여 5,500만 원 이하일 때 적용되는 16.5%보다 낮은 수준이에요. |
| `gemini-3.5-flash-lite` | 총급여 5,500만 원을 초과하면 연금계좌(세제혜택을 받으며 노후 자금을 모으는 계좌) 세액공제율이 13.2%로 적용돼요. 이는 5,500만 원 이하일 때 적용되는 16.5%보다 낮은 수준이에요. |

읽어서 확인한 경향은 다음과 같다.

- **Haiku가 가장 간결하다.** 출력 토큰 평균 69로 5개 모델 중 최소다. 결론 우선 원칙에 가장 잘 맞는다.
- **Sonnet은 괄호 부연이 길다.** 토큰이 Haiku의 1.7배인데, 늘어난 분량이 대부분 용어 설명 괄호다.
  일부 응답은 문장을 쉼표로 이어 붙여 해요체 종결이 어색해진다(`적용돼요, 이는 ...`).
- **`gpt-5.6-luna`는 출력이 가장 길다(155토큰).** 원문에 없는 수식어를 붙여 문장을 늘리는 편이다.
- **Gemini 두 모델은 한국어 표기가 흔들린다.** `5,500만 원`처럼 띄어쓰기를 넣는데, 우리 화면 표기는
  `5,500만원`이다. 표기 통일이 필요하면 후처리를 붙여야 한다.
- **`gemini-3.5-flash-lite`는 권유 꼬리를 자주 붙인다.** `미리 확인해 두면 도움이 돼요`,
  `계획을 세우는 데 도움이 돼요` 같은 문장을 요청하지 않아도 덧붙인다. 자문업 문맥에서
  권유로 읽힐 여지가 있어 추가 가드가 필요하다.

## 5. 가드 통과율 80%의 정체 — 모델 차이가 아니다

5개 모델이 **정확히 같은 80%**를 기록한 것이 이상해서 원인을 추적했다.
실패한 2개는 전 모델 공통으로 `q01`(DC 70% 한도)과 `q03`(IRP vs DC)이었다.

원인은 모델이 아니라 `narration_guard.py`의 판정 방식이다. `guarantee` 패턴이
`%`와 `보장`을 40자 이내 거리에서 잡는데, 검증 원문의 `70%까지 ... 원리금보장상품`이
여기에 걸린다. 원문도 후보도 함께 걸리므로 부분집합 비교로 통과해야 정상인데,
가드가 **정규화된 매치 문구 전체를 문자열로 비교**해서 사이 문장이 조금만 달라져도 탈락한다.

```text
원문 매치:   ('guarantee', '70%까지일반위험자산으로운용할수있어요나머지30%는원리금보장')
후보 매치:   ('guarantee', '70%까지일반위험자산으로운용할수있고나머지30%는원리금보장')
                                          ^^^^ 어미만 다름 → issubset 실패 → 재서술 폐기
```

즉 **오탐이며, 어떤 모델을 써도 통과할 수 없는 케이스**다. 사용자에게 틀린 답이 나가지는
않는다(가드는 안전한 방향으로 실패해 검증 원문을 그대로 보여준다). 다만 DC·IRP 70% 안내는
사실상 항상 재서술이 폐기되고 있으므로, API 비용을 쓰고 결과를 버리는 셈이다.

이 결함은 이 문서의 범위 밖이며 별도 작업으로 다룬다. 발표에서도 "모델별 안전성 차이"로
읽히지 않도록 이 해석을 그대로 밝힌다.

## 6. 결론

**같은 안전성이면 싸고 빠른 쪽을 쓴다.** 다섯 모델의 숫자 정확도와 가드 통과율이 동일한
이상, 남는 선택 기준은 비용·속도·문체뿐이다.

- 내레이터는 `claude-haiku-4-5`를 유지한다. 상위 모델(Sonnet)은 3.6배 비싸고 2.2배 느리면서
  안전성 지표가 같다. 출력이 가장 간결해 결론 우선 답변 원칙에도 맞는다.
- 뉴스 요약은 `claude-sonnet-5`를 유지한다. 기사 원문을 읽고 사실을 압축하는 작업은 성격이
  다르고, 결과가 DB에 저장돼 재사용되므로 지연이 사용자에게 노출되지 않는다.
- **벤더 종속은 없다.** `gpt-5.6-luna`와 `gemini-3.5-flash-lite` 모두 같은 프롬프트·같은 가드에서
  동일한 통과율로 동작했다. 벤더 장애나 가격 개정 시 교체 가능하다는 것을 측정으로 확인했다.
- `gemini-3.5-flash-lite`는 Haiku보다 3.7배 싸고 근소하게 빠르다. 유일한 걸림돌은 권유성 문장을
  덧붙이는 성향과 한국어 표기 흔들림이다. 비용이 문제가 되는 시점에는 후처리 가드를 붙여
  전환을 검토할 수 있다.

솔직하게 적어둔다. **"Claude가 가장 우수해서 골랐다"고 말할 근거는 이 측정에 없다.**
우리 구조에서는 LLM이 검증된 수치를 서술만 하므로 모델 등급이 답변 품질로 이어지지 않는다.
이건 아키텍처의 약점이 아니라 의도한 강점(Explainable by Design)의 증거다.

## 7. 재현 방법

```bash
uv run python scripts/benchmark_narration_models.py \
    --model anthropic:claude-haiku-4-5 \
    --model anthropic:claude-sonnet-5 \
    --model openai:gpt-5.6-luna \
    --model google:gemini-3.6-flash \
    --model google:gemini-3.5-flash-lite \
    --pricing scripts/data/model_pricing.json \
    --json-out scripts/data/vendor_benchmark.json \
    --answers-out scripts/data/vendor_answers.md
```

기본은 모델당 10응답이다. `--repeat`을 올리면 호출 수와 비용이 배로 늘어난다.
API 키는 루트 `.env`의 `ANTHROPIC_API_KEY`·`OPENAI_API_KEY`·`GOOGLE_API_KEY`에서 읽으며,
키가 없는 벤더는 건너뛰고 사유를 남긴다.
