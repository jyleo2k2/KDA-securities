# 기술 아키텍처 — 연금 코파일럿

> 코드·데이터·외부 연동의 기술 SSOT. 역할을 겹치지 않게 자르고 결과를 재현하기 위한 계약이다.
> 근거: [기획서.md](../10_기획/기획서.md) v2.5 §4·§7 · 단계: 기존 원격 실데이터 E2E·챗봇 pydantic-ai·BGE-M3 하이브리드 검색·ETF 원격 통합 완료 / ETF 위험·스트레스 대기

## 1. 확정 스택과 단방향 의존

```text
[① 프레젠테이션]
React + TypeScript + Vite 모바일 PWA
        │ REST/JSON
        ▼
[② API·오케스트레이션]
FastAPI
  ├─ FSS/KRX/KIS/KIND/DART/법령/NAVER 외부 API 수집·조회
  ├─ 규칙 엔진 도구 호출
  ├─ PostgreSQL 구조화 조회
  ├─ RAG 검색(PostgreSQL 전문검색 + pgvector)
  └─ Claude API 설명·Q&A 하네스
        │
        ├───────────────┐
        ▼               ▼
[③ 비즈니스 로직]   [④ 데이터]
Python 규칙 엔진     Supabase PostgreSQL + 검증 캐시
핵심 6모듈 +         구조화 테이블 + pgvector
ETF 근거 엔진        + 원본·정규화 JSON
```

의존 방향은 `frontend → FastAPI → engine/data`다. 역방향 import를 금지한다.

- 프론트엔드는 엔진·DB를 직접 계산 계층으로 사용하지 않고 REST 계약에 의존한다.
- FastAPI는 인증 컨텍스트, 외부 API, DB, 규칙 엔진, RAG와 LLM을 오케스트레이션한다.
- 규칙 엔진은 가능한 한 순수 함수로 유지하며 FastAPI·Supabase·LLM에 의존하지 않는다.
- PostgreSQL은 원본·상태·실행 이력을 저장하지만 제품 판단 로직을 대신하지 않는다.
- Claude API는 엔진 수치와 검색 근거를 설명할 뿐 직접 계산·판정하지 않는다.

## 2. 규칙 엔진 6모듈 — 계산·판단의 단일 소스

| # | 모듈 | 입력 → 출력 |
|---|---|---|
| 1 | 성향 분석 | 설문 → 5단계 성향(규칙 스코어링) |
| 2 | 계좌 규칙 검사 | 계좌 유형·보유 상품 → DC형/IRP 한도 또는 연금저축 적격성 판정 |
| 3 | 계좌별 진단 | 보유 상품·현금성 자산·자산군 비중 → 계좌별 운용 점검 항목 |
| 4 | 통합 집계 | DC형·IRP·연금저축 자산 → 전체 자산군 비중·중복 |
| 5 | 적립 시뮬레이션 | 계좌별 납입액·기간·승인 가정수익률 → 개별·합산 시나리오 적립금 |
| 6 | 포트폴리오 예시 | 성향·기간·계좌 규칙 → 자산군 단위 전략·교육용 예시·근거 |

> 설명 가능성은 별도 예측 모델이 아니라 엔진 입력·출력·규칙 버전·출처를 연결해 확보한다. 화면의 계좌 상태 카드, 단계별 운용 원리, what-if는 같은 엔진을 다른 입력으로 실행한 표현이다.

## 3. FastAPI·LLM·RAG 계약

- **Engine tools**: 위 6개 엔진 모듈을 명시적 입력·출력 스키마를 가진 도구로 등록한다.
- **Retrieval tools**: 공식 지식 RAG, 구조화 공시 조회, 최신 뉴스 조회를 서로 다른 도구로 둔다.
- **Guardrails**: 수치는 엔진 또는 SQL/API 결과만 인용한다. 성향 밖 상품과 계좌 규칙 위반 결과를 차단한다.
- **RAG**: 제도·용어·규칙의 근거를 찾는다. 최신 공시 숫자, 뉴스 목록, 사용자 계좌 계산을 RAG에 맡기지 않는다.
- **LLM**: 엔진 결과와 검색 근거를 요약·비교·설명한다. 새 숫자·목표가·매매의견을 만들지 않는다.
- **Verification loop**: 답변 수치와 엔진·SQL 결과를 대조하고 불일치하면 재생성 또는 답변 거절한다.
- **Evidence**: 답변과 엔진 실행, 적용 규칙, 데이터 출처, RAG 청크, 뉴스 링크를 연결한다.
- **Logging**: 입력 스냅샷·출력·엔진 버전·규칙 버전·모델/프롬프트 버전·근거를 감사 가능하게 남긴다.
- **Audited API**: `/engine/risk-cap/audited`는 Supabase Bearer token으로 uid를 검증하고, DB 규칙 버전·파라미터와 계산 결과를 대조한 뒤 `run_id`를 반환한다. 인증 없는 `/engine/risk-cap`은 데모 계산만 하며 DB에 쓰지 않는다.
- **Chatbot MVP**: `/chat/demo`는 자연어 질문을 계좌 규칙·목시나리오·공시·뉴스·연금계좌 세액공제/연금외수령 추정·범위 밖 요청으로 분류하고 Pydantic 응답 계약으로 근거 연결을 검증한다. 연금세액 질문은 구조화된 사용자 입력을 `pension_tax`로 받고 Planner가 선택한 읽기·계산 전용 Tool만 호출한다. `/chat/demo/capabilities`와 `/chat/demo/scenarios`는 프론트엔드 연결용 기능·시나리오 계약을 제공한다. `/engine/mock-scenario/{code}`는 같은 목시나리오를 홈 화면 시연용으로 엔진에 태워 반환한다.
- **Pension tax tools**: `/engine/pension-tax-credit`와 `/engine/non-pension-withdrawal-estimate`는 2026년 규칙 버전을 고정한 순수 엔진을 공유하되 입력 스키마를 분리한다. 세액공제 Tool은 계좌 잔액을 요구하지 않고, 연금외수령 Tool은 일반 인출 계산에만 잔액·당해연도 납입액을 요구한다. 챗봇의 제한된 결정론적 슬롯 추출기는 질문에 명시된 계좌별 금액·소득 기준·인출 사유만 구조화하며 계산하지 않는다. 후자는 과거 미공제 원금·IRP 이연퇴직소득을 구분할 수 없으면 가정을 표시한 최대 기타소득 원천징수 추정만 반환하고, 부득이한 인출 사유는 잔액 없이도 금액을 만들지 않고 전문가 검토 대상으로 돌린다.
- **Local RAG fallback**: 서버 `DATABASE_URL`이 없을 때는 허용된 프로젝트 검증 문서를 제목 단위로 분할한 로컬 전문검색을 사용한다. 공시 fixture는 챗봇 수치 답변에 사용하지 않는다.
- **Claude narration(pydantic-ai)**: API 키가 있으면 pydantic-ai Agent(NativeOutput 구조화 출력 + adaptive thinking)가 검증된 답변만 자연어로 재서술하고, 검토 과정(`narration_reasoning` — thinking 요약 우선, 없으면 검토 노트)을 함께 반환한다. 원문에 없던 숫자를 본문에서 감지하면 결정론적 답변으로 복귀하고, 검토 과정에서 감지하면 그 필드만 생략한다. API 키가 없거나 호출이 실패해도 골든패스는 동작한다.

## 4. 데이터 계층 — SQL/RAG 및 실/목 경계

모든 수치의 종류·모집단·변환·허용 용도와 목데이터 병합 게이트는 [데이터 품질·설명 가능성 계약](./데이터_품질_계약.md)을 따른다.

| 데이터 | 실/목 | 저장·조회 | 용도 |
|---|---|---|---|
| 통합연금포털(FSS) OpenAPI 공시 | **실** | PostgreSQL 공시 스냅샷 + 원본 JSON + 수집 이력 | 회사별·제도별 적립금·과거 수익률·수수료 |
| KRX ETF·지수 | **실** | 원본 JSON·매니페스트·검증 캐시 | 상장·NAV·유동성·지수 위험·스트레스 근거 |
| KIS ETF·수정주가 | **실** | 원본 JSON·상품별 수정주가 캐시 | 적격 후보·비용·기업행위 조정 가격·상관관계 |
| 금융위원회·KIND·DART·법령 | **실/공식 근거** | 원본·정규화 캐시·출처 URL | 자산군·분배금·분배락·공시·계좌 규칙 검증 |
| NAVER 검색 API 뉴스 | **실 메타데이터 + 파생 요약** | 한국·미국 증시 선별 점수·근거·BGE-M3 중복 벡터 + 제목·검색 요약·원문 링크·발행일 + 원문 기반 LLM 3줄 요약·본문 해시·모델/프롬프트 버전 | 최근 5일 주요 증시 뉴스 답변 |
| 정부·공공기관 공식 문서 | **검증 지식** | 문서·청크·전문검색 값·pgvector embedding | 제도·용어·규칙 RAG |
| 사용자 DC형·IRP·연금저축계좌 | **목** | 시나리오·계좌·보유자산 구조화 테이블 | 실제 계좌 연동 대체 |
| 사용자가 직접 입력한 연금저축·IRP 잔액/납입액 | **사용자 입력** | 요청 Pydantic 스키마 → 규칙 엔진; RAG·공시 데이터와 혼합/embedding 금지 | 세액공제·연금외수령 교육용 추정 |
| 공개 포트폴리오 | **목** | 익명 프로필·포트폴리오·보유자산 | 벤치마킹 시연 |

고정 원칙:

- FSS fixture는 파서·회귀 테스트 입력이다. 공시 테이블의 실 적재는 서버가 OpenAPI를 직접 호출한 결과로 생성한다.
- 공시 수집은 호출 종류·요청 기간·시각·상태·수신/적재 건수·오류를 `ingestion_runs`에 남긴다.
- 금액은 원 단위 `numeric`, 수익률·수수료율은 고정소수점 `numeric`을 사용하고 원본 값·단위·payload를 보존한다. FSS 응답 본문에는 적립금 단위가 없어 현재 백만원/억원 변환은 프로젝트 가정과 `reserve_unit_not_in_api_response` 품질 플래그를 함께 저장하며, 운영 전 공식 단위 근거를 추가 확인한다.
- NAVER 뉴스 기사 전문은 저장하거나 embedding하지 않는다. 공개 원문 HTML은 요약 작업 중에만 최대 2MB까지 읽고, 추출한 본문으로 3줄 요약과 SHA-256을 만든 뒤 메모리에서 폐기한다. 최신성은 `published_at`으로 판정한다.
- RAG에는 검증된 공통 지식만 넣는다. 사용자 목계좌·성향·진단·대화의 개인정보성 필드는 embedding하지 않는다.
- 모든 화면 수치에는 출처·기준일·수집 시각·실/목 구분을 표시한다.
- 관측값·파생값·합성값·미래 가정·엔진 결과를 동일한 수익률 필드에 섞지 않는다.

## 5. PostgreSQL 스키마 그룹

실제 마이그레이션의 테이블명과 제약이 최종 기준이다.

| 목 벤치마크 | `mock_public_profiles`, `mock_public_portfolios`, `mock_public_portfolio_holdings` | 익명 공개 포트폴리오 시연 |
| 규칙·실행 | `rule_sets`, `pension_rules`, `engine_runs`, `engine_run_evidence` | 버전형 규칙, 엔진 입력·출력, 규칙·출처 근거 |
| RAG·콘텐츠 | `knowledge_documents`, `knowledge_chunks`, `news_items`, `curated_contents` | 공식 문서·청크·embedding, 뉴스 메타데이터·파생 3줄 요약, 검수 콘텐츠 |
| 챗봇 | `chat_sessions`, `chat_messages`, `chat_message_evidence`, `chat_request_idempotency` | 대화와 엔진·문서·청크·뉴스 근거 연결, 요청 재처리 방지 |
| 사용자·성향·계좌 | `user_profiles`, `profile_question_sets`, `profile_questions`, `profile_question_options`, `investment_profile_assessments`, `investment_profile_answers`, `pension_accounts`, `account_snapshots`, `account_cash_flows`, `financial_products`, `account_holding_snapshots` | Auth 사용자 확장, 진단 이력, 실·목 계좌 공통 구조 |
| ETF 유니버스 | `etf_dataset_versions`, `etf_universe_products`, `etf_return_histories` | 버전형 계좌 적격 상품과 총수익 이력 |

`knowledge_chunks.embedding`은 **BGE-M3(1024차원)**로 확정됐다. 적재는 `scripts/embed_knowledge_chunks.py`(선택 그룹 `uv sync --group embeddings`), 검색은 전문검색+벡터 RRF 하이브리드이며 임베딩 미설치·실패 시 전문검색으로 폴백한다. 원격 45개 청크의 차원과 `knowledge_chunks_embedding_hnsw_idx`를 재검증했다(2026-07-19).

## 6. 외부 API 수집 계약

### 6.1 통합연금포털(FSS)

1. FastAPI 서버 프로세스가 환경변수의 API 키로 직접 호출한다.
2. 호출 시작 시 `ingestion_runs`를 만들고 성공·부분 성공·실패를 기록한다.
3. 원본 응답을 보존하고 회사명을 표준 기관·별칭에 연결한다.
4. 퇴직연금과 연금저축은 필드·단위가 다르므로 별도 공시 테이블에 정규화한다.
5. DB·DC·IRP 공시는 보존하되 사용자 진단 대상은 DC·IRP·연금저축으로 제한한다.
6. fixture와 실호출 결과를 혼동하지 않으며 출처·기준분기·수집시각을 검증한다.

### 6.2 NAVER 검색 API

1. API 자격증명은 FastAPI 서버 환경변수에만 둔다.
2. GitHub Actions가 24시간마다 한국·미국 증시 검색군 14개를 날짜순으로 조회한다. NAVER 뉴스 페이지 링크와 승인 매체 원문 URL이 모두 확인되고 발행 후 24시간 이내인 결과만 후보가 된다.
3. 규칙 엔진이 시장 영향 30점·직접 관련성 20점·구체성 15점·출처 신뢰도 15점·최신성 10점·새로움 10점으로 계산해 70점 이상만 남긴다. 추천주·목표가·소문·광고와 증시 연관이 약한 보험·부동산·연금 기사는 제외한다.
4. 정규화 URL·제목 해시·사건 지문·본문 SHA-256과 BGE-M3 유사도 0.90 이상을 중복으로 차단한다. 한국·미국 각 8건을 우선하고 동일 사건 1건, 동일 매체 3건, 동일 주제 3건 상한으로 하루 최대 20건을 고른다.
5. 원문 URL·리다이렉트를 공개 IP로 제한하고 HTML 본문을 임시 추출한 뒤 Claude 구조화 출력으로 정확히 한국어 3문장을 생성한다. 첫 줄은 사건, 둘째 줄은 수치·원인·시장 반응, 셋째 줄은 영향 시장·업종과 원문상 불확실성이다.
6. 원문에 없는 숫자나 새 투자 행동 표현을 거부한다. 본문은 저장하지 않고 DB에는 선별 점수·근거·중복 벡터, 3문장, 모델·프롬프트 버전, 본문 SHA-256과 요약 시각만 저장한다.
7. 외부 호출과 요약을 모두 끝낸 뒤 짧은 DB 트랜잭션에서 검증 완료 기사만 적재한다. 100건 미만이면 남은 자리만 채우고, 100건일 때는 새 기사 20건이 모두 준비된 경우에만 가장 오래된 20건을 지우고 20건을 넣는다.
8. 증시 뉴스 질문에는 최근 5일 후보 중 최대 3건을 무작위로 뽑아 `첫 번째 3줄 요약 → 원문 링크 → 두 번째 → 원문 링크 → 세 번째 → 원문 링크` 순서로 결정론적으로 반환한다. 뉴스 외부 입력은 Claude 내레이터에 다시 전달하지 않는다.

### 6.3 KRX ETF·지수 일별 통계

1. 서버 프로세스가 `KRX_API_KEY`를 헤더로 전달하며 키를 로그·예외·산출물에 남기지 않는다.
2. 날짜별 원본 JSON과 SHA-256 매니페스트를 `data/raw/krx/`에 보존하고, 재실행 시 검증된 파일은 다시 호출하지 않는다.
3. 휴장일 플레이스홀더와 실제 거래 관측을 종가 존재 여부로 분리한다.
4. KRX·KOSPI·KOSDAQ 시리즈와 채권지수 API로 대표 지수 8종의 과거 위험·상관관계 근거를 별도 저장한다.
5. 연금 적격 ETF의 가격수익률·변동성·상관관계는 한투 수정종가를 우선 사용하고, 비연금 비교상품 또는 누락 상품만 KRX 종가를 대체값으로 사용한다.
6. KRX NAV·거래대금·순자산·기초지수는 거래소 근거로 유지하며, 과거수익률을 미래 계획수익률로 외삽하지 않는다.
7. 수수료·분배금·연금계좌 적격성은 KRX 값으로 추정하지 않고 별도 검증 상품 마스터를 요구한다.

상세 계약과 재현 명령은 [KRX_데이터_수집_계약.md](./KRX_데이터_수집_계약.md), [KRX_지수_데이터_수집_계약.md](./KRX_지수_데이터_수집_계약.md)를 따른다.

## 7. Supabase 보안 계약

- 브라우저에는 publishable key만 허용하며 `service_role` 또는 secret을 노출하지 않는다.
- 노출 스키마의 모든 테이블은 RLS를 활성화한다. Data API 접근 권한(`GRANT`)과 행 접근 정책(RLS)은 별도로 검증한다.
- 사용자 소유 실행·대화 데이터는 `TO authenticated`와 `(select auth.uid()) = owner_id` 조건을 함께 적용한다.
- UPDATE 정책은 `USING`과 `WITH CHECK`를 모두 두고 필요한 SELECT 정책을 함께 둔다.
- 내부 수집·규칙·공시 원본·RAG 데이터는 기본적으로 FastAPI 서버 경유로 접근한다.
- 뷰를 노출할 때는 `security_invoker = true`를 사용하거나 노출 권한을 명시적으로 차단한다.
- 원격 `KDA-securities`에서 마이그레이션·RLS·인덱스·Data API 권한과 익명/인증/service_role 역할을 검증했다(2026-07-15). 내부 테이블의 `anon` 권한은 회수하고 인증 사용자에게는 소유 대화·엔진 결과 최소 권한만 부여한다.
