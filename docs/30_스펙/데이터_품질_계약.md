# 데이터 품질·설명 가능성 계약

> 공시·뉴스·연구 통계·합성 목데이터·규칙 엔진 산출값에 공통 적용하는 병합 기준이다. 숫자가 존재한다는 사실보다 그 숫자의 의미와 적용 범위를 재현할 수 있는지가 우선이다.

## 1. 데이터 종류를 먼저 고정한다

| `data_kind` | 의미 | 제품 사용 |
|---|---|---|
| `observed` | API·공시·가격 등에서 직접 관측한 값 | 출처·기준일·단위 확인 후 사용 |
| `derived` | 관측값을 집계·비율·가중평균 등으로 변환한 값 | 계산식과 입력 출처를 함께 표시 |
| `synthetic` | 통계와 가정으로 생성한 가상 개인·계좌 값 | 데모·분포·부하 테스트만 사용 |
| `scenario` | 사용자가 선택한 미래 가정 또는 충격값 | 교육용 what-if만 사용, 예측으로 표현 금지 |
| `engine_result` | 버전이 고정된 규칙 엔진의 계산 결과 | 입력·규칙·가정·엔진 버전과 함께 사용 |

한 필드가 둘 이상의 종류를 동시에 의미하면 안 된다. 특히 `return_pct`처럼 범위가 불명확한 이름을 금지하고 `observed_product_trailing_12m_return_pct`, `synthetic_account_return_pct`, `calculated_twr_pct`처럼 의미를 이름에 드러낸다.

## 2. 모든 숫자에 필요한 계보

외부 또는 파생 수치는 최소한 다음 정보를 가져야 한다.

- `source_id`, 원문 URL 또는 원본 payload 위치
- `as_of_date`와 관측기간
- 원단위·백만원·퍼센트 등 `unit`
- `observed_population`: 실제 관측 모집단과 제외 범위
- 단순평균·적립금가중평균·중앙값 등 `aggregation_method`
- 파생값이면 `transformation`과 입력 필드
- 합성·시나리오면 `assumption_id`, 버전, 근거, 허용 용도
- 해석상 주의가 필요하면 `quality_flags`

출처가 공식이어도 적용 범위가 다르면 그대로 전용하지 않는다. 예를 들어 DC형·기업형 IRP 합산 설문은 `observed_population=DC_AND_CORPORATE_IRP_SURVEY`로 기록하고 순수 DC 통계로 표시하지 않는다. 상품 적립금 가중평균 수익률은 개인 혼합계좌 수익률로 사용하지 않는다.

## 3. 수익률 계약

- 공식 공시 수익률은 해당 공시의 상품·회사·계약 모집단에 대한 과거 관측값이다.
- 전략 성과는 평가액 시계열에서 입출금 영향을 제거한 TWR로 계산한다.
- 사용자 납입시점까지 반영한 체감성과는 XIRR로 별도 표시하며 전략 비교에 사용하지 않는다.
- 합성계좌 수익률은 자산군별 동일 기간 과거수익률과 실제 보유비중의 가중 결과로 생성한다. 계좌종류별 목표 평균에 사후 강제 보정하지 않는다.
- 현금·채권·주식 등 모든 자산군의 수익률과 비용을 각각 계산하고 기여도를 보존한다.
- 미래 가정은 `scenario`로 저장하며 관측수익률·합성수익률·엔진 실현성과와 같은 컬럼이나 화면에 섞지 않는다.

계좌 수익률의 최소 설명 단위는 `자산군 비중 × 자산군 과거수익률 - 비용`이다. 엔진은 총수익률뿐 아니라 자산군별 기여도와 적용 출처를 함께 반환해야 한다.

## 4. 목데이터 브랜치 적용 계약

`origin/codex/mock-pension-data`는 생성 아이디어와 재현성 검증만 채택하며 현재 상태로 병합하지 않는다.

| 브랜치 값 | 애플리케이션 계약 |
|---|---|
| `DC` | `dc` |
| `IRP` | `irp` |
| `PENSION_SAVINGS_FUND` | `pension_savings` |
| 대문자 시나리오 코드 | `mock_scenarios.code`의 버전형 소문자 코드 |
| `asset_class` | `asset_classes.code` 조회 후 `asset_class_id` |
| `amount_krw` | `market_value_krw` |
| `weight` | 금액 합계 검증용 파생값, DB의 단일 진실로 사용하지 않음 |
| `trailing_12m_return_pct` | 분포 실험용 합성값, 실제/전략 성과 테이블에 적재하지 않음 |

보유자산에는 `instrument_name`, `risk_treatment`, 필요한 경우 `statutory_exception`을 명시한다. 사용자 1만 명을 실제 사용자 테이블이나 `auth.users`에 만들지 않고 별도의 합성 벤치마크 데이터셋으로 취급한다.

저장소에는 3개 골든패스 fixture와 생성기·출처·검증 요약만 커밋한다. 1만 명 CSV는 명령으로 재생성하고 기본적으로 Git에 커밋하지 않는다.

## 5. 자동 병합 게이트

다음 조건을 모두 통과해야 애플리케이션용 목데이터로 병합할 수 있다.

1. **스키마 계약**: 계좌·시나리오·자산군 코드와 필수 필드가 현재 migration과 일치한다.
2. **의미 계약**: 모집단·기간·평균방식·단위가 출처 원문과 일치한다.
3. **인과 계약**: 계좌 수익률이 보유자산 수익률·비중·비용에서 재계산된다.
4. **불변조건**: 계좌와 보유자산 합계 일치, DC·IRP 일반 위험자산 70% 이하, 연금저축 규칙 분리.
5. **설명 재현**: 임의 계좌의 총수익률을 자산군 기여도까지 다시 계산해 같은 값이 나온다.
6. **경계 입력**: `--users 0`, `1`, `10`, `300`, `10000`의 기대 동작이 테스트로 고정된다. 0은 명시적으로 거부하거나 빈 결과를 반환한다.
7. **재현성과 규모**: 같은 시드의 파일 해시가 같고, 1만 명은 생성 명령과 검증 요약으로 재현된다.
8. **품질 도구**: 전체 Pytest·Ruff·SQL 계약 검증을 통과한다.

## 6. Supabase 저장·노출 원칙

- 합성 대규모 벤치마크는 서버 수집·분석용이며 `service_role` 경로로만 적재한다.
- `public`에 테이블을 추가하면 RLS를 반드시 활성화하고 Data API `GRANT`와 RLS 정책을 별도로 검증한다.
- 공개 화면에는 검수된 집계 또는 `is_published=true`인 대표 포트폴리오만 노출한다.
- `service_role` 키는 프론트엔드에 두지 않는다.
- 원격 적용은 migration 이력, 적재 행 수, anon/authenticated 조회 결과, Advisor 결과를 함께 남겨야 완료로 본다.

## 7. 다른 데이터 분야에도 동일 적용

- **FSS 공시**: API 필드명, 단위 미기재 여부, 회사·상품·기간 범위를 보존한다.
- **NAVER 뉴스**: 검색 결과 메타데이터와 기사 사실을 구분하고 원문 전문을 임의 저장하지 않는다.
- **RAG 문서**: 문서 버전·발행기관·기준일을 보존하고 개인 계좌정보를 embedding하지 않는다.
- **포트폴리오 전략**: 정책 파라미터와 과거 검증 결과를 분리하고 규칙 변경 시 버전을 올린다.
- **화면 지표**: 출처 칩과 기준일, 계산 또는 가정 정보를 함께 표시한다. 데이터 원천 분류는 내부 계약으로 관리한다.

## 8. 이번 통합의 완료 조건

1. 생성기만 현재 계약에 맞춰 재베이스한다.
2. 수익률 강제 평균 보정을 제거하고 자산군 기여도 방식으로 교체한다.
3. 모집단·가중방식 메타데이터를 수정한다.
4. 대표 fixture만 저장소에 두고 대규모 CSV는 제외한다.
5. 어댑터·경계값·설명 재현 테스트가 모두 통과한 뒤 별도 PR로 병합한다.
