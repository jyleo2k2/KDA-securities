# ETF 테마 챗봇 계약

## 목적과 범위

챗봇이 ETF 테마 1~23을 설명하고, 사용자의 완료된 투자성향 설문과 보유 계좌 범위 안에서 교육용 ETF 비교 후보를 제시하며, 요청 시 한국투자증권 API 구성종목 비중을 근거로 답한다. 상품 선택·주문·미래 수익률 예측은 하지 않는다.

## 데이터 경계

| 데이터 | 단일 원본 | 답변 경계 |
|---|---|---|
| 테마 쉬운 설명·포함 분야·관찰 요인·비유·정의·장점·위험 | `data/reference/etf_theme_catalog.json` | 사용자 조사자료 기반 서비스 설명·카탈로그 `2026-07-20.4` 프로젝트 승인 |
| 테마별 대표기업 3곳·쉬운 설명·선정 이유 | `data/reference/etf_theme_catalog.json` | 기업 공식 홈페이지 URL·기준일을 함께 보존한 교육용 예시 |
| 테마 질문 유형별 공식 검증 상태 | `etf_theme_content_reviews`, `etf_theme_content_evidence` | 카탈로그 버전·응답 payload SHA-256과 승인 지식 근거 연결 |
| 계좌별 ETF 적격성·비용·품질지표 | `data/cache/returns/{account}_etf_cost_return_*.json` | 규칙 엔진 산출물 |
| ETF 상품별 승인 설명 | `data/reference/etf_product_descriptions.json`·`etf_product_descriptions` | 상품명 정규화 키로 연결한 전체 설명·답변용 한 줄 설명 |
| ETF 상품 설명 통합 원문·공식 보강 | `docs/20_리서치/ETF_상품/ETF_상품_설명_통합원문.md` | 공개 대화 17개 메시지와 원문 미수록 상품의 운용사 공식 설명 |
| 구성종목·비중 | `data/cache/kis/etf_snapshot_YYYY-MM-DD.json` | 한국투자증권 API 기준일 스냅샷 |
| 테마 질문 의도와 응답 | `backend/app/chat/` | 결정론적 라우팅·근거 연결 |

테마 설명과 숫자 근거를 섞어 출처를 가장하지 않는다. 특히 구성종목 배열의 `etf_cnfg_issu_rlim`은 한국투자증권이 반환한 값을 그대로 Decimal로 정규화하고, 챗봇이 비중을 새로 추정하지 않는다.

### 조사자료 정규화 원칙

- 공유 대화의 `쉽게 말하면`, 포함 기업·분야, 가격 동인과 한 줄 비유는 테마별 `plain_summary`, `exposure_segments`, `performance_drivers`, `one_line_analogy`로 보존한다. 주의점은 `risks`, 서비스 분류 설명은 `definition`으로 관리한다.
- 대표기업은 테마마다 정확히 3곳을 `representative_companies`에 보존한다. 각 항목은 기업명, 테마에서의 역할, 초보자용 설명, 대표 사례로 고른 이유, 기업 공식 홈페이지 URL, 기준일을 포함한다.
- `performance_drivers`는 테마마다 정확히 3개를 보존한다. 각 항목은 `관찰 요인명: 해당 요인이 산업의 주문·매출·비용·가동률 등에 연결되어 성과 평가에 필요한 이유` 형식으로 작성하며 미래 수익률 예측으로 표현하지 않는다.
- 런타임은 `data/reference/etf_theme_catalog.json`만 읽는다. 공유 대화 원문이나 동일한 내용을 23개 Markdown 파일로 복제하지 않는다.
- ETF 상품 설명은 종목코드가 없는 승인 원문도 연결할 수 있도록 상품명을 키로 사용한다. 연결할 때는 NFKC 정규화, 대소문자 통일, 공백 제거만 적용하며 정규화 결과가 충돌하면 자동 선택하지 않고 적재를 거부한다.
- 상품 설명 저장소에는 승인 원문의 전체 설명과 답변용 한 줄 설명을 함께 보존한다. 원문 미수록 상품은 운용사 공식 페이지·팩트시트에서 설명을 먼저 보강한다.
- 런타임은 순위 계산이 끝난 최대 3개 후보만 묶어 LLM에 전달한다. 입력은 해당 상품의 통합 원문 발췌·승인 또는 운용사 공식 설명·검증된 기초/비교지수·KIS 상위 구성종목·분류값으로 제한한다. 전체 원문을 매 요청마다 통째로 전달하지 않는다.
- LLM 출력은 종목코드 완전성·중복·길이·금지 표현·위험 금융주장과 입력에서 그대로 복사한 `support_quote`를 검증한다. 검증 실패·API 비활성·근거 원문 누락 시 `승인 한 줄 설명 → 기초지수+KIS 구성종목 → 기초지수 → 구성종목 → 테마 분류` 순의 결정론 폴백을 사용하며 `상품 설명 확인 필요`를 노출하지 않는다.
- 공통 체크리스트와 테마 간 중복 비교는 이 계약과 리서치 문서에서 관리하고, ETF 구성종목·비중은 정적 설명에 섞지 않는다.
- 공식 링크 교차 검토와 프로젝트 승인을 받은 범위만 `docs/20_리서치/ETF_테마/README.md`와 `data/knowledge/approved_documents.json`을 통해 승인 RAG로 승격한다. 공유 대화 URL 자체는 공식 발행기관 출처로 표시하지 않는다.

### 공식 검증 장부

- 답변 문구의 단일 원본은 계속 JSON 카탈로그다. DB에 같은 문구를 복제하지 않는다.
- 검토 단위는 23개 테마 × `overview`, `representative_companies`, `investment_considerations`, `performance_drivers`, `risks` 5종의 115개다.
- 각 검토 행은 실제 렌더링 필드의 정규화된 SHA-256을 저장한다. 카탈로그 문구가 바뀌어 해시가 달라지면 기존 승인을 재사용하지 않는다.
- `verified` 상태, 유효한 검토기한, `permitted` 승인 지식 문서, 활성 청크, 해당 문서의 `official_source_urls`에 등록된 URL을 모두 확인한 경우에만 공식 검증 완료로 취급한다.
- 검증 완료된 질문 유형에서는 공식 근거를 `verified_knowledge` 출처로 연결하고 `공식 문서 검증 전 초안` 한계만 제외한다. 미래 성과 비예측·대표기업 비추천 한계는 유지한다.

## 처리 흐름

1. 질문의 테마명·동의어 또는 `N번 테마`를 카탈로그에 매칭한다.
2. `OO 테마가 뭐야`, `OO 테마 알려줘` 같은 개요 요청이면 쉬운 정의, 무엇을 담는지, 한 줄 비유를 제공하고 `테마 대표기업`, `테마 장단점`, `테마 ETF상품` 후속 버튼을 표시한다. `테마 대표기업`은 `OO 테마 대표기업은 뭐야?` 질문으로 연결한다.
3. 개요 답변의 `테마 장단점` 후속 버튼은 `investment_considerations`로 연결하고, 해당 테마 ETF에 투자할 때의 이점 3개와 위험 3개를 쉬운 말로 함께 제공한다. 사용자가 직접 `고유 위험`을 질문하면 기존 위험 전용 응답을 유지한다.
4. `OO 테마 대표 기업` 요청이면 카탈로그의 대표기업 3곳을 제공한다. 각 기업은 회사명을 굵게 표시하고, `테마에서의 역할` 문단에 기존 역할과 대표 사례 선정 이유를 합친 뒤 `쉽게 말하면` 문단을 분리한다. 두 문단의 라벨은 굵게 표시하며 `대표 사례로 보는 이유` 라벨은 별도로 노출하지 않는다.
5. `OO 테마에 투자할 때 고려할 점` 요청이면 투자할 때의 이점 3개와 주의할 위험 3개를 함께 제공한다.
6. `성과에 영향을 주는 요인` 요청은 `performance_drivers`, `고유 위험` 요청은 `risks`로 분리한다. 성과 관찰요인은 독립된 3개 항목으로 표시하고 각 요인이 해당 산업의 주문·매출·비용·가동률 등에 연결되어 평가 기준이 되는 이유를 함께 설명한다.
7. 선택된 질문 유형의 카탈로그 payload 해시로 DB 검증 장부를 조회한다. 검증이 완료됐으면 공식 근거를 연결하고, 그렇지 않으면 초안 한계를 유지한다.
8. `ETF 대표 종목`, `구성종목`, `편입 비중` 요청은 대표기업 설명보다 우선해 KIS 구성종목 흐름으로 보낸다. 대표기업 예시와 실제 ETF 편입종목을 혼동하지 않는다.
9. ETF 후보 요청이면 완료된 설문과 계좌 유형을 요구한다.
10. 계좌별 적격 유니버스에서 테마를 다대다 분류하고, 성향별 목표 슬리브가 0보다 큰 상품만 남긴다.
11. 계좌 적격성과 투자성향 범위를 통과하고 거래대금·총보수가 모두 확인되는 후보를 일별 거래대금 중앙값 내림차순으로 정렬한다. 거래대금이 같으면 총보수 오름차순, 순자산 내림차순, 종목코드 오름차순으로 동률을 해소한다. 과거 수익률은 순위에 넣지 않는다.
12. 구성종목 후속 요청이면 직전 상품 응답에 저장한 정확한 ETF 종목코드(최대 3개)만 내부 조회키로 사용해 구성종목 전용 테이블의 최신 KIS 스냅샷 TOP3를 출처·수집시각·숫자 근거와 함께 반환한다. 화면에는 ETF별 `구성종목·구성비중` 2열만 표시하고 종목코드와 별도 수치 카드는 노출하지 않는다. 세 ETF 섹션은 기본으로 모두 펼치며 모바일 화면 폭에서 좌우 스크롤 없이 표시한다. 후보를 다시 선정하거나 이전 상품 카드를 다시 표시하지 않는다.
13. `테마 ETF상품` 응답은 최대 3개 후보를 세로형 상품 설명으로 표시한다. 총보수는 소수점 둘째 자리, 일별 거래대금 중앙값은 억원 정수 단위로 반올림해 표시하고 원본 수치는 계좌별 ETF 실데이터 마스터 근거에 연결한다. 상품 특징은 승인 설명·통합 원문·기초지수·KIS 구성종목을 근거로 한 한두 문장으로 표시하며, LLM 검증 실패 시에도 같은 검증 데이터의 결정론 문장을 사용한다.
14. 상품 요청 응답에는 `OO 테마란?` 개요 섹션과 중복 숫자 카드·가로 비교표를 포함하지 않는다. 개요는 개요 질문에서만 제공한다.

### 공통 표시 규칙

- 모든 `etf_theme` 답변은 문단형 항목 사이에 공통 `10pt` 간격을 사용한다. 섹션 소개와 첫 답변 블록, 이점·위험·관찰요인 목록의 각 항목, 대표기업의 두 설명 문단, 대표기업·ETF상품 설명 카드, 복수의 확인 문단에 같은 값을 적용한다.
- 목록 제목과 첫 항목 사이에도 `10pt`를 적용한다. 후속 질문 버튼과 표의 행은 문단형 항목 간격의 적용 대상에서 제외한다.
- 간격을 만들기 위해 카탈로그 문장이나 배열 항목에 임의의 줄바꿈을 추가하지 않는다. 각 의미 단위는 기존 `AnswerBlock`과 목록 항목 구조를 유지하고 프런트 표시 계층에서 간격을 적용한다.

## 가드레일

- 안정형·안정추구형처럼 전술 슬리브 목표가 없는 성향에는 테마 ETF 후보를 제안하지 않는다.
- 질문 계좌가 설문 프로필의 계좌에 없으면 그 계좌 상품을 제안하지 않는다.
- DC형·IRP·연금저축의 적격 유니버스를 섞지 않는다.
- KIS 공개 시세 데이터만으로 연금계좌 적격성을 판단하지 않는다.
- 구성종목 배열이 비어 있으면 비중을 생성하거나 추정하지 않고 한계를 표시한다.
- 대표기업 3곳은 테마를 이해하기 위한 사례이며, 특정 ETF의 실제 편입종목이나 매수 추천으로 표현하지 않는다.
- 동일 ETF가 여러 테마에 속할 수 있다. 테마 일치 자체는 매수 추천이나 미래 성과 근거가 아니다.
- 답변에 표시한 모든 `%`와 `원` 값은 해당 섹션의 `NumericEvidence`와 `SourceEvidence`에 연결한다.

## 실패 시 동작

- 테마 카탈로그 없음: 테마 기능을 `unavailable`로 응답한다.
- 설문 없음: 테마 설명만 제공하고 후보는 제시하지 않는다.
- 계좌별 적격 유니버스 없음: 해당 계좌 후보를 생략하고 한계를 표시한다.
- KIS 스냅샷 없음: 후보 설명은 가능하지만 해당 ETF의 구성종목 비중은 표시하지 않는다. 다른 ETF의 결과는 유지하고 누락 종목을 명시한다.
- 상품 설명 LLM 비활성·호출 실패·출력 검증 실패: 카드 형식과 수수료·거래대금 로직은 유지하고 승인 설명 또는 검증된 기초지수·구성종목 기반 문장을 표시한다.
- 검증 DB 미적용·연결 실패·검토기한 경과·해시 불일치·공식 URL 불일치: 테마 답변은 계속 제공하되 `공식 문서 검증 전 초안` 한계를 유지한다.
