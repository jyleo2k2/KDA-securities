## 0. 요약

### 0.1 한 줄 정의

**DC형·IRP·연금저축펀드의 서로 다른 운용 규칙과 전체 자산구성을 한곳에서 해석하고, 근거가 보이는 AI 설명과 규칙 기반 계산으로 이용자가 스스로 연금 운용 결정을 내리도록 돕는 증권사형 연금 가이드 서비스다.**

### 0.2 해결하려는 문제

연금계좌 보유자는 다음 문제를 동시에 겪는다.

- 계좌는 여러 개지만 DC형·IRP·연금저축펀드의 차이를 정확히 알기 어렵다.
- 상품은 많지만 내 투자성향과 은퇴 시점에 맞춰 무엇을 점검해야 하는지 판단하기 어렵다.
- 계좌별 화면만 보면 여러 계좌에 같은 위험자산이 반복된 중복·편중을 놓치기 쉽다.
- 세액공제, 납입한도, 위험자산 한도, 연금수령 과세가 서로 다른 개념인데 한 흐름에서 설명되지 않는다.
- 자동운용이나 상품 추천을 받더라도 “왜 이 선택인지” 이해하지 못하면 행동으로 이어지지 않는다.

### 0.3 제품의 해법

연금 코파일럿은 다음 흐름을 제공한다.

1. 실제 계좌 연동을 전제로 한 사용자 계좌 구조를 불러온다.
2. 투자성향 설문 결과와 은퇴까지의 기간을 확인한다.
3. 규칙 엔진이 계좌별 한도·적격성·자산구성·위험·세금·수령 계획을 계산한다.
4. 챗봇이 엔진 결과와 공식 출처를 쉬운 문장과 카드·그래프로 설명한다.
5. 이용자는 결과를 비교하고 공식 금융회사 채널에서 직접 선택·실행한다.

### 0.4 핵심 차별점

단순 통합조회, 계산기, 챗봇 중 하나가 아니라 다음 조합이 핵심이다.

> **세 계좌의 규칙 분리 × 계좌별·통합 포트폴리오 해석 × 설명 가능한 규칙 엔진 × 공식 데이터 출처 × 이용자 자기결정**

### 0.5 현재 상태

현재 `main`에는 다음 골든패스가 통합돼 있다.

- Supabase Auth 로그인과 세션 보호
- 계좌 연동 동의 및 투자성향 진단
- 사용자별 연금계좌 조회와 통합 자산 홈
- 규칙 엔진 기반 SSE 챗봇
- 계좌별 포트폴리오·리밸런싱 점검
- 과거 유사국면 ETF 성과 확인
- 연금계산기와 세액공제 계산
- 투자전략 10종 탐색·상세
- 대표 고객 포트폴리오 User Pick
- 저장 대화·팔로우·프로필·리밸런싱 알림
- Vercel·Render·Supabase 원격 배포

실제 MyData 금융사 연결, 주문, 자동 리밸런싱은 구현 범위가 아니다.

## 1. 추진 배경

### 1.1 왜 연금인가

[왜 연금인가](../20_리서치/왜_연금인가.md)와 [퇴직연금 2025 운용현황](../20_리서치/퇴직연금_2025_운용현황.md)에 정리된 핵심 문제는 “연금상품이 없어서”가 아니라 “관심은 있지만 운용 방법을 몰라 방치하는 이용자가 많다”는 점이다.

프로젝트가 확인한 대표 근거는 다음과 같다.

| 근거 | 확인 내용 | 제품 시사점 |
|---|---|---|
| 직장인 퇴직연금 인식조사 | 57.1%가 관심은 있지만 운용 방법을 잘 모른다고 응답 | 쉬운 설명과 다음 점검 행동이 필요 |
| 같은 조사 | 정보 비대칭 해소가 제도개선 요구 1순위 24.6% | 단순 상품 나열보다 근거 제공이 중요 |
| 퇴직연금 운용 현황 | 원리금보장형과 대기성 자금 비중이 높음 | 방치 상태를 계좌 단위로 찾아야 함 |
| 디폴트옵션 현황 | 안정형 쏠림이 큼 | 자동화만으로 이해 부족을 해결하기 어려움 |
| 연금저축·퇴직연금 성장 | 개인이 직접 운용하는 계좌와 ETF 활용이 확대 | 세 계좌를 함께 보는 도구의 필요성 증가 |

외부 수치는 발표나 사용자 화면에 사용할 때 원문 기준일과 모집단을 다시 확인한다. 전체 퇴직연금, DC형, IRP의 분모가 다르므로 서로 다른 통계를 같은 비율처럼 비교하지 않는다.

### 1.2 사용자 문제를 한 문장으로 정의

> “연금계좌는 가지고 있지만, 계좌마다 무엇이 다르고 현재 구성을 어떻게 점검해야 하는지 몰라 그대로 두고 있다.”

### 1.3 기존 대안의 빈틈

| 대안 | 강점 | 빈틈 |
|---|---|---|
| 증권사 MTS 연금 메뉴 | 실제 계좌·상품·주문과 연결 | 상품 탐색 중심이며 초보자가 규칙과 이유를 이해하기 어려움 |
| 은행·보험 연금 서비스 | 안정감과 기존 고객 기반 | 투자형 연금의 자산구성·위험 설명이 약함 |
| 통합연금포털·마이데이터 | 자산 통합조회 | 조회 이후 무엇을 점검할지 연결이 약함 |
| 로보어드바이저·디폴트옵션 | 편리한 자동배분 | 이용자에게 근거가 블랙박스로 느껴질 수 있음 |
| 범용 생성형 AI | 자유로운 질문 | 개인 계좌 규칙·수치 정확성·출처·재현성을 보장하기 어려움 |

연금 코파일럿은 기존 서비스를 대체하기보다, 조회와 실행 사이에서 “왜 그런지”를 설명하는 의사결정 레이어를 목표로 한다.

## 2. 목표 고객과 페르소나

### 2.1 핵심 고객

- DC형, IRP, 연금저축펀드 중 하나 이상을 보유한 직장인
- 연금 운용에는 관심이 있지만 상품·계좌 규칙을 잘 모르는 사람
- 여러 계좌의 전체 위험과 중복을 한 번에 보고 싶은 사람
- 자동매매보다 근거를 이해한 뒤 직접 결정하려는 사람
- 세액공제와 노후 준비를 함께 점검하려는 사람

### 2.2 비핵심 고객

- 단기 매매 종목이나 목표가를 원하는 이용자
- 수익 보장 또는 확정 미래수익률을 원하는 이용자
- 모든 판단과 주문을 시스템에 전권 위임하려는 이용자
- 연금이 아닌 일반 주식·가상자산 투자만을 목적으로 하는 이용자

### 2.3 핵심 고객 과업

사용자가 해결하려는 과업은 다음 다섯 가지다.

1. **파악**: 내 연금계좌와 전체 자산구성을 알고 싶다.
2. **이해**: 계좌마다 왜 다른 규칙이 적용되는지 알고 싶다.
3. **점검**: 현금 방치, 자산 편중, 계좌 간 중복을 확인하고 싶다.
4. **비교**: 내 성향과 기간에 맞는 전략·수령 계획·세금 결과를 비교하고 싶다.
5. **결정**: 근거를 확인한 뒤 내가 다음에 할 일을 스스로 정하고 싶다.

### 2.4 대표 시나리오 고객

프로젝트는 기능과 회귀를 검증하기 위해 여섯 가지 대표 상황을 유지한다. 1~5번은 로그인 시연 후보이며, 수령 전환 고객은 데이터 검증용으로 유지한다.

| 고객 | 대표 상황 | 보유 계좌 | 투자성향 예시 | 핵심 점검 |
|---|---|---|---|---|
| 박준호 | DC 적립금 방치 | DC형 | 안정형 | 현금·원리금보장 편중과 낮은 운용 참여 |
| 이서연 | 세액공제 후 미운용 | IRP, 연금저축펀드 | 안정추구형 | 납입 후 현금 대기와 단계적 분산 |
| 최지훈 | 가족 지출 부담 | DC형, IRP, 연금저축펀드 | 위험중립형 | 성장·방어자산 균형과 납입 여력 |
| 정민재 | 계좌 간 중복 위험 | DC형, IRP, 연금저축펀드 | 적극투자형 | 같은 ETF·테마의 반복 보유 |
| 김하린 | 은퇴까지 긴 기간 | DC형, 연금저축펀드 | 공격투자형 | 높은 성장자산 비중과 계좌별 한도 차이 |
| 윤정희 | 연금수령 전환 | IRP, 연금저축펀드 | 안정형 | 적립에서 수령으로의 전환과 과세 |

투자성향은 사용자에게 고정된 속성이 아니다. 위 표는 시나리오 초기값이며, 실제 서비스에서는 설문 재진단 결과로 갱신될 수 있다.

## 3. 제품 비전과 가치제안

### 3.1 제품 비전

> 누구나 자신의 연금계좌가 어떻게 구성돼 있고 어떤 규칙이 적용되는지 설명할 수 있으며, 시장 변동이나 생애 변화가 생겼을 때 스스로 점검하고 결정할 수 있게 한다.

### 3.2 가치제안

| 고객 가치 | 제공 방식 |
|---|---|
| 여러 연금계좌를 한 번에 이해 | 계좌별 잔액·자산군과 통합 도넛 제공 |
| 계좌별 규칙을 혼동하지 않음 | DC형·IRP와 연금저축펀드 규칙을 엔진에서 분리 |
| 숫자를 신뢰할 수 있음 | 규칙 엔진 계산, Decimal 정밀도, 출처·기준일 연결 |
| 어려운 결과를 쉽게 이해 | 챗봇이 결론 우선 문장과 그래프로 설명 |
| 내 성향에 맞게 비교 | 저장된 최신 설문 결과와 손실감내도 사용 |
| 실제 보유 상태를 점검 | 사용자 계좌에 있는 계좌 유형과 ETF만 진단 |
| 미래를 단정하지 않음 | 과거 실적과 승인 가정을 분리하고 한계 표시 |
| 최종 결정권을 유지 | 주문·자동운용 없이 비교와 확인까지만 지원 |

### 3.3 브랜드 메시지

**“연금을 대신 굴려주는 서비스가 아니라, 내가 이해하고 굴릴 수 있게 설명해 주는 연금 코파일럿.”**

## 4. 사업 포지셔닝과 KPI

### 4.1 기본 포지셔닝

[사업모델·KPI 설계](./사업모델_KPI.md)의 기본 서사를 따른다.

- 1차 포지션: 키움 등 증권사 자사 앱 안의 연금 운용 가이드
- 확장 포지션: 규칙 엔진과 설명형 챗봇을 금융회사에 제공하는 화이트라벨
- 고객 과금보다 자사 연금 AUM 순증과 이탈 방어를 우선
- 프리미엄 기능과 그룹 연계는 보조 수익원

### 4.2 수익모델

| 층 | 모델 | 설명 |
|---|---|---|
| 1층 | 자사 연금 AUM | 무료 핵심 기능으로 연금계좌 유지·추가 납입·이전 유입을 지원 |
| 2층 | 프리미엄 구독 | 심화 시뮬레이션, 다계좌 분석, 알림·모니터링 등 판단 도구에 과금 |
| 3층 | 화이트라벨·그룹 연계 | 규칙 엔진·데이터·설명 모듈을 금융회사 서비스에 공급 |

특정 상품 판매량이나 거래 횟수를 제품 성공지표로 삼지 않는다. 이는 이용자 자기결정과 자문·정보형 경계를 훼손할 수 있다.

### 4.3 북극성 지표

**북극성: 이해→행동 전환율**

정의 예시는 다음과 같다.

> 계좌·전략·세금 설명을 확인한 활성 이용자 중 정해진 기간 안에 점검 완료, 시뮬레이션 저장, 추가 정보 확인, 공식 채널 이동 등 유효한 다음 행동을 한 비율

사업 최종 목표는 자사 연금 AUM 순증과 이탈 방어로 별도 관리한다.

### 4.4 KPI 체계

| 영역 | 핵심 지표 |
|---|---|
| 획득 | 가입자, 기존 자사고객 전환율, 채널별 유입 |
| 활성화 | 로그인→홈 도달률, 성향진단 완료율, 첫 가치까지 시간 |
| 이해 | 출처 열람률, 챗봇 답변 완료율, 재질의율, 설명 만족도 |
| 행동 | 리밸런싱 점검 완료율, 계산기 실행률, 전략 비교율, 공식 채널 이동 |
| 리텐션 | 월·분기 재방문율, 알림 유지율, 연말정산 시즌 재접속률 |
| 사업 | 연금 AUM 순증, 계좌 유지율, 이전 방어율, 납입 지속률 |
| 신뢰 | 수치 근거 커버리지, 규칙 위반 0건, 오답 신고율, 민원율 |

### 4.5 가드레일 지표

- 엔진과 답변 수치 불일치 0건
- 성향 밖 상품 제안 0건
- 계좌 규칙 위반 0건
- 출처 없는 법·세제 숫자 0건
- 미래수익 보장 표현 0건
- 개인화 매수·매도 지시 0건
- 개인정보 소유권·마스킹 위반 0건

## 5. 제품 범위와 골든패스

### 5.1 전체 사용자 흐름

```text
로그인
```

## 6. 기능 상세

### 6.1 인증과 온보딩

#### 사용자 목표

내 계정으로 안전하게 로그인하고, 보유 계좌와 투자성향을 서비스 전체에 연결한다.

#### 주요 동작

- Supabase Auth 세션을 확인한다.
- 만료 토큰은 보호 API 호출 전에 차단한다.
- 401 발생 시 토큰 갱신은 한 번만 시도한다.
- 계좌 연동 동의 화면에서 대상 계좌와 표시 목적을 설명한다.
- 투자정보 설문을 규칙 엔진에 전달해 5단계 성향을 산출한다.
- 유효한 저장 결과가 있으면 재로그인 시 복원한다.
- 사용자가 바뀌면 이전 사용자의 브라우저 상태를 지운다.

#### 수용 기준

- 다른 사용자의 계좌·대화·성향이 섞이지 않는다.
- 설문 점수는 프론트나 LLM이 재계산하지 않는다.
- 투자성향 결과에는 진단일과 유효기간이 있다.

### 6.2 내 연금자산 홈

#### 사용자 목표

앱을 열자마자 전체 연금자산과 가장 먼저 확인할 내용을 파악한다.

#### 주요 출력

- 총 연금자산
- 계좌별 잔액
- 전체 자산군 비중 도넛
- 계좌·보유 기준일
- 저장 투자성향
- 연금가이드, 계산기, 전략, User Pick 진입점
- 계좌가 없는 경우 안내 상태

#### 설계 원칙

- 계좌별 규칙 판정과 통합 합산을 분리한다.
- 통합 화면은 합계를 보여주되 연금저축에 DC·IRP 한도를 적용하지 않는다.
- 계좌 데이터가 없다고 0원 자산처럼 오인시키지 않는다.

### 6.3 연금가이드 챗봇

#### 사용자 목표

복잡한 연금·상품·전략·세금 결과를 자연어로 묻고 근거와 함께 이해한다.

#### 지원 질문

- DC형·IRP·연금저축펀드의 차이
- 위험자산 한도와 상품 적격성
- 세액공제·연금외수령
- 내 투자성향에 맞는 연금 전략
- 실제 보유 ETF 리밸런싱 점검
- ETF 테마·특징·분배금 재투자
- 시장 뉴스와 과거 뉴스이벤트 사후성과
- 과거 유사 거시국면과 ETF 실현 성과
- 투자 용어와 시작 방법
- 망설임·재확인 질문

#### 답변 파이프라인

```text
질문
→ 안전·의도 분류
→ 사용자 계좌·성향 문맥 확인
→ 규칙 엔진·공식 데이터·승인 지식 조회
→ 근거가 연결된 결정론 답변 생성
→ SSE로 우선 표시
→ 선택적 LLM 재서술
→ 숫자·위험 표현 재검증
→ 최종 응답과 근거 저장
```

#### LLM의 역할

- 계산하지 않는다.
- 엔진 결과를 임의로 바꾸지 않는다.
- 원문에 없는 숫자·추천·확정 표현을 만들지 않는다.
- 검증에 실패하면 결정론 답변으로 되돌아간다.
- pydantic-ai 모델 추상화를 사용해 지원되는 공급자 모델을 선택할 수 있다.

### 6.4 포트폴리오와 리밸런싱 점검

#### 사용자 목표

내가 실제로 보유한 계좌와 ETF가 목표 구성에서 얼마나 벗어났는지 알고 싶다.

#### 입력

- 현재 로그인 사용자의 계좌 유형
- 계좌별 ETF와 평가금액
- 최신 투자성향 설문 결과
- 현재 나이와 연금수령 시작 나이
- 손실감내도
- 신규 납입금

#### 출력

- 현재 자산군 비중과 목표 비중
- 가장 큰 이탈 자산군
- 점검이 필요한 자산군 수
- 계좌 규칙 적용 결과
- 신규 납입금 우선 보완 순서
- 정기 점검 주기와 허용 이탈폭
- 과거 위험·스트레스 결과
- 계좌별 포트폴리오 그래프
- 과거 유사국면 ETF 총수익률·최대낙폭

#### 핵심 정책

- 보유하지 않은 계좌 그래프는 만들지 않는다.
- 박준호는 DC형, 이서연은 IRP·연금저축펀드처럼 사용자별 실제 계좌 조합만 표시한다.
- DC형·IRP는 일반 위험자산 70% 한도를 적용한다.
- 연금저축펀드에는 같은 70% 총량한도를 적용하지 않는다.
- 위험자산 목표가 70% 이하라면 계좌별 수치가 같을 수 있으며 정상이다.
- 매도 수량이나 주문을 만들지 않는다.
- 신규 납입금으로 부족한 자산군을 먼저 보완하는 방식을 우선 안내한다.
- 과거 유사국면은 설명 근거일 뿐 리밸런싱 신호로 사용하지 않는다.

### 6.5 투자성향별 점검주기

점검주기는 미래 시장을 예측한 매매 주기가 아니다. 변동성이 큰 자산과 전술 비중이 높을수록 목표비중이 빠르게 달라질 수 있어 “확인 빈도”만 높이는 규칙이다.

| 투자성향 | 기본 점검주기 | 허용 이탈폭 | 쉬운 설명 |
|---|---:|---:|---|
| 안정형 | 12개월 | 5%p | 방어자산이 많아 연 1회 큰 변화만 확인 |
| 안정추구형 | 6개월 | 5%p | 주식·실물자산이 늘어 반기마다 점검 |
| 위험중립형 | 3개월 | 5%p | 성장·방어자산 균형을 분기마다 확인 |
| 적극투자형 | 2개월 | 3%p | 성장·전술자산 변동을 더 촘촘히 확인 |
| 공격투자형 | 1개월 | 3%p | 주식·전술 비중 변화가 커 매월 확인 |

점검주기가 도래했거나 이탈폭을 넘었다고 자동매매하지 않는다. 이용자가 화면에서 결과를 확인한 뒤 직접 판단한다.

### 6.6 연금계산기

#### 사용자 목표

현재 잔액과 납입 계획이 은퇴 시점의 적립금과 월수령액에 어떤 차이를 만드는지 비교한다.

#### 주요 입력

- 계좌별 현재 잔액
- 월 또는 연 납입액
- 현재 나이
- 납입 종료 나이
- 연금수령 시작 나이
- 수령 기간
- 승인 전략

#### 주요 출력

- 연차별 원금·수익·잔액 시계열
- 전략별 적립 결과 비교
- 세전·세후 예상 월수령액
- 연령별 연금소득세 가정
- 연 1,500만원 기준과 수령한도 안내
- 계산에 사용한 가정·비용·출처

계산 결과는 승인 가정을 적용한 시나리오이며 확정 미래자산이나 수익 보장이 아니다.

### 6.7 세액공제와 연금외수령

#### 세액공제

- 연금저축 공제 대상 인정액: 연 600만원 한도
- 연금저축과 퇴직연금계좌 합산 공제 대상 인정액: 연 900만원 한도
- 개인 납입 합산한도: 연 1,800만원
- 소득구간에 따라 지방소득세 포함 16.5% 또는 13.2% 효과 표시

납입한도, 세액공제 대상 한도, 예상 세액공제액, 실제 환급액은 서로 다른 개념으로 표시한다.

#### 연금외수령

- 사용자 입력과 명시된 가정만 사용한다.
- 과거 미공제 원금과 이연퇴직소득을 구분할 수 없으면 최대 기타소득 원천징수 추정과 한계를 표시한다.
- 복잡한 사유는 전문가 확인 대상으로 돌린다.

### 6.8 투자전략 탐색

#### 사용자 목표

전략 이름만 보는 것이 아니라 어떤 원리로 움직이고 어느 계좌에서 어떻게 고려할지 이해한다.

#### 현재 기능

- 전략 10종 카드 탐색
- 키보드·포인터 이동
- 선택 전략 복원
- 전략 작동 원리
- 계좌 적용 설명
- 전략 분류와 용어 설명
- 챗봇 답변에서 해당 전략 Pick 화면으로 이동

#### 후속 목표

- 현재 구성과 전략의 차이 비교
- 계좌 규칙 재검사
- 적용 후 구성 시뮬레이션
- 사용자 초안 저장

초안은 주문서가 아니며, 실제 매매·수량·가격을 생성하지 않는다.

### 6.9 User Pick

#### 사용자 목표

다른 대표 포트폴리오를 수익률 순위가 아니라 구성·위험·운용 이유 중심으로 참고한다.

#### 현재 기능

- 대표 고객 목록·상세
- 계좌·ETF·자산군 구성
- 과거 성과와 기준일
- 운용 이유와 위험 설명
- 팔로우 상태와 집계
- 상세에서 목록으로 돌아가기

#### 보호 원칙

- 정확한 실명·계좌번호·개인 잔액을 공개하지 않는다.
- 과거수익률을 미래 성과처럼 표현하지 않는다.
- 타 고객 포트폴리오를 자동 복사하지 않는다.
- 내 성향이나 계좌 규칙에 맞지 않으면 그대로 적용하지 않는다.

### 6.10 프로필과 대화 이력

- 사용자 이름·이메일
- 저장 투자성향과 유효기간
- 보유 계좌 범위와 기준일
- 팔로우한 User Pick
- 소유 대화 세션·메시지
- 소유 대화 삭제
- 로그아웃

모든 사용자 데이터는 인증 소유자 범위에서 조회한다.

## 7. 계좌·투자 규칙

### 7.1 계좌별 역할

| 구분 | DC형 | 개인형 IRP | 연금저축펀드 |
|---|---|---|---|
| 기본 목적 | 회사 퇴직급여의 개인 운용 | 퇴직급여 이전·개인 추가 납입 | 개인 노후자금 적립 |
| 일반 위험자산 총량 | 원칙적으로 70% 한도 | 원칙적으로 70% 한도 | 같은 70% 총량한도 없음 |
| 법정 예외 | 적격 TDF·디폴트옵션 등 별도 판정 | 적격 TDF·디폴트옵션 등 별도 판정 | 별도 상품 적격성 적용 |
| 중도인출·수령 | 법정 사유와 제도 제약 | 법정 사유와 제도 제약 | 계좌·세제 규칙 적용 |
| 엔진 처리 | 퇴직연금 규칙 | 퇴직연금 규칙 | 연금저축 전용 규칙 |

TDF의 실제 매수·매도 가능 여부는 계좌 유형만으로 단정하지 않고, 해당 금융회사의 취급 여부와 상품별 적격성을 함께 확인한다.

### 7.2 투자성향

투자성향은 설문 점수로 산출한다.

- 안정형
- 안정추구형
- 위험중립형
- 적극투자형
- 공격투자형

투자성향은 정적 사용자 속성이 아니다. 설문 재진단, 유효기간 만료, 사용자 상황 변화에 따라 새로운 결과를 저장한다. 챗봇과 엔진은 최신 유효 결과를 사용한다.

### 7.3 목표 자산배분

목표 자산배분은 다음 순서로 계산한다.

1. 투자성향별 기본 위험·현금 정책
2. 나이와 연금수령까지 남은 기간 보정
3. 계좌별 위험자산 한도·적격성 적용
4. 사용자 손실감내도에 맞춘 위험 축소
5. 코어주식·실물자산·전술자산·채권·현금의 합계 100% 조정

LLM과 프론트는 이 수치를 다시 계산하지 않는다.

### 7.4 ETF 후보 선정

후보 품질점수에는 다음 요소를 사용한다.

- 비용
- 유동성
- 순자산
- NAV 괴리
- 추적오차
- 이력 깊이
- 후보 간 상관관계와 지역 중복

과거 수익률은 ETF 순위를 높이는 점수로 사용하지 않는다.

### 7.5 위험과 스트레스

공통 일별 수익률 관측이 충분할 때 다음 과거 위험 통계를 계산한다.

- 연환산 변동성
- 하방위험
- 최대낙폭
- VaR 95%

정책 스트레스는 주식시장 급락, 금리·물가 충격, 복합 충격을 점검한다. 가장 큰 손실과 사용자 손실감내도를 비교하되, 과거 통계와 스트레스 결과를 미래 손실 예측으로 표현하지 않는다.

### 7.6 과거 유사국면

공식 거시지표를 표준화해 과거와 현재의 유사도를 계산하고, 계좌에 실제 보유한 ETF의 이후 과거 총수익률과 최대낙폭을 연결한다.

- 유사국면은 미래 예측이 아니다.
- 실제 ETF 가격·분배금 관측이 있는 경우만 표시한다.
- 관측이 없는 국면·ETF는 숨긴다.
- 2025년 7월, 2024년 7월처럼 성과 관측이 시작된 달을 명확히 표시한다.
- 배분·주문·리밸런싱 트리거로 사용하지 않는다.

## 8. AI·데이터·기술 설계

### 8.1 전체 구조

```text
[React + TypeScript + Vite PWA]
               │ REST / SSE
               ▼
[FastAPI 인증·오케스트레이션]
     ├─ 규칙 엔진
     ├─ PostgreSQL 구조화 조회
     ├─ RAG 하이브리드 검색
     ├─ 공식 외부 데이터
     └─ 선택적 LLM 설명
               │
               ▼
[Supabase PostgreSQL + pgvector + 검증 캐시]
```

의존 방향은 `frontend → FastAPI → engine/data`로 고정한다.

### 8.2 규칙 엔진

규칙 엔진은 다음 계산·판단의 단일 소스다.

1. 투자성향 분석
2. 계좌 규칙 검사
3. 계좌별 진단
4. 통합 집계
5. 연금계산기
6. 포트폴리오 예시·리밸런싱
7. 세액공제·연금외수령
8. ETF 적격성·위험·계획가정
9. 과거 유사국면

엔진은 DB·네트워크·LLM에 의존하지 않는 순수 Python 계산을 지향하며 `Decimal`과 명시적 반올림을 사용한다.

### 8.3 챗봇

- FastAPI가 인증·사용자 문맥·도구 호출을 조정한다.
- 질문은 결정론 규칙으로 먼저 분류한다.
- 계산 질문은 허용된 엔진 도구만 호출한다.
- 제도·용어 질문은 승인 RAG 근거를 사용한다.
- 뉴스·공시·ETF는 구조화 저장소나 명시적 외부 경로를 사용한다.
- LLM은 최종 문장 표현만 개선한다.

### 8.4 RAG

- 승인된 공식 문서만 지식 코퍼스에 포함한다.
- BGE-M3 1024차원 임베딩과 PostgreSQL 전문검색을 RRF로 결합한다.
- 임베딩이 없거나 실패하면 전문검색으로 폴백한다.
- 검토기한이 지난 문서는 런타임 검색에서 제외한다.
- 개인정보, 사용자 계좌, 대화 원문은 지식 임베딩에 넣지 않는다.

### 8.5 데이터 원천

| 데이터 | 주요 원천 | 용도 |
|---|---|---|
| 연금사업자 공시 | FSS 통합연금포털 | 사업자별 적립금·과거수익률·수수료 |
| ETF 시장·지수 | KRX | 상장·NAV·유동성·대표지수 위험 |
| ETF 수정주가·구성 | KIS | 과거 위험·상관관계·구성종목 |
| 분배금·분배락 | KIND | 총수익률 계산 |
| 펀드·ETF 기본정보 | 금융위원회·운용사 | 상품 식별·적격성·설명 |
| 공시·법령 | DART·법령 API | 상품·계좌 규칙 근거 |

원본, 정규화 결과, 기준일, 요청 파라미터, 출처 URL 또는 해시를 보존한다.

### 8.6 데이터 경계

- 시장·상품·제도 수치는 공식 데이터와 승인 근거를 사용한다.
- 사용자 계좌는 최종적으로 MyData 또는 자사 계좌 연결을 전제로 한다.
- 현재 시나리오 데이터는 실연동 시 흐를 계약을 검증하는 스캐폴딩이다.
- 개인 계좌 데이터는 RAG와 뉴스 데이터에 혼합하지 않는다.
- 모든 화면 수치에는 출처·기준일 또는 가정을 표시한다.
- 사용자 화면에 내부 구현 방식이나 데이터 준비 방식을 노출하지 않는다.

이후 병합된 기능은 각 PR의 로컬 검증 결과를 따르며, 전체 기준 수치는 다음 통합 재검증 때 갱신한다.

### 12.3 CI 운영 주의

2026-07-26 이후 GitHub Actions 무료 한도 소진으로 작업이 실행 전에 실패할 수 있다. 이 경우 코드 실패로 오인하지 않고 로컬 자동검증 훅과 수동 테스트 결과를 PR에 기록한다. 한도 초기화 또는 총괄의 상향 후 CI를 다시 정상 게이트로 사용한다.

## 15. 성공 기준

### 15.1 제품 수용 기준

- 사용자가 보유한 계좌만 화면과 챗봇 결과에 표시된다.
- DC형·IRP와 연금저축펀드 규칙이 섞이지 않는다.
- 투자성향 재진단 결과가 이후 전략에 반영된다.
- 포트폴리오·세금·수령 수치가 규칙 엔진과 일치한다.
- 모든 중요 수치에 출처·기준일 또는 가정이 연결된다.
- 과거성과와 미래 가정이 구분된다.
- 사용자가 계좌 차이와 현재 점검 이유를 설명할 수 있다.
- 실제 주문 없이 다음 확인 행동을 선택할 수 있다.

### 15.2 기술 수용 기준

- 동일 입력은 동일 엔진 결과를 만든다.
- 인증 사용자의 데이터 소유권이 격리된다.
- LLM 없이도 핵심 골든패스가 동작한다.
- 저장 응답 손상과 스트림 오류가 사용자에게 안전하게 전달된다.
- 원격 배포에서 로그인·홈·챗봇·계산기·전략·User Pick이 동작한다.
- 로컬 회귀·빌드와 데이터 계약 검증이 통과한다.

### 15.3 사업 수용 기준

- 사용자가 서비스 설명 후 의미 있는 다음 행동을 한다.
- 자사 연금계좌 유지·납입·이전 방어에 기여한다.
- 미래수익 보장이나 과도한 거래를 성과로 삼지 않는다.
- 신뢰·준법 가드레일 지표가 목표 범위 안에 있다.
