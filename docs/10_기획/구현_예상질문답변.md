# 연금 코파일럿 — 김태형 구현 예상 질문·답변

> 버전: v1.0
>
> 기준일: 2026-07-28
>
> 대상: 프로젝트 발표, 기술 면접, 심사 질의응답, 팀 인수인계
>
> 연계 문서: [프로젝트 최종기획서](./최종기획서.md)

이 문서는 김태형 담당 영역인 **연금 규칙 엔진, 계좌별 포트폴리오, 리밸런싱, 위험·스트레스, ETF 데이터, 과거 유사국면, 뉴스 이벤트 근거, 챗봇·화면 연결**을 중심으로 예상 질문과 답안을 정리한 실전용 문서다.

답변은 다음 원칙을 따른다.

1. 먼저 결론을 한 문장으로 말한다.
2. 제품 의도와 구현 방식을 구분해서 설명한다.
3. 숫자는 엔진·계약·테스트로 확인된 값만 말한다.
4. 구현하지 않은 기능을 구현했다고 과장하지 않는다.
5. 과거 데이터와 계획가정, 미래 예측을 명확히 구분한다.
6. 주문·자동 리밸런싱·일임 기능이 아니라 이용자의 판단을 돕는 정보·자문형 가이드라는 경계를 유지한다.

## 0. 발표 직전 암기용 핵심 답변

### 0.1 30초 자기 역할 소개

“저는 연금 코파일럿에서 **규칙 기반 연금 엔진과 ETF 데이터 통합을 중심으로 담당**했습니다. DC형·IRP·연금저축펀드의 서로 다른 규칙을 엔진에 분리하고, 설문 투자성향·나이·은퇴 시점·손실감내도를 입력으로 계좌별 목표 자산배분과 리밸런싱 점검 결과를 만들었습니다. 또 한투 수정주가, KIND 분배금, KRX 시장자료 등 공식 데이터를 결합해 위험·비용·과거 성과 근거를 만들고, 이 결과가 챗봇과 모바일 화면에서 이해하기 쉽게 보이도록 연결했습니다.”

### 0.2 가장 중요한 설계 원칙

“**계산과 판단은 결정론적 규칙 엔진이 하고, LLM은 그 결과를 설명만 하도록 분리**했습니다. 그래서 같은 입력에는 같은 숫자가 나오고, 모든 결과의 출처와 정책 버전을 추적할 수 있습니다.”

### 0.3 가장 어려웠던 문제

“세 계좌가 비슷해 보이지만 법적 운용 규칙이 다르고, 사용자는 계좌를 한 개 또는 여러 개 보유할 수 있다는 점이 가장 어려웠습니다. 이를 해결하기 위해 계좌 유형별 규칙을 입력 단계부터 분리하고, 로그인 사용자가 실제로 보유한 계좌 목록만 평가하도록 바꿨습니다.”

### 0.4 리밸런싱을 한 문장으로 설명

“현재 자산비중이 설문과 은퇴 조건으로 계산한 목표비중에서 얼마나 벗어났는지 확인하고, 가능하면 **매도보다 새 납입금으로 부족한 자산을 먼저 채우는 점검 가이드**입니다.”

### 0.5 과거 유사국면을 한 문장으로 설명

“현재와 거시지표가 비슷했던 과거 시점을 찾고 그 다음 달부터 ETF가 실제로 어떻게 움직였는지 보여주되, 이를 미래 예측이나 리밸런싱 신호로 사용하지 않습니다.”

### 0.6 현재 구현의 경계

“실제 금융사 계좌 연결과 주문 실행은 범위 밖입니다. 현재는 인증된 사용자의 계좌 시나리오를 바탕으로 계산·설명·시뮬레이션을 제공하고, 최종 매수·매도 판단과 실행은 이용자가 합니다.”

## 1. 프로젝트와 제품에 관한 질문

### Q1. 이 프로젝트를 한 문장으로 설명해 주세요.

**핵심 답변**

DC형·IRP·연금저축펀드의 계좌별 규칙과 전체 자산구성을 해석해, 사용자가 스스로 연금 운용 결정을 내리도록 돕는 증권사형 연금 가이드입니다.

**구체 답변**

연금계좌 사용자는 세금, 위험자산 한도, 상품 적격성, 투자성향, 은퇴 시점이라는 여러 조건을 동시에 이해해야 합니다. 기존 화면은 잔액이나 상품 목록을 보여주는 데 그치는 경우가 많습니다. 이 프로젝트는 로그인부터 계좌 확인, 설문, 홈 진단, 챗봇 질문, 전략 탐색, 리밸런싱 점검, 연금계산기까지 하나의 흐름으로 연결했습니다. 핵심은 AI가 임의로 숫자를 만드는 것이 아니라, 규칙 엔진이 만든 결과를 사용자가 이해할 수 있는 언어와 차트로 전달하는 것입니다.

**근거**

### Q2. 왜 연금계좌를 주제로 선택했나요?

**핵심 답변**

연금은 장기 의사결정이면서 계좌별 규칙이 복잡해, 설명 가능한 개인화 가이드의 가치가 큰 영역이기 때문입니다.

**구체 답변**

연금은 오랜 기간 반복 관리해야 하지만 사용자는 DC형·IRP·연금저축펀드의 차이를 혼동하기 쉽습니다. 단순히 수익률이 높은 상품을 찾는 문제가 아니라 세액공제, 납입, 위험자산 한도, 은퇴 시점, 손실감내도를 함께 봐야 합니다. 따라서 규칙 기반 계산과 대화형 설명을 결합하면 정보 비대칭을 줄이고 실제 행동으로 이어질 가능성이 높다고 판단했습니다.

### Q3. 기존 증권사 연금 서비스와 무엇이 다른가요?

**핵심 답변**

상품 나열보다 **사용자의 전체 계좌 구조와 현재 상태를 먼저 해석하고, 계산 근거까지 대화형으로 설명**하는 점이 다릅니다.

**구체 답변**

차별점은 세 가지입니다. 첫째, 계좌를 각각 분리해 보여주면서도 전체 관점에서 중복과 편중을 확인합니다. 둘째, 설문 투자성향과 은퇴 조건을 규칙 엔진에 연결해 목표비중과 점검 기준을 계산합니다. 셋째, 공식 데이터와 승인된 문서를 근거로 답변하고 출처 칩을 표시합니다. 사용자는 “무엇을 사야 하나”뿐 아니라 “왜 이 점검 결과가 나왔나”를 확인할 수 있습니다.

### Q4. 로보어드바이저와 같은 서비스인가요?

**핵심 답변**

아닙니다. 현재 범위는 자동 주문이나 일임이 아니라 정보·자문형 운용 가이드입니다.

**구체 답변**

로보어드바이저가 주문과 운용 실행까지 연결될 수 있는 것과 달리, 이 프로젝트는 규칙 엔진의 계산 결과, 과거 데이터, 계좌 제약을 설명합니다. 매수·매도 지시를 생성하지 않고 `sell_instruction_produced=False`를 유지하며, 리밸런싱도 새 납입금 활용 예시를 우선 제공합니다. 실계좌 연결이나 자동매매로 확장하려면 별도의 법률, 보안, 적합성, 비상정지 체계가 필요합니다.

**근거**

- [최종기획서 §11](./최종기획서.md#11-컴플라이언스)

### Q5. 실제 사용자는 어떤 흐름으로 서비스를 이용하나요?

**핵심 답변**

로그인 후 계좌를 확인하고 투자정보 설문을 완료한 뒤, 홈과 챗봇에서 계좌 진단·전략·리밸런싱·연금계산을 이용합니다.

**구체 답변**

골든패스는 `로그인 → 계좌 확인 → 투자정보 입력 → 성향 결과 → 홈 → 챗봇·전략·계산기 → 프로필`입니다. 챗봇에서 “내 연금계좌 리밸런싱 점검해줘”라고 물으면 저장된 설문과 보유 계좌를 불러와 계좌별 결과를 보여줍니다. 사용자는 필요하면 설문을 다시 수행해 투자성향을 갱신할 수 있습니다.

### Q6. 제품의 가장 중요한 성공 지표는 무엇인가요?

**핵심 답변**

단순 방문자 수보다 **연금 운용 점검을 완료하고 근거를 확인한 사용자 수**가 중요합니다.

**구체 답변**

북극성 지표는 월간 유효 연금 운용 점검 사용자로 볼 수 있습니다. 보조 지표로 리밸런싱 점검 완료율, 계산기 실행률, 전략 비교율, 출처 확인률, 재방문율을 봅니다. 반대로 출처 없는 수치 노출, 성향 밖 제안, 계좌 규칙 위반, 인증 소유권 오류는 가드레일 지표입니다.

## 2. 김태형 담당 범위와 기여에 관한 질문

### Q7. 프로젝트에서 정확히 어떤 역할을 맡았나요?

**핵심 답변**

연금 규칙 엔진 오너로서 계좌 규칙, 목표 자산배분, 위험·스트레스, 리밸런싱 정책을 담당했고, ETF 공식 데이터와 챗봇·화면 연결까지 구현했습니다.

**구체 답변**

담당 범위는 크게 네 축입니다.

1. DC형·IRP·연금저축펀드의 계좌 규칙과 투자성향별 자산배분 엔진
2. 손실감내도, 위험 통계, 스트레스 시나리오, 계획수익률, 리밸런싱 점검
3. ETF 가격·분배금·비용·적격성 데이터의 수집, 결합, 검증, 운영
4. 엔진 결과를 챗봇 카드와 프론트 화면에서 사용자 중심으로 표시하는 통합

공용 인증·DB·프론트 영역은 팀원과 계약을 맞춰 협업했고, 제 담당 정책이 다른 계층에서 중복 계산되지 않도록 엔진을 단일 기준으로 유지했습니다.

### Q8. 본인이 구현한 것 중 가장 핵심적인 기능은 무엇인가요?

**핵심 답변**

실제 보유 계좌별로 다른 규칙을 적용해 목표 자산배분과 리밸런싱 결과를 일관되게 만드는 엔진입니다.

**구체 답변**

처음에는 챗봇이 고정된 계좌 조합을 생성하는 문제가 있었습니다. 이를 설문 프로필의 `portfolio_account_types()`를 사용하도록 변경해 사용자가 가진 계좌만 평가하게 했습니다. 동시에 DC형·IRP에는 일반 위험자산 70% 한도를 적용하고 연금저축펀드에는 같은 법정 총량한도를 적용하지 않도록 계좌 규칙을 분리했습니다. 이 결과를 회귀 테스트로 다섯 사용자 조합에 대해 고정했습니다.

### Q9. 가장 어려웠던 기술적 문제는 무엇이었나요?

**핵심 답변**

법적 계좌 규칙, 개인 성향, 시장 데이터, 화면 표현을 섞지 않으면서 하나의 결과로 연결하는 일이 가장 어려웠습니다.

**구체 답변**

예를 들어 “위험중립형”이라는 같은 성향이라도 사용자의 나이, 은퇴 시작 나이, 손실감내도, 계좌 종류에 따라 결과가 달라질 수 있습니다. 반면 위험자산 목표가 70% 이하라면 DC형과 연금저축펀드의 그래프가 같을 수도 있습니다. 이 차이와 같음을 모두 정상 상태로 처리해야 했습니다. 해결 방법은 규칙을 엔진에 모으고, 챗봇은 결과를 설명하며, 프론트는 계좌별 결과를 그대로 표시하도록 경계를 나눈 것입니다.

### Q10. 본인의 구현이 팀 전체 구조에 어떤 영향을 줬나요?

**핵심 답변**

숫자와 정책의 단일 기준을 엔진에 고정해 챗봇·API·화면 간 수치 불일치를 줄였습니다.

**구체 답변**

계좌 한도, 리밸런싱 주기, 손실감내도 조정, 위험·스트레스 산식이 각각의 화면이나 챗봇 문구에 중복되면 정책 변경 시 표류합니다. 그래서 프론트와 챗봇은 엔진 응답을 표시만 하고 계산하지 않도록 했습니다. 결과 모델에는 엔진 이름, 버전, 출처, 경고를 포함해 재현성과 감사 가능성도 확보했습니다.

### Q11. 협업 중 충돌은 어떻게 관리했나요?

**핵심 답변**

작업마다 전용 브랜치·워크트리·파일 claim을 사용하고, 계약 변경과 구현 변경을 분리했습니다.

**구체 답변**

여러 명이 동시에 프론트, 챗봇, 엔진을 수정했기 때문에 공유 파일 충돌 위험이 컸습니다. `git-session-manager`로 작업 범위를 사전에 claim하고, 공용 연결 파일은 한 명이 통합하도록 했습니다. 엔진 결과 구조가 바뀌면 계약과 테스트를 먼저 정리한 뒤 백엔드와 프론트를 순서대로 연결했습니다.

### Q12. 구현하면서 일부 기능을 뺀 이유가 있나요?

**핵심 답변**

사용자의 첫 판단에 필요하지 않은 정보가 핵심 결과를 가려, 정보 우선순위에 따라 단계적으로 줄였습니다.

**구체 답변**

리밸런싱 화면에서 이탈폭, 납입 후 비중, 추가 납입 예시처럼 엔진에는 유용하지만 첫 화면에서 복잡도를 높이는 열을 제거했습니다. 긴 설명 카드는 줄이고, 계좌별 파이차트와 “무엇이 목표보다 많은가”를 먼저 보여줬습니다. 데이터는 엔진에 유지하되 화면 노출만 줄였기 때문에 정책 계산은 훼손하지 않았습니다.

## 3. 규칙 엔진과 계좌 정책에 관한 질문

### Q13. 왜 LLM이 아니라 규칙 엔진으로 계산했나요?

**핵심 답변**

연금의 세금·한도·비율은 같은 입력에 같은 결과가 나와야 하고 검증 가능해야 하기 때문입니다.

**구체 답변**

LLM은 자연어 설명에는 강하지만 정확한 숫자 계산과 정책 버전 관리에는 적합하지 않습니다. 엔진은 DB, 네트워크, LLM 의존성이 없는 순수 함수로 만들고 `Decimal`과 `ROUND_HALF_UP`을 사용했습니다. 테스트에서 입력과 기대 결과를 고정할 수 있고, 정책이 바뀌면 버전을 올려 영향 범위를 확인할 수 있습니다. LLM은 엔진 결과의 의미를 풀어 설명하는 역할만 합니다.

### Q14. 세 계좌의 핵심 차이는 무엇인가요?

**핵심 답변**

DC형과 IRP는 일반 위험자산 70% 한도를 계좌별로 적용하고, 연금저축펀드는 같은 총량한도를 적용하지 않습니다.

**구체 답변**

DC형과 IRP는 일반 위험자산 비중을 원칙적으로 적립금의 70%까지 운용할 수 있습니다. 적격 TDF나 디폴트옵션 같은 예외는 별도 적격성 규칙으로 다뤄야 합니다. 연금저축펀드는 동일한 일반 위험자산 총량 70% 규제를 적용하지 않고 상품 적격성을 별도로 판단합니다. 따라서 세 계좌를 하나의 한도 로직으로 계산하면 안 됩니다.

### Q15. 연금저축펀드에는 정말 아무 상한도 없나요?

**핵심 답변**

DC형·IRP와 같은 법정 일반 위험자산 70% 총량한도는 없지만, 엔진 포트폴리오 모델에는 과도한 집중을 막는 설계상 범위가 있습니다.

**구체 답변**

법적 계좌 한도와 모델의 포트폴리오 설계 범위를 구분해야 합니다. 엔진 내부에서 연금저축펀드 목표 위험비중은 모델의 최대 범위인 90% 안에서 계산되지만, 이를 법정 계좌 한도로 노출하지 않으며 `account_cap`은 `None`으로 반환합니다. 즉 “연금저축도 법적으로 90% 제한”이라는 뜻이 아니라, 현재 전략 모델이 현금·방어자산을 최소한 남기도록 만든 상한입니다.

**근거**

- [목표 자산배분 계산](../../backend/app/engine/educational_portfolio.py)

### Q16. 투자성향은 사용자에게 고정된 값인가요?

**핵심 답변**

아닙니다. 저장되는 현재 설문 결과이며, 사용자가 설문을 다시 하면 갱신될 수 있습니다.

**구체 답변**

사용자에게 영구적인 “공격형” 꼬리표를 붙이지 않습니다. 성향 결과에는 확인 시점과 유효기간이 있고, 챗봇과 화면은 현재 저장된 설문 결과를 사용합니다. 설문을 다시 완료하면 이후 포트폴리오와 리밸런싱 점검도 새 결과를 기준으로 계산됩니다. 그래서 화면 문구도 “고정 성향”이 아니라 “현재 투자성향 설문 결과”라고 표현합니다.

### Q17. 투자성향별 기본 위험비중은 어떻게 정했나요?

**핵심 답변**

다섯 성향의 위험 수준이 단계적으로 증가하도록 기본값과 최소·최대 범위를 정책 테이블로 관리합니다.

**구체 답변**

현재 엔진의 기본 위험비중은 안정형 20%, 안정추구형 35%, 위험중립형 50%, 적극투자형 65%, 공격투자형 85%입니다. 각각 최소·최대 범위를 두고, 나이와 은퇴 시점 보정 후 범위 안으로 제한합니다. 이는 특정 상품 수익률을 예측한 값이 아니라 성향별 자산배분 정책의 출발점입니다.

| 성향 | 기본 위험비중 | 최소 | 최대 | 전술자산 기준 | 현금 기준 |
|---|---:|---:|---:|---:|---:|
| 안정형 | 20% | 5% | 30% | 0% | 15% |
| 안정추구형 | 35% | 15% | 45% | 0% | 10% |
| 위험중립형 | 50% | 25% | 60% | 5% | 7% |
| 적극투자형 | 65% | 35% | 75% | 10% | 5% |
| 공격투자형 | 85% | 45% | 90% | 15% | 3% |

### Q18. 나이와 은퇴 시점은 자산배분에 어떻게 반영되나요?

**핵심 답변**

나이가 어리거나 은퇴 시작이 늦을수록 운용기간이 길다고 보고 정책 범위 안에서 위험비중을 높입니다.

**구체 답변**

현재 보정식은 다음과 같습니다.

```text
나이·은퇴 보정 = (35 - 현재 나이) × 0.75
               + (은퇴 시작 나이 - 55) × 0.75

원시 위험비중 = 성향 기본 위험비중 + 나이·은퇴 보정
```

계산값은 성향별 최소·최대 범위로 제한한 뒤 계좌 한도와 손실감내도를 적용합니다. 이 식은 장기 운용 가능 기간을 반영하는 정책식이지 기대수익률 예측식이 아닙니다.

### Q19. 손실감내도는 어떻게 반영하나요?

**핵심 답변**

현재 자산배분의 스트레스 손실이 사용자의 감내 수준을 넘으면 위험비중을 이분탐색으로 낮춥니다.

**구체 답변**

먼저 위험비중을 다섯 슬리브로 배분하고 주식, 실물, 전술, 채권에 정책 충격률을 적용해 스트레스 손실을 계산합니다. 손실이 사용자의 감내율 이하이면 그대로 사용합니다. 초과하면 32회 이분탐색으로 허용 가능한 가장 높은 위험비중을 찾습니다. 마지막 미세 초과는 채권 일부를 현금으로 이동해 맞춥니다. 그래서 투자성향이 공격형이어도 손실감내도가 낮으면 최종 위험비중이 내려갈 수 있습니다.

### Q20. 왜 이분탐색을 사용했나요?

**핵심 답변**

허용 가능한 최대 위험비중을 빠르고 결정론적으로 찾을 수 있기 때문입니다.

**구체 답변**

위험비중이 높아질수록 정책 스트레스 손실도 대체로 증가하는 구조입니다. 0부터 현재 위험비중 사이를 절반씩 줄이면 반복 횟수가 고정되고 결과를 재현하기 쉽습니다. 복잡한 최적화 라이브러리를 도입하지 않아도 충분한 정밀도를 확보하며, 실패 원인과 계산 과정을 테스트하기도 쉽습니다.

### Q21. 자산을 왜 다섯 슬리브로 나눴나요?

**핵심 답변**

상품명이 아니라 포트폴리오에서 맡는 역할로 묶어 사용자가 구조를 이해하도록 하기 위해서입니다.

**구체 답변**

다섯 슬리브는 핵심 주식, 실물자산, 전술자산, 채권, 현금입니다. 같은 주식형 ETF라도 광범위 시장 ETF는 핵심 주식, 섹터·테마 ETF는 전술자산으로 역할이 다릅니다. 역할 기준으로 묶으면 목표비중, 현재 편중, 스트레스 충격, 추가 납입 우선순위를 일관되게 설명할 수 있습니다.

### Q22. 위험 통계는 어떤 방식으로 계산하나요?

**핵심 답변**

공통 관측 기간의 일별 총수익률로 변동성, 하방편차, 최대낙폭, 하위 분위 손실을 계산합니다.

**구체 답변**

ETF별 가격 기간을 맞추고 포트폴리오 가중 일별 수익률을 만듭니다. 최소 공통 관측일 조건을 충족할 때 연율화 변동성, 연율화 하방편차, 최대낙폭, 일간 5% 분위 손실, 최악 일간 손실을 계산합니다. 이 값은 과거 위험 측정치이며 미래 손실 예측값으로 사용하지 않습니다.

### Q23. 스트레스 시나리오는 무엇인가요?

**핵심 답변**

주식 급락, 금리·물가 충격, 국내시장 충격의 세 정책 시나리오로 포트폴리오 손실을 점검합니다.

**구체 답변**

각 시나리오에서 슬리브별 충격률을 곱해 가중 손실을 계산합니다. 예를 들어 주식 급락 시 핵심 주식 -35%, 실물자산 -25%, 전술자산 -45%, 채권 -8%, 현금 0%를 적용합니다. 이는 미래 확률을 예측하는 모델이 아니라, 동일한 정책 충격으로 포트폴리오 간 민감도를 비교하는 도구입니다.

### Q24. 계획수익률은 과거 수익률 평균인가요?

**핵심 답변**

아닙니다. 장기 자산군 가정과 비용을 결합한 계획용 범위이며, 미래 수익 보장값이 아닙니다.

**구체 답변**

과거 ETF 수익률을 그대로 미래에 외삽하지 않습니다. 장기 자산군별 가정, 포트폴리오 비중, 검증된 비용을 결합해 계획수익률 범위를 산출합니다. 과거 가격은 위험 측정과 데이터 품질 확인에 사용하고, 계획수익률과 과거 실적은 화면에서도 구분합니다. 보수, 거래비용, 추적 관련 값 중 실제로 계획식에 포함된 항목과 진단용 항목도 분리합니다.

### Q25. 현금성 80%, 단일 자산군 50% 진단 기준은 무엇인가요?

**핵심 답변**

현금 방치와 비현금 자산군 편중을 사용자가 빠르게 인지하도록 만든 승인된 진단 임계값입니다.

**구체 답변**

현금성 자산이 80% 이상이면 장기 연금 운용에서 미투자 상태를 점검하도록 표시하고, 비현금 단일 자산군이 50% 이상이면 집중 위험을 확인하도록 표시합니다. 이 값은 강제 매도선이나 법정 기준이 아니라 진단 정책입니다. 2026-07-23 엔진 오너와 총괄 승인을 거쳐 수식과 골든 테스트로 고정했습니다.

## 4. 리밸런싱 정책과 구현에 관한 질문

### Q26. 리밸런싱 점검은 정확히 무엇을 계산하나요?

**핵심 답변**

현재 슬리브별 비중과 목표비중의 차이를 계산하고, 새 납입 후 허용 이탈 범위 안으로 들어오는지 확인합니다.

**구체 답변**

보유 ETF를 핵심 주식, 실물, 전술, 채권, 현금으로 분류한 뒤 현재 금액과 비중을 계산합니다. 목표 금액은 `현재 총액 + 새 납입금`에 목표비중을 곱해 구합니다. 부족한 슬리브에 납입금을 비례 배분한 후 예상 비중과 목표비중의 차이를 계산합니다. 최종 상태는 허용 범위 이내, 납입 후에도 부족, 과다 비중 검토로 나눕니다.

### Q27. 이탈폭 계산식을 설명해 주세요.

**핵심 답변**

이탈폭은 현재 또는 납입 후 비중에서 목표비중을 뺀 퍼센트포인트 값입니다.

**구체 답변**

```text
현재 비중 = 현재 슬리브 금액 / 현재 총액 × 100
납입 후 비중 = (현재 금액 + 해당 슬리브 납입액)
             / (현재 총액 + 새 납입금) × 100
이탈폭 = 실제 비중 - 목표비중
```

양수면 목표보다 많고 음수면 부족합니다. 다만 화면에서는 사용자의 첫 판단을 단순하게 하기 위해 모든 중간 열을 항상 노출하지 않고, 핵심 현재·목표 비교와 우선 설명을 보여줍니다.

### Q28. 왜 매도보다 추가 납입을 우선하나요?

**핵심 답변**

불필요한 거래를 줄이고 사용자가 실행하기 쉬운 방식으로 목표비중에 접근하기 위해서입니다.

**구체 답변**

연금계좌는 장기 납입이 반복되므로 부족한 자산을 새 납입으로 채우는 방식이 자연스럽습니다. 엔진은 슬리브별 목표 금액과 현재 금액의 차이를 구해 새 납입금을 부족액 비율로 나눕니다. 남는 금액은 현금에 둡니다. 매도 지시를 생성하지 않고 과다 비중은 `review_only`로 표시합니다.

### Q29. 투자성향별 점검 주기는 어떻게 정했나요?

**핵심 답변**

변동성과 전술자산 비중이 높을수록 더 자주 점검하되, 점검을 자동매매와 분리했습니다.

**구체 답변**

| 투자성향 | 정기 점검 | 허용 이탈폭 | 설계 이유 |
|---|---:|---:|---|
| 안정형 | 12개월 | 5%p | 방어자산 비중이 높아 큰 이탈을 연 1회 확인 |
| 안정추구형 | 6개월 | 5%p | 주식·실물자산 비중 증가를 반기마다 확인 |
| 위험중립형 | 3개월 | 5%p | 성장·방어자산 균형을 분기마다 확인 |
| 적극투자형 | 2개월 | 3%p | 성장·전술자산 변동을 더 촘촘히 확인 |
| 공격투자형 | 1개월 | 3%p | 전술자산·주식 변동이 커 매월 확인 |

주기는 매매 빈도가 아니라 사용자가 계좌를 열어보는 권장 간격입니다. 실제 조정은 이탈폭과 납입 계획을 함께 봅니다.

### Q30. 점검 주기의 학술적 근거가 있나요?

**핵심 답변**

특정 논문이 “공격형은 정확히 매월”이라고 규정한 값은 아니며, 변동성·전술비중·거래비용의 균형을 반영한 제품 정책입니다.

**구체 답변**

리밸런싱에는 달력 기준과 이탈 기준을 함께 쓰는 방식이 일반적입니다. 너무 자주 조정하면 거래비용과 추격매매 가능성이 커지고, 너무 늦으면 목표 위험에서 오래 벗어날 수 있습니다. 이 프로젝트는 변동성이 낮은 성향은 6~12개월, 높은 성향은 1~3개월로 점검 간격을 줄이고, 실제 행동은 5%p 또는 3%p 이탈 기준을 추가로 충족할 때 검토하도록 했습니다. 따라서 수치는 법규가 아니라 버전 관리되는 정책값이며 실서비스에서는 사용자 행동 데이터로 재검증해야 합니다.

### Q31. 왜 안정형 5%p, 공격형 3%p인가요?

**핵심 답변**

위험자산과 전술자산의 변동이 큰 성향일수록 목표 위험에서 빠르게 멀어질 수 있어 허용 범위를 좁혔습니다.

**구체 답변**

안정형은 방어·현금 비중이 커 단기 가격변동이 전체 포트폴리오에 미치는 영향이 상대적으로 작습니다. 적극·공격형은 주식과 전술자산 비중이 커 같은 시장 움직임에도 비중 이탈이 빨리 커집니다. 다만 3%p와 5%p 역시 거래 지시선이 아니라 점검 우선순위를 정하는 정책값입니다.

### Q32. 정기 점검일이 오면 무조건 리밸런싱하나요?

**핵심 답변**

아닙니다. 점검일에는 상태를 확인하고, 이탈 기준·납입금·미분류 자산을 함께 검토합니다.

**구체 답변**

정기 주기는 알림과 확인 시점입니다. 허용 이탈폭 안에 있으면 유지할 수 있고, 밖에 있어도 새 납입으로 조정 가능한지 먼저 봅니다. 과다 비중이 남아도 엔진은 매도를 지시하지 않습니다. 사용자는 상품 적격성, 거래비용, 시장 상황을 추가로 확인해 최종 판단합니다.

### Q33. 보유 상품을 분류하지 못하면 어떻게 하나요?

**핵심 답변**

추측해서 배분하지 않고 미분류 금액을 별도로 표시해 추가 확인을 요청합니다.

**구체 답변**

우선 ETF 상품 분류를 사용하고, 없으면 계좌 스냅샷의 명확한 자산군을 제한적으로 슬리브에 매핑합니다. 혼합형 TDF처럼 역할이 모호하면 임의 추정하지 않습니다. 미분류 금액이 있으면 결과 상태를 `partial_unclassified_holdings`로 바꾸고 경고를 제공합니다.

### Q34. 로그인 사용자가 가진 계좌만 보여주는 방식은 어떻게 구현했나요?

**핵심 답변**

설문 프로필의 계좌 목록을 단일 계좌 값으로 대체하지 않고 `portfolio_account_types()`로 순회합니다.

**구체 답변**

`CompletedSurveyProfile`은 대표 `account_type`과 전체 `account_types`를 가집니다. `portfolio_account_types()`는 전체 목록이 있으면 그 목록을, 이전 데이터처럼 목록이 없으면 대표 계좌 하나를 반환해 하위 호환성을 유지합니다. 챗 서비스는 반환된 계좌마다 엔진 요청을 만들고 결과 카드를 생성합니다. 보유하지 않은 계좌는 요청 자체를 만들지 않습니다.

### Q35. 사용자별 계좌 조합은 어떻게 검증했나요?

**핵심 답변**

다섯 대표 사용자의 기대 계좌 조합을 회귀 테스트로 고정했습니다.

**구체 답변**

| 사용자 | 기대 표시 계좌 |
|---|---|
| 박준호 | DC형 |
| 이서연 | IRP, 연금저축펀드 |
| 정민재 | DC형, IRP, 연금저축펀드 |
| 김하린 | DC형, 연금저축펀드 |
| 최지훈 | DC형, IRP, 연금저축펀드 |

테스트는 평가 결과의 계좌 순서와 집합, 계좌별 위험 한도 설명, 연금저축펀드 별도 설명을 확인합니다. 이 테스트 덕분에 고정된 DC형+연금저축 조합으로 되돌아가는 회귀를 막습니다.

### Q36. 계좌별 그래프 수치가 같으면 버그 아닌가요?

**핵심 답변**

반드시 버그는 아닙니다. 위험자산 목표가 70% 이하라면 DC형·IRP 한도가 실제로 작동하지 않아 같은 결과가 나올 수 있습니다.

**구체 답변**

계좌 차이는 한도가 결과에 결합될 때 드러납니다. 예를 들어 위험중립형의 최종 위험목표가 50%라면 DC형·IRP의 70% 한도 아래이므로 연금저축펀드와 목표배분이 같을 수 있습니다. 핵심 수용 기준은 억지로 다른 숫자를 만드는 것이 아니라 보유하지 않은 계좌를 숨기고, 한도가 결합될 때 올바르게 제한하는 것입니다.

### Q37. 리밸런싱 화면에서 무엇을 가장 먼저 보여주나요?

**핵심 답변**

계좌별 파이차트와 현재 상태의 핵심 문제를 먼저 보여주고, 긴 설명과 세부 열은 뒤로 보냅니다.

**구체 답변**

초기 화면은 긴 설명 카드와 표가 차트를 밀어내 사용자가 결과를 늦게 보게 했습니다. 이를 계좌 제목, 핵심 한 줄 진단, 파이차트, 현재·목표 비교 순으로 재배치했습니다. 표에서는 이탈폭, 납입 후, 추가 납입 예시 열을 제거해 모바일 가로 스크롤을 줄였습니다. 계산 데이터는 엔진에 남아 있어 향후 상세보기로 다시 제공할 수 있습니다.

### Q38. 왜 리밸런싱 화면에서 정보를 계속 줄였나요?

**핵심 답변**

정확한 정보가 많아도 사용자가 핵심 행동을 찾지 못하면 좋은 의사결정 지원이 아니기 때문입니다.

**구체 답변**

사용자 테스트 관점에서 첫 화면의 질문은 “지금 무엇이 목표보다 많은가”와 “내 계좌별 목표는 무엇인가”입니다. 계획수익률, 손실감내도 상세, 현재 보유 계획가정, 추가 납입 예시는 중요하지만 같은 위계로 놓으면 인지부하가 커집니다. 그래서 결론 우선, 시각화 우선, 세부 근거 후순위 원칙으로 화면을 정리했습니다.

## 5. ETF 데이터와 비용·분배금에 관한 질문

### Q39. ETF 데이터는 어디에서 가져오나요?

**핵심 답변**

KRX, 한국투자증권, KIND, 금융감독원, 금융투자협회 등 공식·검증 가능한 원천을 역할별로 사용합니다.

**구체 답변**

- KRX: 상장 ETF, 시장 스냅샷, 거래량·거래대금
- 한국투자증권: 수정주가 기반 가격 이력
- KIND: 확정 분배금과 분배 관련 공시
- 금융투자협회·운용사 공시: 비용 진단
- 금융감독원·금융위원회·법령: 계좌 제도와 규칙 근거

각 데이터는 원본과 정규화 결과, 요청 조건, 기준일, 출처 URL 또는 해시를 보존해 재현할 수 있게 했습니다.

### Q40. 왜 수정주가와 분배금을 함께 사용하나요?

**핵심 답변**

가격 변화만 보면 분배금 지급으로 생긴 수익을 놓칠 수 있어 투자자의 실제 총수익을 더 가깝게 측정하기 위해서입니다.

**구체 답변**

분배금 이벤트가 있는 구간의 일별 총수익 계수는 다음 구조를 사용합니다.

```text
일별 총수익 계수 = (당일 종가 + 당일 적용 분배금) / 직전 관측 종가
```

이 계수를 기간 동안 연결해 총수익률을 계산합니다. 분배금 기준일과 가격 이벤트를 정확히 연결하고, 데이터가 없는 경우 임의로 채우지 않습니다.

**근거**

- [ETF 총수익률·비용 마스터 계약](../30_스펙/ETF_총수익률_비용_마스터_계약.md)

### Q41. 수정주가에 이미 분배금이 반영됐다면 이중 계산 아닌가요?

**핵심 답변**

데이터 정의를 먼저 확인하고, 가격계열과 현금분배 이벤트의 역할을 계약으로 고정해 이중 반영을 방지합니다.

**구체 답변**

“수정주가”라는 이름만 보고 자동으로 분배금이 완전히 재투자됐다고 가정하지 않습니다. 공급 원천의 필드 정의와 이벤트 연결 규칙을 검증하고, 총수익률 빌더에서 어떤 가격과 현금흐름을 결합했는지 출처 라벨로 남깁니다. 중복 이벤트는 이벤트 키와 기준일로 제거하며 결과 수치의 입력 이력을 재현할 수 있게 합니다.

### Q42. ETF 비용은 수익률에 어떻게 반영하나요?

**핵심 답변**

검증된 비용만 계획식에 포함하고, 확인되지 않은 비용은 진단값으로 분리해 임의 차감하지 않습니다.

**구체 답변**

총보수처럼 정의와 기준일이 명확한 항목과, 매매·중개수수료나 추적 관련 진단값을 구분합니다. 같은 비용을 기준가와 계획수익률 양쪽에서 이중 차감하지 않습니다. 데이터가 없으면 0으로 단정하지 않고 “미확인”으로 처리하며 계획가정 표시를 제한할 수 있습니다.

### Q43. ETF 후보는 어떤 기준으로 선정하나요?

**핵심 답변**

계좌 적격성과 슬리브 역할을 먼저 통과한 뒤 데이터 품질, 거래 가능성, 비용, 중복도를 기준으로 비교합니다.

**구체 답변**

먼저 해당 계좌에서 운용 가능한 ETF인지 확인하고, 상품 분류를 목표 슬리브와 맞춥니다. 그 다음 가격 이력의 충분성, 비용, 거래대금, 품질점수, 이미 선택된 후보와의 상관 중복을 봅니다. 테마 후보에서는 일별 거래대금 중앙값을 우선하고 동률이면 총보수가 낮은 순서를 사용합니다. 최종 후보는 사용자의 성향 밖 상품을 강제로 제안하지 않습니다.

### Q44. ETF끼리 비슷한 상품이 여러 개면 어떻게 하나요?

**핵심 답변**

이름이 아니라 수익률 상관과 분류 역할을 비교해 중복이 큰 후보의 우선순위를 낮춥니다.

**구체 답변**

동일 슬리브 후보 간 공통 가격 기간의 상관을 계산하고, 이미 선택한 ETF와 최대 상관이 높은 후보를 피하도록 합니다. 다만 데이터가 부족하면 상관을 억지로 만들지 않고 미측정으로 둡니다. 사용자가 화면에서 “한곳에 몰림”을 이해할 수 있도록 섹터 분산 파이차트와 중복 설명도 제공합니다.

### Q45. 분배금 데이터 갱신은 어떻게 운영하나요?

**핵심 답변**

공식 공시 원본을 보관하고 증분 수집·정규화·버전 적재·품질검사를 거쳐 서비스 데이터로 승격합니다.

**구체 답변**

수집기는 KIND의 확정 현금분배 공시와 관련 일정을 가져와 원본을 비공개 저장소에 보관합니다. 이벤트 키는 정규화된 내용의 해시로 만들어 재실행해도 중복 적재되지 않게 합니다. 이후 기준일, 지급예정일, 주당 분배금, 출처를 검증하고 이벤트 버전과 서비스용 행을 갱신합니다. 원본 저장소는 정책을 만들지 않는 deny-by-default 구조이고 보존주기도 별도로 관리합니다.

**근거**

- [ETF 분배금 정기갱신 운영설계](../30_스펙/ETF_분배금_정기갱신_운영설계.md)
- [ETF 종목 이벤트 마스터 계약](../30_스펙/ETF_종목_이벤트_마스터_계약.md)

### Q46. 수집 도중 일부 데이터가 실패하면 어떻게 하나요?

**핵심 답변**

부분 성공을 완전 성공으로 표시하지 않고, 기존 정상 버전을 유지한 채 실패 원인과 건수를 기록합니다.

**구체 답변**

네트워크 오류, 빈 응답, 스키마 변화, 비정상 감소를 구분합니다. 품질 게이트를 통과하지 못하면 최신 서비스 버전을 덮어쓰지 않습니다. 원본과 실행 기록이 남아 재처리할 수 있고, 데이터 감사 스크립트로 DB와 캐시의 건수·키·기준일을 비교합니다.

### Q47. 데이터가 오래되면 사용자에게 잘못된 결과를 주지 않나요?

**핵심 답변**

모든 결과에 기준일과 출처를 표시하고, 신선도 조건을 통과하지 못한 데이터는 제한하거나 경고합니다.

**구체 답변**

시장·분배금·비용 데이터는 갱신 주기가 다릅니다. 그래서 각 데이터셋에 기준일과 버전을 두고 서비스 응답의 출처 칩에 연결합니다. 데이터가 없거나 오래됐을 때 임의 추정값으로 채우지 않고, 위험·리밸런싱 계산은 가능한 범위에서 유지하되 해당 계획가정이나 일정 표시만 제외합니다.

## 6. 과거 유사국면과 뉴스 이벤트에 관한 질문

### Q48. 과거 유사국면은 어떻게 찾나요?

**핵심 답변**

한국·미국의 금리, 물가, 장기금리, 기대인플레이션을 월별 확장 표준화한 뒤 현재와의 거리를 계산합니다.

**구체 답변**

사용 지표는 한국 기준금리, 한국 소비자물가 상승률, 미국 연방기금금리, 미국 소비자물가 상승률, 미국 10년 국채금리, 미국 10년 기대인플레이션입니다. 각 시점까지의 데이터만 사용해 확장 윈도우 z-score를 만들고, 동일 가중 RMS 거리로 현재와 과거를 비교합니다. 최소 36개월의 선행 이력이 있어야 하고, 최근 12개월은 제외하며, 선택된 시점끼리는 최소 12개월 떨어지게 합니다.

**근거**

- [거시 유사국면 엔진](../../backend/app/engine/macro_regime.py)
- [거시 유사국면 결과 엔진](../../backend/app/engine/macro_regime_outcomes.py)

### Q49. 왜 2025년 7월과 2024년 7월 데이터가 나오나요?

**핵심 답변**

유사국면 자체는 2025년 6월과 2024년 6월이고, 성과는 다음 달 첫 거래일부터 측정해 7월 기준으로 표시되기 때문입니다.

**구체 답변**

현재 스냅샷의 유사 시점 상위 결과에 2025년 6월과 2024년 6월이 포함됩니다. 같은 달의 가격을 사용하면 유사국면 판정에 사용된 정보와 성과 구간이 겹칠 수 있습니다. 그래서 국면이 끝난 다음 달 첫 거래일부터 실제 ETF 총수익률과 최대낙폭을 계산합니다. 화면의 2025년 7월, 2024년 7월은 이 성과 측정 시작 시점을 의미합니다.

### Q50. 미래 정보가 과거 유사국면 계산에 섞이지 않나요?

**핵심 답변**

각 과거 시점까지 이용 가능했던 데이터만으로 표준화하고 성과 구간을 다음 달부터 분리해 미래 정보 누수를 줄였습니다.

**구체 답변**

전체 기간 평균과 표준편차로 과거를 다시 표준화하면 미래 값이 과거 점수에 영향을 줍니다. 이를 막기 위해 expanding-window 방식으로 해당 월까지의 데이터만 사용합니다. 또한 최근 12개월을 유사국면 후보에서 제외하고, 성과는 판정 다음 달부터 측정합니다. 그래도 과거 유사성은 일부 지표만 반영하므로 모든 시장 위험을 설명할 수 없다는 한계를 명시합니다.

### Q51. 과거 유사국면 성과를 리밸런싱에 사용하나요?

**핵심 답변**

사용하지 않습니다. 사용자 설명을 위한 참고 근거이며 배분, 계획수익률, 주문, 리밸런싱 트리거와 분리했습니다.

**구체 답변**

거시 유사국면 스냅샷에는 `planning_return_input=False`, `allocation_weight_input=False`, `rebalancing_trigger_input=False`가 명시됩니다. 프론트에도 “미래 예측이나 자동 리밸런싱 신호가 아니다”라는 한계를 표시합니다. 데이터가 없어도 기본 리밸런싱 결과는 그대로 제공하고 유사국면 카드만 숨깁니다.

### Q52. 과거 성과에 어떤 지표를 보여주나요?

**핵심 답변**

관측 가능한 경우 기간 총수익률과 최대낙폭을 보여줍니다.

**구체 답변**

사용자가 보유한 ETF의 가격과 분배금 이력이 성과 시작일 이후 충분히 존재할 때 총수익률과 구간 최대낙폭을 계산합니다. 수익률만 보여주면 경로 중 위험을 숨길 수 있어 최대낙폭을 함께 제공합니다. 데이터가 부족한 ETF는 0으로 만들지 않고 미표시합니다.

### Q53. 뉴스 이벤트 성과 장부는 왜 만들었나요?

**핵심 답변**

뉴스를 단순 요약하는 데서 끝내지 않고, 과거 유사 이벤트 이후 실제 시장 반응을 검증 가능한 형태로 설명하기 위해서입니다.

**구체 답변**

FOMC, 한국은행 기준금리 변경 등 사건을 구조화하고 기준 시점 이후 ETF 또는 시장의 관측 성과를 장부에 저장합니다. 뉴스 카드가 사건 유형을 분류하면 해당 유형의 과거 근거를 연결할 수 있습니다. 다만 사건 장부도 배분이나 주문 입력으로 사용하지 않고, 참고 설명과 학습에만 사용합니다.

### Q54. FOMC와 한국은행 이벤트를 어떻게 검증했나요?

**핵심 답변**

공식 발표일과 정책 변경 내용을 기준 원장으로 만들고, 가격 이력의 시작일·결측·중복을 감사했습니다.

**구체 답변**

이벤트마다 고유 키, 사건일, 정책 방향, 출처를 기록합니다. 같은 사건이 중복되지 않는지, 성과 구간 시작일이 사건 이후인지, 필요한 가격 이력이 존재하는지 테스트합니다. 원격 적재 후에는 로컬 원장과 DB 건수, 키, 기준일을 비교합니다.

### Q55. 뉴스가 시장을 움직였다고 인과관계를 주장하는 것 아닌가요?

**핵심 답변**

아닙니다. 사건 이후 함께 관측된 결과를 보여줄 뿐 단일 뉴스의 인과효과라고 주장하지 않습니다.

**구체 답변**

시장 가격은 같은 시점의 여러 정보에 영향을 받습니다. 따라서 “이 뉴스 때문에 수익률이 올랐다”가 아니라 “유사한 정책 이벤트 이후 이런 결과가 관측됐다”고 표현합니다. 통제집단이나 사건연구가 없는 단순 사후 관측이라는 한계를 명시하고 미래 방향 예측에 사용하지 않습니다.

## 7. 챗봇과 RAG에 관한 질문

### Q56. 챗봇은 질문을 어떻게 처리하나요?

**핵심 답변**

질문 의도를 결정론적으로 분류하고, 필요한 엔진·DB·RAG 도구를 호출한 뒤 구조화된 응답을 스트리밍합니다.

**구체 답변**

세금, 계좌 규칙, 포트폴리오, 뉴스, 분배금, 용어 설명 같은 인텐트를 분류합니다. 계산 질문은 엔진으로, 제도 설명은 승인 RAG로, 사용자 데이터는 소유권이 확인된 저장소로 보냅니다. 응답은 텍스트, 섹션, 출처, 카드, 시각화, 후속 질문 구조를 가지며 SSE로 전달됩니다. 마지막에 공통 가드와 표현 규칙을 한 번 적용합니다.

### Q57. RAG는 어떤 구조인가요?

**핵심 답변**

BGE-M3 벡터 검색과 PostgreSQL 전문검색 후보를 RRF로 결합하고, 승인된 공식 문서만 답변 근거로 사용합니다.

**구체 답변**

문서는 manifest에서 출처, 해시, 검토일, 만료일을 검증한 뒤 헤딩 단위로 청킹합니다. 각 청크는 BGE-M3 1024차원 임베딩과 전문검색 인덱스를 가집니다. 질의 시 두 검색의 순위를 `RRF(k=60)`으로 융합하고 재랭킹합니다. 사용자가 볼 답변에는 실제 사용한 출처를 연결합니다.

**근거**

- [검색 저장소](../../backend/app/retrieval/repository.py)
- [코드베이스 지도 §3](../30_스펙/코드베이스_지도.md#3-rag-backendappretrieval-backendappchatknowledgepy)

### Q58. 벡터 검색이 실패하면 챗봇도 멈추나요?

**핵심 답변**

아닙니다. 임베딩 모델이 없거나 호출에 실패하면 전문검색 경로로 안전하게 폴백합니다.

**구체 답변**

하이브리드 검색을 기본으로 사용하지만, 임베더 초기화나 쿼리 임베딩이 실패해도 PostgreSQL 전문검색 결과를 유지합니다. 폴백 출처는 별도 네임스페이스로 구분해 원격 청크 식별자와 섞이지 않게 했습니다. 품질은 다소 낮아질 수 있지만 서비스 전체가 중단되는 것보다 승인 문서의 전문검색 결과를 제공하는 편이 낫다고 판단했습니다.

### Q59. RAG가 있어도 환각이 생길 수 있지 않나요?

**핵심 답변**

가능성을 0으로 만들 수는 없지만, 계산 분리·승인 문서 제한·출처 연결·금지 표현 검사로 위험을 줄였습니다.

**구체 답변**

수치는 엔진에서 만들고 LLM에 계산 권한을 주지 않습니다. RAG는 공식 출처와 검토된 문서만 활성화하고, 만료된 문서는 런타임에서 제외합니다. 답변에 사용한 근거를 저장하고, 악성 또는 민감정보 유도 발췌는 답변 전에 차단합니다. 제도 숫자와 사용자 수치는 테스트에서 별도로 검증합니다.

### Q60. 개인 계좌 데이터를 RAG에 넣나요?

**핵심 답변**

넣지 않습니다. 개인 계좌 데이터와 지식 문서·뉴스 데이터는 저장과 검색 경계를 분리합니다.

**구체 답변**

RAG는 법령, 공식 제도 문서, 검증된 리서치 같은 공통 지식을 검색합니다. 사용자의 계좌, 설문, 대화 이력은 인증과 소유권이 적용되는 별도 저장소에서 요청 시점에만 가져옵니다. 개인 데이터를 임베딩 코퍼스에 섞지 않아 다른 사용자의 검색 결과로 노출될 가능성을 차단합니다.

### Q61. 왜 SSE 스트리밍을 사용했나요?

**핵심 답변**

엔진 결과를 빠르게 먼저 보여주고, 긴 설명을 기다리는 체감시간을 줄이기 위해서입니다.

**구체 답변**

챗봇 응답은 엔진·DB·RAG·내레이션 단계가 있어 한 번에 기다리면 지연이 크게 느껴집니다. SSE는 검증된 기본 답변과 카드 구조를 먼저 보내고, 필요한 경우 내레이션 업데이트를 이어서 전달합니다. 저장 실패나 스트림 오류도 무음으로 끊지 않고 명시적인 오류 이벤트로 보냅니다.

### Q62. LLM 모델이 바뀌면 결과가 달라지지 않나요?

**핵심 답변**

설명 문장은 달라질 수 있지만 핵심 수치와 정책 판정은 엔진에서 고정되므로 달라지지 않습니다.

**구체 답변**

내레이터는 여러 공급자 모델을 교체할 수 있게 구성돼 있습니다. 그러나 입력으로 받는 엔진 결과, 출처, 제한사항은 동일합니다. 모델 변경 시 말투와 요약 품질을 검증하되 목표비중, 세금, 한도, 리밸런싱 상태는 회귀 테스트로 고정합니다.

## 8. 프론트엔드와 사용자 경험에 관한 질문

### Q63. 엔진 담당인데 왜 프론트 화면도 수정했나요?

**핵심 답변**

좋은 계산도 사용자가 핵심을 찾지 못하면 가치가 없기 때문에, 엔진 계약을 훼손하지 않는 범위에서 결과 표현을 함께 개선했습니다.

**구체 답변**

계좌 이름, 목표비중, 섹터 분산, 계획수익률, 과거 유사국면이 화면에서 중복되거나 너무 늦게 보이는 문제가 있었습니다. 엔진 숫자는 그대로 두고 프론트의 우선순위, 라벨, 표 열, 카드 배치를 조정했습니다. 계산과 표현의 경계를 지키기 위해 프론트에서 새 비율을 만들지 않고 API 응답을 그대로 사용했습니다.

### Q64. 파이차트를 앞으로 배치한 이유는 무엇인가요?

**핵심 답변**

사용자가 설명을 읽기 전에 계좌별 구성 차이를 한눈에 비교하도록 하기 위해서입니다.

**구체 답변**

기존에는 “한곳에 너무 몰렸는지 보기”라는 긴 설명과 표 뒤에 차트가 있어 핵심 시각 정보가 화면 아래로 밀렸습니다. 리밸런싱 질문의 첫 답은 계좌별 구성과 편중이므로 파이차트를 상단으로 올리고 설명을 축약했습니다. 모바일 화면에서 첫 스크롤 안에 결론과 차트가 보이는 것을 목표로 했습니다.

### Q65. 표에서 이탈폭·납입 후·추가 납입 예시를 삭제한 이유는 무엇인가요?

**핵심 답변**

모바일에서 표가 가로로 길어지고 비슷한 숫자가 많아, 현재와 목표라는 핵심 비교를 방해했기 때문입니다.

**구체 답변**

세 열은 엔진 검증과 상세 분석에는 유용하지만 첫 화면에서는 사용자가 숫자 관계를 해석해야 했습니다. 현재·목표 열만 남기면 “어디가 많고 부족한가”가 바로 보이고 가로 스크롤도 사라집니다. 삭제는 화면 표시만 대상으로 했으며 엔진 응답의 이탈과 납입 예시는 유지했습니다.

### Q66. 과거 유사국면 카드가 데이터 없을 때 빈칸으로 나오지 않나요?

**핵심 답변**

실제 관측 가능한 결과가 없으면 카드 자체를 숨기고 기본 리밸런싱 답변만 보여줍니다.

**구체 답변**

0%나 임의 문구로 채우면 사용자가 실제 관측 결과로 오해할 수 있습니다. 그래서 보유 ETF, 유사국면, 가격·분배금 기간이 모두 연결될 때만 표시합니다. 데이터 로딩 실패와 “정상적으로 결과 없음”도 구분해 처리합니다.

### Q67. 접근성은 어떻게 고려했나요?

**핵심 답변**

차트만으로 정보를 전달하지 않고 텍스트·표·라벨을 함께 제공하며, 키보드와 스크린리더용 의미 구조를 유지했습니다.

**구체 답변**

도넛과 파이차트에는 범례, 비율, 계좌 제목을 함께 표시합니다. 카드와 섹션은 의미 있는 제목과 `aria-label`을 사용하고, 색상만으로 상태를 구분하지 않습니다. 모바일 터치 영역, 줄바꿈, 가로 스크롤, 로딩 스켈레톤의 레이아웃 이동도 테스트했습니다.

## 9. 인증·보안·데이터 소유권에 관한 질문

### Q68. 다른 사용자의 계좌가 보일 가능성은 없나요?

**핵심 답변**

API 인증, 저장소 소유권 조건, Supabase RLS를 중첩 적용하고 두 사용자 격리 E2E로 검증했습니다.

**구체 답변**

브라우저가 보낸 사용자 식별자를 그대로 신뢰하지 않고 액세스 토큰에서 인증 주체를 확인합니다. 쿼리는 소유자 ID로 제한하고 DB에도 RLS를 적용합니다. 사용자 전환 시 브라우저 상태와 진행 중 요청을 정리해 이전 사용자의 응답이 늦게 도착해 섞이는 경합도 막았습니다.

### Q69. API 키가 프론트에 노출되지 않나요?

**핵심 답변**

브라우저에 필요한 공개 키만 `VITE_` 환경변수로 사용하고, 서비스롤·외부 데이터·LLM 비밀키는 서버에만 둡니다.

**구체 답변**

루트 `.env`를 단일 환경 설정으로 사용하지만 Vite는 `VITE_` 접두사만 번들에 노출합니다. DB 서비스롤 키, LLM 키, 수집기 인증값은 백엔드 환경변수로만 읽습니다. 로그와 오류 메시지에도 비밀값을 출력하지 않습니다.

### Q70. 대화 저장 중 재시도가 발생하면 중복되지 않나요?

**핵심 답변**

요청 식별자와 idempotency 계약으로 같은 요청의 중복 저장을 막습니다.

**구체 답변**

스트리밍 연결은 네트워크 상황에 따라 재시도될 수 있습니다. 서버는 사용자의 요청 키와 소유권을 확인하고 이미 완료된 요청이면 같은 결과를 재생합니다. 대화와 근거 저장도 사용자 소유 세션에 한정합니다.

## 10. 테스트·품질·운영에 관한 질문

### Q71. 본인 구현은 어떻게 검증했나요?

**핵심 답변**

순수 엔진 단위 테스트, API·챗봇 계약 테스트, 프론트 컴포넌트 테스트, 원격 DB·인증 E2E를 계층별로 수행했습니다.

**구체 답변**

엔진에서는 `Decimal` 계산, 계좌 한도, 손실감내도 결합, 스트레스, 후보 선정, 리밸런싱을 테스트했습니다. 챗봇에서는 실제 계좌 범위, 문구, 출처, 시각화 구조를 검증했습니다. 프론트에서는 계좌명, 표 열, 차트, 유사국면 표시 조건을 확인했습니다. 공식 데이터는 원본 건수·해시·DB 동등성을 비교하고, 인증은 두 사용자 소유권 격리 E2E를 수행했습니다.

### Q72. 전체 프로젝트 테스트 규모는 어느 정도인가요?

**핵심 답변**

2026-07-27 기록 기준 백엔드 1,553개 통과, 프론트 186개 통과, FastAPI 라우트 47개이며 원격 골든패스 E2E를 완료했습니다.

**구체 답변**

해당 수치는 특정 기능 하나의 테스트가 아니라 당시 `main` 통합 기준입니다. 이후 변경은 각 PR의 관련 테스트와 빌드 결과를 추가로 기록합니다. 발표 시에는 “현재 코드 전체의 최신 절대값”이라고 과장하지 않고 기준일을 함께 말해야 합니다.

**근거**

- [최종기획서 §12.2](./최종기획서.md#122-기록된-검증-기준)
- [기술 아키텍처 §9](../30_스펙/아키텍처.md#9-구현검증-상태)

### Q73. 계좌별 리밸런싱 회귀 테스트는 무엇을 확인하나요?

**핵심 답변**

사용자별 실제 계좌만 생성되는지, 계좌 이름과 위험 한도 설명이 올바른지 확인합니다.

**구체 답변**

박준호는 DC형 하나, 이서연은 IRP와 연금저축펀드, 정민재와 최지훈은 세 계좌, 김하린은 DC형과 연금저축펀드만 나오는지 검증합니다. DC형·IRP에는 일반 위험자산 한도 설명이 있고, 연금저축펀드에는 같은 한도를 적용하지 않는 설명이 있는지도 확인합니다.

### Q74. 데이터 파이프라인 테스트는 어떻게 하나요?

**핵심 답변**

고정된 원본 입력으로 정규화 결과와 이벤트 키를 검증하고, 재실행·결측·중복·부분실패 시나리오를 테스트합니다.

**구체 답변**

수집기 테스트는 외부 API를 직접 호출하는 대신 기록된 응답과 경계 사례를 사용합니다. 동일 입력을 여러 번 넣어도 중복이 생기지 않는지, 지급일 변경 시 새 버전이 만들어지는지, 빈 응답이 기존 정상 데이터를 덮지 않는지 확인합니다. 원격 통합은 별도 opt-in E2E로 실행합니다.

### Q75. CI가 실패한 PR은 어떻게 검증했나요?

**핵심 답변**

현재 일부 CI 실패는 코드 실행 전 GitHub Actions 결제·한도 문제이며, 로컬 훅과 수동 검증 결과를 PR에 남겼습니다.

**구체 답변**

백엔드·프론트·라우트 동기화 작업이 모두 0개 단계로 즉시 실패하고 “recent account payments have failed or spending limit needs to be increased”가 표시되는 경우는 코드 실패가 아닙니다. 그렇더라도 성공으로 간주하지 않고 Ruff, pytest, Vitest, production build, 링크·문서 검증을 로컬에서 실행해 결과를 기록합니다. 한도 복구 후 CI를 다시 돌리는 것이 최종 운영 절차입니다.

### Q76. 같은 입력에 같은 결과가 나온다는 것을 어떻게 보장하나요?

**핵심 답변**

엔진을 순수 함수로 만들고 Decimal, 정렬 규칙, 동률 규칙, 정책 버전을 고정했습니다.

**구체 답변**

네트워크나 LLM을 엔진에서 호출하지 않으며, 후보 정렬은 거래대금·비용·코드 같은 명시적 동률 기준을 사용합니다. 부동소수점 오차가 정책 경계를 바꾸지 않도록 금액과 비율은 `Decimal`로 처리합니다. 동일 fixture의 결과를 골든 테스트로 비교하고, 정책 변경 시 엔진 버전과 기대 결과를 함께 갱신합니다.

## 11. 날카로운 반론과 방어 질문

### Q77. 결국 추천 상품을 보여주는데 투자자문 아닌가요?

**핵심 답변**

현재는 계좌 규칙과 투자성향 범위 안의 정보·자문형 콘텐츠를 제공하지만, 실제 서비스화 전에는 금융소비자보호·투자자문 규제를 별도로 검토해야 합니다.

**구체 답변**

상품 후보와 자산배분을 보여주더라도 미래 수익을 보장하지 않고 주문을 실행하지 않으며, 근거·기준일·한계를 표시합니다. 하지만 개인화 수준, 표현, 제휴 수익 구조가 달라지면 규제 판단도 달라질 수 있습니다. 따라서 외부 베타 전 광고심의, 적합성·적정성, 이해상충, 개인정보, 투자자문 해당 여부를 법무·준법 부서가 승인해야 합니다.

### Q78. 공격형 사용자에게 위험자산을 많이 보여주는 것이 위험하지 않나요?

**핵심 답변**

성향만 보지 않고 계좌 한도, 나이·은퇴 시점, 손실감내도, 스트레스 결과를 순서대로 적용해 위험을 낮출 수 있습니다.

**구체 답변**

공격형 기본 위험비중은 높지만 최종값은 그대로 확정되지 않습니다. 나이·은퇴 보정 후 정책 범위, DC·IRP 70% 한도, 손실감내도 결합을 차례로 적용합니다. 사용자의 손실감내도가 낮으면 이분탐색으로 위험비중을 낮추고, 최악 스트레스가 감내 수준을 넘는지도 별도로 표시합니다.

### Q79. TDF는 DC형·IRP에서 70% 한도 예외가 될 수 있는데 반영했나요?

**핵심 답변**

일반 위험자산 70% 한도와 적격 TDF·디폴트옵션의 법정 예외를 같은 규칙으로 단순화하지 않고 상품 적격성에서 별도 처리하도록 설계했습니다.

**구체 답변**

TDF라고 이름에 적혀 있다고 자동 예외로 인정하면 안 됩니다. 감독규정상 요건과 상품 분류가 확인된 적격 상품인지 검증해야 합니다. 현재 포트폴리오의 일반 위험자산 한도와 ETF 계좌 적격성은 분리돼 있으며, 실제 매수 가능 여부는 판매사 상품목록과 최신 법령을 마지막으로 확인해야 합니다.

### Q80. 연금계좌에서 TDF를 매수·매도할 수 있나요?

**핵심 답변**

계좌와 판매사에서 취급하는 적격 TDF라면 일반적으로 매수·매도가 가능하지만, 상품별 적격성·거래 가능 시간·환매 조건을 확인해야 합니다.

**구체 답변**

DC형·IRP는 퇴직연금 감독규정과 사업자 상품목록을, 연금저축펀드는 판매사 취급 여부를 확인해야 합니다. TDF가 ETF인지 공모펀드인지에 따라 거래 방식과 결제·환매 기간도 다릅니다. 이 서비스는 가능 여부와 원리를 설명하지만 실제 주문을 대신 실행하지 않습니다.

### Q81. 과거 유사국면에서 수익이 좋았던 ETF를 사면 되는 것 아닌가요?

**핵심 답변**

아닙니다. 유사한 거시지표라도 당시 시장 가격, 기업실적, 정책 기대가 달라 같은 결과가 반복된다는 보장이 없습니다.

**구체 답변**

유사국면은 여섯 거시지표의 거리만 비교합니다. 밸류에이션, 지정학, 수급, 상품 구조 같은 모든 위험을 포함하지 않습니다. 성과 카드의 목적은 “과거에는 이런 경로도 있었다”는 참고이지 다음 수익률의 예측이 아닙니다. 그래서 엔진 계약에서도 배분과 리밸런싱 입력을 명시적으로 `False`로 둡니다.

### Q82. 계획수익률 숫자가 있으면 사용자는 예측으로 오해하지 않나요?

**핵심 답변**

그 위험이 있어 “장기 계획가정”과 범위로 표현하고 과거 실적·예측·보장값이 아니라는 문구와 출처를 함께 표시합니다.

**구체 답변**

단일 숫자만 크게 보여주지 않고 가정 기준일, 포함 비용, 사용 기간, 범위를 제공합니다. 계획수익률은 연금 적립 시나리오를 비교하기 위한 입력이지 상품 선정 순위나 미래 성과 약속이 아닙니다. 사용자 문구에서도 “예상 수익”보다 “장기 계획수익률”을 사용합니다.

### Q83. 법이나 세제 기준이 바뀌면 하드코딩된 값이 틀리지 않나요?

**핵심 답변**

정책값을 엔진 버전과 출처로 관리하고 공식 법령 검증·회귀 테스트를 통해 변경 영향을 추적합니다.

**구체 답변**

70% 한도, 세액공제, 과세율 같은 값은 화면 문구 여러 곳에 복사하지 않습니다. 정책 모듈과 계약에서 단일 관리하고, 법령 수집기는 핵심 원문 표현의 변경 여부를 확인합니다. 변경이 확인되면 근거 문서, 정책 버전, 엔진 테스트, 챗봇 문구를 한 변경 단위로 갱신합니다.

### Q84. 사용자가 설문에 거짓으로 답하면 개인화가 무의미하지 않나요?

**핵심 답변**

설문은 자기보고라는 한계가 있으므로 손실감내도·나이·은퇴 시점·실제 보유구성의 교차 점검과 재설문을 함께 제공합니다.

**구체 답변**

투자성향만으로 최종 위험을 결정하지 않습니다. 손실감내도가 충돌하면 더 보수적으로 낮추고, 현재 포트폴리오의 스트레스 손실이 감내도보다 큰지도 표시합니다. 프로필은 갱신 가능하며 실서비스에서는 응답 일관성 검사와 중요 답변 재확인 절차가 필요합니다.

### Q85. 사용자의 현재 보유 ETF 데이터가 없으면 어떻게 하나요?

**핵심 답변**

현재 보유 기준 리밸런싱은 계산하지 않고 입력이 필요하다고 안내하며, 성향 기반 목표 가이드는 별도로 제공할 수 있습니다.

**구체 답변**

엔진은 `current_holdings`가 비어 있으면 상태를 `not_requested`로 반환하고 임의의 현재 비중을 만들지 않습니다. 목표 포트폴리오 예시는 설문 조건으로 계산할 수 있지만 “현재 계좌를 점검했다”고 표현하지 않습니다. 일부 상품만 분류 가능하면 부분 결과와 미분류 금액 경고를 함께 제공합니다.

### Q86. 실제 금융사 계좌가 아닌데 “실제 보유 계좌”라고 말해도 되나요?

**핵심 답변**

현재 프로젝트에서는 인증 사용자에게 연결된 계좌 시나리오의 실제 보유 범위를 뜻하며, 외부 금융사 MyData 실계좌 연결은 아직 구현되지 않았다고 구분해서 말해야 합니다.

**구체 답변**

“실제 보유 계좌에 맞춘다”는 요구는 사용자별로 저장된 계좌 종류와 보유내역을 사용한다는 의미입니다. 은행·증권사 원장과 실시간 연결된 것은 아닙니다. 발표에서는 “사용자별 보유 시나리오 데이터”와 “향후 MyData 실계좌 연동”을 분리해 설명해야 과장되지 않습니다.

### Q87. 왜 자동 리밸런싱까지 구현하지 않았나요?

**핵심 답변**

자동매매는 기술 연결만의 문제가 아니라 일임·적합성·보안·오주문 통제까지 필요한 별도 제품 단계이기 때문입니다.

**구체 답변**

자동 리밸런싱에는 주문 API, 계좌 상태 동기화, 거래 가능 상품, 비용, 최소 주문단위, 실패 복구, 승인 절차, 비상정지, 감사 로그가 필요합니다. 금융규제상 일임 또는 로보어드바이저 검토도 필요합니다. 현재는 사용자가 구조와 근거를 이해하는 가이드에 집중하고, 실행은 명시적 비범위로 두었습니다.

### Q88. 이 시스템이 가장 크게 실패할 수 있는 지점은 어디인가요?

**핵심 답변**

규칙 변경을 놓치거나, 오래된 데이터와 계획가정을 현재 사실처럼 보여주거나, 개인화 설명이 확정적 추천으로 오해되는 지점입니다.

**구체 답변**

대응은 정책 버전·기준일·출처, 데이터 신선도 게이트, 계좌 규칙 회귀 테스트, 사용자 문구 검토, 운영 모니터링입니다. 기술적으로 숫자가 맞아도 표현이 과도하면 제품은 실패할 수 있으므로 엔진 정확성과 설명 품질을 같은 수준으로 관리해야 합니다.

### Q89. 다시 만든다면 무엇을 개선하고 싶나요?

**핵심 답변**

정책 파라미터의 근거와 실험 이력을 더 구조화하고, 실제 사용자 이해도와 행동 데이터를 바탕으로 정보 위계를 검증하고 싶습니다.

**구체 답변**

현재도 정책 버전과 테스트가 있지만, 각 파라미터의 승인자·근거·실험 결과를 관리 화면에서 추적할 수 있게 만들 수 있습니다. 리밸런싱 주기와 화면 구성은 사용자별 이해도, 재방문, 실제 점검 완료율로 검증해야 합니다. 데이터 측면에서는 실계좌 연동 전 별도 샌드박스로 계좌 동기화·상품 적격성 변경·주문 전 검증을 시험하고 싶습니다.

### Q90. 상용화를 위해 가장 먼저 해야 할 일은 무엇인가요?

**핵심 답변**

준법·법무 검토와 실계좌 데이터 계약을 먼저 확정한 뒤, 운영 모니터링과 사용자 수용성 검증을 진행해야 합니다.

**구체 답변**

우선 개인화 콘텐츠의 규제 지위, 광고심의, 적합성, 개인정보 처리, 외부 LLM 이용조건을 확정해야 합니다. 다음으로 MyData 또는 금융사 원장 연동 계약, 데이터 신선도와 장애 대응, 상품 적격성 변경 운영을 설계합니다. 이후 제한된 외부 베타에서 설명 이해도와 오해 가능성을 측정하고 주문 연결은 마지막 단계에서 검토합니다.

## 12. 시연 중 바로 쓸 수 있는 짧은 답변

| 질문 | 10초 답변 |
|---|---|
| AI가 비중을 계산하나요? | 아니요. 규칙 엔진이 계산하고 AI는 설명합니다. |
| 계좌가 왜 두 개만 나오나요? | 로그인 사용자가 보유한 계좌만 표시하기 때문입니다. |
| DC형과 IRP 한도는? | 일반 위험자산은 원칙적으로 계좌별 70% 한도입니다. |
| 연금저축도 70%인가요? | 아닙니다. 같은 일반 위험자산 총량 70% 한도를 적용하지 않습니다. |
| 그래프가 계좌마다 같은데요? | 목표 위험비중이 70% 이하이면 한도가 결합되지 않아 같을 수 있습니다. |
| 성향은 고정인가요? | 현재 설문 결과이며 재설문하면 갱신됩니다. |
| 공격형이면 무조건 85%인가요? | 아닙니다. 나이·은퇴·계좌 한도·손실감내도로 다시 조정합니다. |
| 왜 매월 점검하나요? | 공격형은 변동이 커 자주 확인하되 자동 매매는 하지 않습니다. |
| 과거 2025년 7월은 왜 나오나요? | 2025년 6월 유사국면 다음 달부터 실제 성과를 측정했기 때문입니다. |
| 과거 성과로 추천하나요? | 아니요. 참고 설명일 뿐 배분·계획수익률·리밸런싱 입력이 아닙니다. |
| 수익률을 예측하나요? | 과거 위험과 장기 계획가정을 보여줄 뿐 미래 수익을 예측·보장하지 않습니다. |
| 데이터 출처는? | KRX, 한투, KIND, FSS, 금융위 등 공식 원천을 사용합니다. |
| 분배금은 반영되나요? | 네. 가격과 확정 분배금 이벤트를 결합해 총수익을 계산합니다. |
| 매도하라고 알려주나요? | 매도 지시는 만들지 않고 새 납입으로 부족 자산을 채우는 예시를 우선합니다. |
| 실제 주문도 되나요? | 아닙니다. 현재는 정보·자문형 가이드이며 실행은 이용자가 합니다. |
| 다른 사람 계좌가 보일 수 있나요? | 인증·소유자 조건·RLS를 중첩하고 두 사용자 격리 E2E를 검증했습니다. |
| RAG가 실패하면요? | 승인 문서 전문검색으로 폴백해 서비스 전체 중단을 피합니다. |
| CI가 왜 빨간색인가요? | 현재 GitHub Actions 결제·한도로 실행 전 실패했으며 로컬 검증 결과를 별도로 기록했습니다. |

## 15. 마무리 답변

발표 마지막에 “본인이 만든 가치는 무엇인가”라는 질문을 받으면 다음과 같이 답한다.

> “제가 만든 핵심 가치는 복잡한 연금 규칙과 흩어진 ETF 데이터를 사용자가 이해할 수 있는 하나의 점검 흐름으로 연결한 것입니다. 특히 숫자를 LLM에 맡기지 않고 결정론 엔진으로 분리해 계좌 한도, 손실감내도, 리밸런싱 결과를 재현 가능하게 만들었습니다. 동시에 실제 보유 계좌만 보여주고 과거 데이터는 미래 신호로 쓰지 않는 경계를 지켜, 설명 가능성과 사용자 경험을 함께 개선했습니다.”
