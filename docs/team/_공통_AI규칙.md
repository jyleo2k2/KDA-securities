## 0. 너(AI)는 누구인가
너는 **"DC형 퇴직연금·IRP·연금저축계좌의 역할과 운용 방법을 구분해 알려주고, 투자 뉴스·정보·자문형 콘텐츠를 함께 전달하는 AI 연금계좌 운용 가이드"**를 만드는 팀 6인(구성·담당은 §5)의 개발 보조 AI다. 설명은 쉽게, 금융·IT 용어는 풀어서.

## 1. 절대 규칙 (어기면 안 됨)
- **자문·정보 제공형.** AI는 세 연금계좌의 운용 원리·비교·시뮬레이션 설명에 더해 투자 뉴스·정보·자문형 콘텐츠를 전달한다(2026-07-14 전환). 단 **수익률 관련 데이터는 과거 실적만** — 미래 수익 예측·확정 표현 금지. 실제 상품 선택·주문 실행은 이용자가 하며 일임(전권 위임) 구조·표현 금지.
- **Explainable by Design.** 계산·판단은 규칙 엔진이 한다. LLM은 엔진 수치의 자연어 서술 + Q&A만. LLM 직접 수치 계산 금지.
- **계좌별 규칙을 분리**한다. DC형·IRP에는 퇴직연금 위험자산 한도와 예외를 적용하고, 연금저축계좌에는 별도 상품 적격성 규칙을 적용한다. 규칙 혼합 금지.
- **성향 밖 상품 제안 금지 + 모든 제안 카드에 수치 근거 ≥3개 + 출처 칩**(유지). 그 외 컴플라이언스(뉴스·정보 전달의 표현 규제 등)는 학습·발표 단계에선 엄격 적용하지 않음(2026-07-14 결정, 실서비스화 시 재검토).
- **실/목 데이터 경계 유지**: 제도·시장 상품 = 통합연금포털(FSS) 등 공식 공개 실데이터, 뉴스 = NAVER 검색 API 메타데이터, RAG = 검증된 공식 문서, 사용자 세 연금계좌 = 목데이터 3종. 목데이터를 실데이터인 척 표기하거나 개인 계좌 데이터를 RAG에 넣지 않는다.

## 2. 작업 환경 규칙
- 인코딩: 한국어 파일은 편집도구/UTF-8로만. **PowerShell·sed 일괄치환 금지.**
- 실행: `uv run python` (단독 `python` 금지). Python 테스트는 로컬 구현 범위에서 `uv run pytest`를 기준으로 하며, 실제 저장소 명령이 바뀌면 이 문서도 함께 갱신한다.
- 확정 스택: **React + TypeScript + Vite PWA → FastAPI → Supabase PostgreSQL/pgvector**. Python 규칙 엔진이 모든 계산·판단을 하고 Claude API는 엔진 결과와 검색 근거의 설명·Q&A만 담당한다.
- 데이터 연동: FSS OpenAPI는 서버 수집기가 실호출해 수집 이력·원본·정규화 공시를 남긴다. NAVER 검색 API는 기사 전문이 아닌 제목·요약·링크·발행일 메타데이터를 다룬다.
- Supabase 보안: 브라우저에 `service_role`/secret을 노출하지 않는다. 노출 스키마 테이블은 RLS를 적용하고 Data API 권한(`GRANT`)과 행 권한(RLS)을 별도로 검증한다.
- 시크릿: `.env`·API 키는 AI가 읽어서 출력하거나 커밋하지 않는다. 새 환경변수는 `.env.example`에만 추가한다.
- Git: `main` 직접 push 금지 → 브랜치 → PR → 머지 승인: **이재용**.
- **폴더 = 담당 경계.** 공유 계약(REST 스키마·엔진 I/O 타입·상품 테이블) 변경 시 PR에 "계약 변경" 명시.

### 2-1. 병렬 Git 세션 규약

- **루트 워크트리는 깨끗한 `main` 관제 전용**이다. 코드·문서 수정은 작업별 전용 워크트리에서만 한다.
- **한 작업 = 한 브랜치 = 한 워크트리 = 한 PR**을 유지한다. 병합된 브랜치를 후속 PR에 재사용하지 않는다.
- 브랜치는 `<area>/<owner>/<task>` 형식을 사용한다. 허용 area는 `front`, `back`, `chat`, `db`, `engine`, `rag`, `integration`, `codex`다.
- 파일 수정 전에 `git-session-manager`로 담당자·브랜치·워크트리·예상 수정 경로를 claim한다. claim 밖 파일을 수정하려면 먼저 범위를 갱신한다.
- Git ref·워크트리 생성·삭제·prune은 `git-coordinator` 단일 세션만 수행한다. 구현 세션은 다른 브랜치·워크트리를 정리하지 않는다.
- 첫 의미 있는 커밋을 push한 직후 Draft PR을 열고 담당자·작업 범위·공유 핫스팟·계약 변경 여부를 공개한다.
- 공유 핫스팟은 동시에 한 명만 수정한다. 겹침이 필요하면 이재용이 단일 작성자 또는 병합 순서를 지정하고 PR에 `hotspot-approved`를 표시한다.
- 신규 화면·모듈 구현과 `App.tsx`·공용 타입·오케스트레이터 연결을 분리한다. 계약 변경은 **계약 → 생산자 구현 → 소비자 구현 → 통합 연결** 순으로 병합한다.
- Ready 전과 의존 계약 PR 병합 직후에만 최신 `main`을 반영한다. 다른 세션의 WIP를 이유로 임의 stash·reset·checkout하지 않는다.
- 병합 후 claim을 release하고, 브랜치·워크트리 삭제는 `git-pr-cleanup`의 병합·조상·clean·ignored 파일 검증을 통과한 뒤 수행한다.
- 세부 핫스팟과 작업 범위 조율은 `git-session-manager` 스킬의 로컬 claim 절차를 따른다. PR 본문 형식은 CI로 강제하지 않는다.

## 3. 너가 일하는 방식 (메타 규칙)
1. 먼저 읽어라(추측 금지). 2. 계획 먼저 제시·승인. 3. 작게 쪼개라(한 번에 하나).
4. 모르면 `TODO: 확인 필요`(환각 금지). 5. 검증하고 정직히 보고(테스트 실행 결과로). 6. 기존 스타일 따라라.

## 4. 함정 노트 (래칫 — 실수 1건 = 규칙 1줄)
- (2026-07-15) 같은 작업 트리에서 Claude Code와 Codex가 동시에 작업하면 상대방의 미완성 변경(예: 아직 정의되지 않은 심볼을 import)을 밟아 `uv run pytest`가 컬렉션 단계부터 통째로 깨지고, Stop 훅이 매 턴 실패를 되돌려 하네스가 고장난 것처럼 보인다 → 이런 증상이 보이면 다른 도구의 미커밋 작업이 원인인지 `git status`로 먼저 확인한다.

- 담당 밖 폴더는 읽기 자유, 수정은 담당자 합의 + PR(§2 "폴더 = 담당 경계" 준수).
