## 2. 기술 스택 선정 이유

### Q1. 왜 백엔드로 FastAPI를 선택했나요? Django나 Flask와 비교했나요?

**30초 답변:** 이 프로젝트는 인증, 외부 데이터 수집, Python 규칙 엔진, RAG, 챗 응답 스트리밍을 하나의 API 경계에서 조합해야 했습니다. 계산 로직이 Python에 있기 때문에 같은 런타임에서 Pydantic 계약과 비동기 API를 연결할 수 있는 FastAPI가 요구사항에 잘 맞았습니다. 다만 Django·Flask와 정량 비교한 기록은 없어서 “가장 우수하다”가 아니라 “현재 구조에 적합했다”고 설명하는 것이 정확합니다.

**꼬리질문 대비:** Django의 관리자·ORM 생태계보다 독립 규칙 엔진과 명시적 API 계약을 우선했습니다. Flask 대비 자동 OpenAPI와 Pydantic 검증을 활용하기 쉬웠습니다. 이 비교는 구현 특성에 따른 설명이며 별도 벤치마크 결과는 아닙니다.

**근거:** `docs/30_스펙/아키텍처.md:29-34`, `backend/app/main.py`

### Q2. 왜 Supabase PostgreSQL을 선택했나요? Firebase와 비교한 이유는 무엇인가요?

**30초 답변:** 사용자별 계좌·대화·투자성향처럼 관계와 소유권이 분명한 데이터가 중심이라 PostgreSQL이 맞았고, Supabase Auth와 RLS를 결합해 타 사용자 행 접근을 DB 계층에서도 차단할 수 있었습니다. Firebase와의 정량 비교 자료는 없으며, 핵심 선정 이유는 관계형 모델과 행 단위 권한을 한 플랫폼에서 운영할 수 있다는 점입니다.

**트레이드오프:** 서비스 역할 키의 권한이 크므로 브라우저에 노출하지 않고, 노출 스키마는 `GRANT`와 RLS를 각각 검증해야 합니다.

**근거:** `docs/30_스펙/아키텍처.md:170-178`, `supabase/AGENTS.md:47-53`

### Q3. 🔴 왜 별도 벡터 DB 대신 pgvector를 사용했나요?

**30초 답변:** 현재 승인 지식은 문서 15건·청크 56건으로 작고, 전문검색과 벡터검색 결과를 RRF로 합치는 구조입니다. 이 규모에서는 인증·메타데이터·벡터를 PostgreSQL 안에서 함께 관리하는 편이 운영 경계를 단순화합니다. HNSW 인덱스를 사용하지만, 코퍼스와 트래픽이 크게 늘면 Pinecone 같은 별도 검색 계층을 재검토해야 합니다.

**말하면 안 되는 답:** 별도 벡터 DB보다 항상 빠르거나 저렴하다는 주장. 해당 비교 실험은 없다.

**근거:** `docs/30_스펙/아키텍처.md:18`, `docs/30_스펙/아키텍처.md:77`, `docs/30_스펙/아키텍처.md:112`

### Q4. 🔴 왜 임베딩 모델로 BGE-M3를 선택했나요?

**30초 답변:** 1024차원 임베딩을 로컬에서 생성해 호출 비용과 외부 API 의존을 줄이고, 모델을 사용할 수 없는 환경에서는 전문검색으로 폴백하도록 구성했습니다. 모델 크기가 약 2GB이므로 프로세스마다 한 번만 로드합니다. 한국어 성능이 다른 모델보다 우수하다는 자체 벤치마크는 없으므로 그 이유를 선정 근거로 주장하지 않습니다.

**트레이드오프:** 첫 로드 비용과 메모리 사용량이 크며, 검색 품질 평가는 별도 질의셋으로 계속 측정해야 한다.

**근거:** `backend/app/ingestion/embeddings.py:3-4`, `backend/app/ingestion/embeddings.py:90`

### Q5. 왜 Claude와 pydantic-ai를 사용했고, 모델을 어떻게 나눴나요?

**30초 답변:** LLM은 계산자가 아니라 엔진 결과를 설명하는 역할로 제한했고, pydantic-ai의 구조화된 도구·응답 계약으로 그 경계를 구현했습니다. 모델은 감으로 고르지 않고 10문항을 각 20회 실행해 검증 통과율을 비교했습니다. Haiku가 60%, Sonnet adaptive thinking이 20%였기 때문에 실시간 내레이션은 Haiku, 일 1회 배치 요약은 Sonnet으로 분리했습니다. 이 결과는 해당 과제·프롬프트에서의 내부 실측이며 GPT나 Gemini와 비교한 결과는 아닙니다.

**추가 수치:** thinking ON은 약 7.2초, OFF는 약 3.6초였다.

**근거:** `docs/50_발표/발표_개요.md:76`, `docs/30_스펙/배포_운영_가이드.md:74-81`, `backend/app/chat/narrator.py:255-270`

### Q6. 왜 React + TypeScript + Vite PWA인가요? 네이티브 앱과 비교했나요?

**30초 답변:** 발표와 검증 단계에서 하나의 웹 코드베이스로 모바일 설치 경험, LAN 단말 테스트, 빠른 배포를 확보하려고 PWA로 구성했습니다. TypeScript는 화면과 API 계약의 정적 오류를 줄이고 Vite는 개발·빌드 경로를 단순화했습니다. 네이티브 앱과의 정량 비교는 없으며, 푸시·백그라운드·기기 API가 핵심이 되면 선택을 다시 검토해야 합니다.

**보안·캐시 포인트:** 인증·SSE 응답은 서비스워커 캐시에 남기지 않는 `no-store` 정책을 적용했다.

**근거:** `frontend/vite.config.ts:9`, `frontend/vite.config.ts:16-36`, `frontend/src/pwa/cachePolicy.ts:2-16`

### Q7. 왜 계산을 Python 규칙 엔진으로 분리했나요?

**30초 답변:** 연금계좌 한도와 세액 계산은 같은 입력에 같은 결과가 나와야 하고, 근거를 테스트로 고정할 수 있어야 합니다. 그래서 `Decimal` 기반 규칙 엔진이 계산·판단을 맡고 LLM은 결과를 바꾸지 못하게 했습니다. 이는 편의보다 금소법상 부당권유 위험과 생성형 모델의 수치 변형 가능성을 줄이기 위한 선택입니다.

**근거:** `docs/50_발표/발표_개요.md:66`, `backend/app/engine/AGENTS.md:20-21`

## 3. 아키텍처·역할 분리

### Q8. LLM이 실제로 숫자를 다시 계산하지 않는다는 것을 어떻게 보장하나요?

**30초 답변:** `evaluate_risk_cap()`과 `calculate_pension_tax_credit()` 같은 순수 함수가 계산한 결과만 도구 계약으로 LLM에 전달합니다. 내레이터가 숫자를 추가하거나 바꾸면 가드가 거부하고, 이미 생성된 결정론 답변을 유지합니다. 즉 프롬프트 지시만이 아니라 실행 순서와 사후 검증으로 막았습니다.

**근거:** `backend/app/engine/portfolio.py:47-101`, `backend/app/chat/tools.py:64-90`, `backend/app/chat/narrator.py:155-158`

### Q9. 질문의 의도 분류도 LLM이 하나요?

**30초 답변:** 1차 분류는 정규식·키워드 기반 `plan_question()`이 결정합니다. 개인정보, 주문 실행, 미래 예측, 개별 종목 요청 차단은 의도 판별보다 먼저 실행합니다. 규칙으로 분류되지 않은 질문만 LLM이 보조 분류하고, 그 결과도 다시 규칙 플래너를 통과시킵니다.

**근거:** `backend/app/chat/query_planner.py:896`, `backend/app/chat/query_planner.py:959`, `backend/app/chat/query_planner.py:1216`, `backend/app/chat/topic_guard.py:101`

### Q10. RAG와 규칙 엔진은 어떤 기준으로 나뉘나요?

**30초 답변:** “제도가 어떻게 되는가”처럼 공식 근거를 설명하는 질문은 RAG, “내 계좌에서 얼마인가”처럼 사용자 입력으로 계산하는 질문은 규칙 엔진이 담당합니다. 예를 들어 세액공제 제도 설명은 승인 문서를 검색하지만 실제 공제액은 엔진을 단일 진실 공급원으로 사용합니다.

**근거:** `docs/30_스펙/아키텍처.md`, `backend/app/chat/handlers/account_rules.py`, `backend/app/engine/pension_tax.py`

### Q11. 왜 WebSocket이 아니라 SSE를 사용했나요?

**30초 답변:** 현재 채팅 응답은 서버가 단계와 답변을 클라이언트로 보내는 단방향 스트림이면 충분해서 SSE로 단일화했습니다. WebSocket과의 별도 비교 ADR은 없으므로 복잡도나 성능 우위를 수치로 주장하지 않습니다.

**근거:** `backend/app/api/chat.py:319`

### Q12. 사용자는 LLM 답변이 늦을 때 무엇을 보나요?

**30초 답변:** 서버가 검증된 결정론 답변을 먼저 `answer_delta`로 전송하고, LLM 서술이 가드를 통과했을 때만 `narration_update`로 교체합니다. 따라서 LLM이 늦거나 실패해도 계산 결과를 먼저 볼 수 있고, 검증되지 않은 문장이 정답을 덮지 않습니다.

**근거:** `backend/app/api/chat.py:681`, `backend/app/api/chat.py:757`, `frontend/src/hooks/useChatStream.ts`

### Q13. 프리워밍으로 무엇이 개선됐나요?

**30초 답변:** BGE-M3와 내레이터처럼 첫 호출 비용이 큰 자원을 프로세스당 한 번 준비하고, 내레이션 캐시와 프롬프트 캐싱을 결합했습니다. 내부 개발 환경에서 내레이터 첫 호출은 약 14초에서 4초, 공시 질의는 약 1,200ms에서 396ms로 줄었습니다. 이 수치는 운영 SLA가 아니라 당시 개발 환경 실측입니다.

**트러블슈팅 서술:** 증상(첫 질문 지연) → 원인(모델·프롬프트 첫 준비 비용) → 조치(부팅 시 준비·캐시) → 결과(동일 조건 재측정) 순서로 말한다.

**근거:** `AGENTS.md`의 PR #51~#53·#54·#60 이력, `backend/app/chat/narrator.py`

### Q14. 동시 사용자가 늘어나도 확장 가능한가요?

**30초 답변:** 현재 부하테스트 결과는 없습니다. API와 DB 경계는 분리돼 있지만 내레이터·토픽가드·RAG 캐시가 프로세스 로컬이고 외부 LLM rate limit도 있어 수평 확장 시 캐시 일관성과 호출 제한이 병목 후보입니다. 다음 단계는 k6 또는 Locust로 p95 지연과 오류율을 측정한 뒤, 필요할 때 공유 캐시와 큐를 도입하는 것입니다.

**말하면 안 되는 답:** “대규모 트래픽을 견딘다.” 이를 입증할 측정이 없다.

## 4. 금융 도메인 정확성

### Q15. 🔴 적격 TDF나 디폴트옵션의 위험자산 한도 예외를 어떻게 판정하나요?

**30초 답변:** 상품명에서 TDF 여부를 추론하지 않습니다. 사업자 공식 목록의 `retirement_investment_limit_percent`가 70이 아닌 경우만 예외로 신뢰합니다. 근거 필드가 없으면 일반 위험자산 규칙을 적용해 보수적으로 실패합니다.

**근거:** `backend/app/engine/pension_eligibility.py:28-47`

### Q16. DC·IRP와 연금저축의 위험자산 규칙이 섞이지 않나요?

**30초 답변:** 계좌 타입별 모델과 평가 경로를 분리했습니다. 연금저축은 위험자산 총량 한도 필드가 `None`이고 결과도 `NOT_APPLICABLE`이며, 법정 예외를 임의 주입하면 Pydantic 검증에서 거부됩니다. 세 계좌 합산 값은 화면 표시용일 뿐 개별 계좌 규칙을 대체하지 않습니다.

**근거:** `backend/app/engine/models.py:130-141`, `backend/app/engine/models.py:174-187`, `backend/app/engine/aggregation.py`, `tests/test_engine.py:37-138`

### Q17. 🔴 연금계좌 연간 납입한도 1,800만원도 검증하나요?

**30초 답변:** 현재 엔진은 연금저축·IRP의 세액공제 한도 900만원 계산을 구현했지만, 연금계좌 합산 납입한도 1,800만원을 별도 차단하는 검증은 아직 없습니다. 발표에서는 둘을 혼동하지 않고, 1,800만원 검증은 후속 규칙으로 명시합니다.

### Q27. JWT를 직접 디코딩해서 인증하나요?

### Q28. 사용자 데이터 격리는 어떻게 보장하나요?

**30초 답변:** 첫째, DB RLS가 `owner_id = auth.uid()`를 검사하고 UPDATE에는 `USING`과 `WITH CHECK`를 모두 둡니다. 둘째, 백엔드 쿼리도 `owner_id` 조건을 중복 적용합니다. 셋째, 프론트는 사용자가 바뀌면 로컬 상태와 저장값을 초기화하고 이전 비동기 응답을 generation 값으로 폐기합니다. 서버 전용 테이블은 브라우저 역할의 권한을 회수했습니다.

### Q29. 액세스 토큰 만료 시 어떻게 처리하나요?

**30초 답변:** 일반 REST 요청은 401을 받으면 `refreshSession()`을 호출하고 같은 요청을 한 번만 재시도합니다. 무한 재시도를 막은 구조입니다. 다만 SSE POST에는 동일한 자동 갱신 경로가 없어 만료 시 재로그인 또는 스트림 재시도가 필요한 현재 한계가 있습니다.

### Q30. SSE 이벤트 순서와 오류 처리는 어떻게 되나요?

## 8. 발표자가 외울 핵심 답변 8개

1. **LLM은 계산하지 않는다.** Python 규칙 엔진이 계산하고 LLM은 검증된 결과만 설명한다.
2. **규칙은 계좌별로 분리했다.** DC·IRP의 70% 규칙을 연금저축에 적용하지 않는다.
3. **RAG와 엔진의 질문이 다르다.** 제도 설명은 RAG, 개인 수치 계산은 엔진이다.
4. **느리면 검증된 답부터 보여준다.** LLM 서술은 가드 통과 시에만 교체된다.
5. **데이터는 출처에서 결과까지 추적한다.** 요청·기준일·원본·해시·정규화 결과를 연결한다.
6. **과거 수익률로 ETF 순위를 만들지 않는다.** 거래대금 중앙값과 총보수로 순위를 정한다.
7. **비교하지 않은 기술은 우월하다고 말하지 않는다.** 요구사항 적합성과 감수한 비용을 함께 말한다.
8. **미구현 범위를 숨기지 않는다.** 실제 계좌 연결·주문, 부하테스트, 일부 세법 날짜 검증은 후속 과제다.

## 10. 근거가 부족한 질문에 답하는 원칙

- 비교 벤치마크가 없으면 “A보다 B가 좋다” 대신 “우리 요구사항에서 B의 이 특성을 사용했다”고 답한다.
- 수치가 있으면 측정 환경·표본·기준일을 함께 말한다. 내부 실측을 운영 성능이나 일반적 모델 우위로 확대하지 않는다.
- 구현되지 않은 기능은 현재 범위와 다음 검증 방법을 함께 말한다.
- 금융 규칙은 기억으로 답하지 않고 코드·공식 근거·기준일을 확인한다.
- 질문의 전제가 틀리면 바로잡는다. 특히 LLM 계산, 엔진·RAG 병렬 실행, 과거 수익률 기반 추천이라는 전제는 사실과 다르다.
