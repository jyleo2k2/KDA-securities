1. 서비스와 연금

사용자가 왜 이 서비스를 써야 하는지, 연금에 특화된 이유를 묻는 질문입니다.

기존 증권사 앱과 무엇이 다른가요?

증권사 앱은 보통 자사 계좌에서 어떤 상품을 거래할지가 중심입니다. 연금 코파일럿은 DC·IRP·연금저축처럼 역할과 제약이 다른 계좌를 놓고, 내 전체 연금을 어떻게 설계할지를 돕습니다.

한 줄 답변: “증권사 앱이 거래 중심이라면, 저희는 연금 의사결정 중심입니다.”

증권사가 똑같이 만들면 차별성이 없어지지 않나요?

맞습니다. 화면만 복제되면 차별성은 약해집니다. 그래서 목표는 증권사와 주문 경쟁을 하는 것이 아니라, 증권사 앱에도 연결될 수 있는 연금 특화 의사결정 레이어가 되는 것입니다.

AI가 상품을 직접 추천하거나 주문하나요?

아닙니다. 자산 진단·연금 계산·세액공제는 규칙 엔진이 처리하고, AI는 결과를 이해하기 쉽게 설명합니다. 실제 상품 선택과 주문은 이용자가 합니다.

DC·IRP·연금저축을 왜 따로 봐야 하나요?

세 계좌는 세제와 운용 제약이 다릅니다. 특히 DC·IRP와 연금저축은 위험자산·상품 적격성 판단을 같은 규칙으로 처리하면 안 되므로, 계좌별 규칙을 분리했습니다.

세액공제 계산 결과가 실제 신고 금액과 같나요?

입력한 소득과 납입 정보 기준의 확인 도구입니다. 개인별 공제 상황은 달라질 수 있으므로 실제 신고 전에는 금융기관 또는 세무 기준을 다시 확인해야 합니다.

이용자 Pick은 다른 사람을 따라 하게 만드는 것 아닌가요?

정답이나 추천 근거가 아니라 참고 정보입니다. 이용자 자신의 자산 진단과 전략 상세가 주된 판단 근거이고, Pick은 비슷한 조건의 사례를 보는 보조 단계입니다.

개인 계좌 정보는 안전한가요?

개인 계좌 정보와 지식 검색 문서를 분리하고, 로그인한 이용자가 자신의 데이터 범위에서만 조회하도록 설계했습니다. 개인 계좌 정보는 지식 검색 문맥에 넣지 않습니다.

실제 금융사 연동과 자동매매도 가능한가요?

현재 범위는 계좌 이해와 운용 판단 지원입니다. 실제 금융사 연결, 자금 이동, 자동매매는 포함하지 않습니다. 상용화 단계에서는 별도의 동의·보안·컴플라이언스 절차가 필요합니다.

2. 증권사 앱과의 관계

“증권사 앱이 ‘어떤 상품을 거래할지’를 돕는다면, 연금 코파일럿은 ‘내 전체 연금을 어떻게 설계할지’를 돕습니다.”

증권사에 적용하더라도 주문·자금이동·자동매매 전 단계의 연금 의사결정 지원 역할에 집중합니다. 특정 상품 추천과 주문 연결까지 제공하는 상용 서비스라면 별도 투자자 보호·컴플라이언스 검토가 필요합니다.

3. 기술 예상 질문

각 답변은 기술 나열보다 “왜 선택했는가”에 초점을 둡니다.

프런트엔드왜 React + TypeScript + Vite인가요?
모바일 화면을 빠르게 구성하고, TypeScript로 API 응답과 화면 상태의 불일치를 줄이기 위해 선택했습니다.
프런트엔드계산기 화면을 iframe으로 만든 이유는?
계산기 UI를 독립적으로 유지하면서도 React 앱과 메시지로 데이터를 교환하기 위해서입니다. 계산 로직은 iframe이 아니라 서버 엔진을 기준으로 둡니다.
프런트엔드챗봇 응답이 느리면 어떻게 하나요?
SSE 스트림으로 먼저 확인 가능한 결과를 보여주고, 자연어 설명은 이어서 갱신해 체감 대기 시간을 줄였습니다.
백엔드왜 FastAPI를 사용했나요?
규칙 엔진이 Python 기반이고, 타입 기반 API 계약과 비동기 스트리밍 응답을 구현하기에 적합합니다.
백엔드AI가 계산하면 틀릴 수 있는데요?
AI는 계산하지 않습니다. 자산 진단·연금 계산·세액공제는 규칙 엔진이 처리하며, AI는 검증된 결과를 설명합니다.
백엔드REST와 SSE를 왜 같이 쓰나요?
계좌·전략·계산기처럼 조회가 명확한 기능은 REST, 문장이 순차적으로 생성되는 챗봇은 SSE로 분리했습니다.
백엔드세액공제 정확성은 어떻게 보장하나요?
소득 구간, 납입액, 계좌별·합산 한도를 규칙으로 명시하고 결과를 테스트로 검증합니다.
데이터시장·ETF 데이터는 믿을 수 있나요?
검증 가능한 원천을 기준으로 수집하며, 기준일·원본 경로·정규화 결과를 보존해 결과를 재현할 수 있게 합니다.
데이터데이터가 없거나 오래되면 어떻게 하나요?
기준일과 출처를 표시하고, 근거가 충분하지 않으면 과도한 결론 대신 추가 확인이 필요하다고 안내합니다.
데이터개인 계좌 데이터와 RAG 문서는 왜 분리하나요?
개인 자산 정보가 지식 검색 문맥에 섞이거나 다른 답변에 노출되는 위험을 줄이기 위해서입니다.
AI·RAGRAG를 왜 사용하나요?
연금 제도와 계좌 규칙처럼 근거가 필요한 정보성 질문에 검증된 문서를 연결하기 위해서입니다.
AI·RAG환각은 어떻게 막나요?
근거 기반 정보 안내와 규칙 엔진 계산을 분리하고, 근거가 부족하면 확정적으로 답하지 않도록 응답 가드를 둡니다.
DB·보안다른 사용자의 계좌가 보일 위험은 없나요?
인증과 행 단위 접근 제어를 적용하고, 서버도 로그인한 이용자의 소유자 범위에서만 조회하도록 설계했습니다.
운영배포와 검증은 어떻게 하나요?
프런트, API, 인증·DB를 역할별로 분리하고, 백엔드 테스트·프런트 테스트·프로덕션 빌드·주요 사용자 흐름 검증을 함께 수행합니다.
