기술 스택 선정 근거

기술의 유명세가 아니라 금융 규칙의 결정성, 데이터 소유권, 설명 가능성, 제한된 개발 기간을 기준으로 선택을 설명합니다. 비교 실험이 없는 부분은 우월성이 아니라 적합성으로 말합니다.

React PWA → FastAPI → PostgreSQL의 단방향 구조 위에서 Python 규칙 엔진이 계산하고, pydantic-ai와 Claude는 검증된 결과의 설명만 담당하도록 책임을 분리했습니다.

03 · FRONTEND ALTERNATIVES

Vue 3도 가능했지만, 현재 요구에는 React 조합이 더 직접적이었습니다

후보가 화면을 만들 수 있는지가 아니라, 인증형 모바일 웹과 별도 FastAPI 백엔드라는 경계에서 불필요한 런타임과 재학습을 늘리지 않는지를 비교했습니다. 아래 평가는 성능 벤치마크 순위가 아니라 프로젝트 요구사항 적합도입니다.

선정 논리

공개 콘텐츠의 SEO·SSR은 핵심이 아니고, 앱스토어 배포와 고급 기기 API도 범위 밖이었습니다. 반면 로그인 이후의 상태 많은 화면, SSE 챗봇, API 계약 검증, 모바일 브라우저 배포가 중요했으므로 React SPA + strict TypeScript + Vite 정적 빌드 + PWA 전달 구조를 선택했습니다.

React상태가 많은 화면을 재사용 가능한 컴포넌트와 단방향 데이터 흐름으로 구성
TypeScriptFastAPI 응답과 화면 상태의 형태를 strict 검사와 tsc --noEmit으로 확인
Vite별도 Node 서버 없이 개발 HMR과 Vercel에 올릴 정적 프로덕션 번들을 담당
PWAURL 접근성을 유지하면서 standalone manifest와 버전된 정적 자산 캐시를 제공
후보잘 맞는 상황이번 요구 적합도이번에 선택하거나 제외한 이유다시 검토할 조건
React + TS
+ Vite PWA		 상호작용이 많은 API 기반 SPA, 컴포넌트 테스트, 정적 웹 배포 높음 · 선택 기존 JavaScript 생태계 안에서 화면·라우팅·SSE 상태를 구성하고, 타입 검사와 정적 배포를 FastAPI와 분리할 수 있었습니다. 네이티브 기능이 핵심이 되면 React Native 등 앱 계층을 별도로 검토
Vue 3 + TS
+ Vite		 점진 도입, Single-File Component, Composition API 기반 SPA 높음 · 대안 가능 Vue 3도 TypeScript·Vite·PWA 요구를 충족합니다. 다만 같은 제품 기능을 위해 React 컴포넌트·JSX·Testing Library 흐름을 SFC·Vue 테스트 흐름으로 바꿀 만큼의 추가 이익이 없었습니다. 새 프로젝트이고 팀의 주력 경험과 공통 UI 자산이 Vue일 때
Next.js 공개 콘텐츠 SEO, SSR·SSG, 서버 컴포넌트와 웹 BFF가 필요한 서비스 중간 핵심 화면이 로그인 뒤의 클라이언트 상호작용이고 서버 계산·인증 API는 FastAPI가 소유합니다. Next.js의 서버 기능을 쓰면 Node 실행 경계가 늘고, 정적 export만 쓰면 핵심 장점을 거의 활용하지 못합니다. 공개 연금 콘텐츠의 검색 유입, 서버 렌더링 또는 프론트 전용 BFF가 핵심이 될 때
Flutter iOS·Android·Web을 한 Dart 코드베이스로 제공하고 앱 UI 일관성이 중요한 경우 조건부 이번 범위는 모바일 브라우저와 URL 시연이 우선이고 앱스토어 배포·고급 기기 API가 필요하지 않았습니다. Dart·Flutter 빌드 체계를 추가할 이유보다 기존 웹 표준과 TypeScript를 유지할 이익이 컸습니다. 스토어 배포, 네이티브 기기 기능, 모바일 앱과 웹의 단일 UI 코드가 핵심이 될 때

중요: Vue 3나 Next.js가 열등해서 제외한 것이 아닙니다. 이번 백엔드 경계와 전달 채널에서 활용하지 않을 기능과 전환 비용을 줄인 선택입니다. PWA도 전체 오프라인 앱을 뜻하지 않으며, 개인정보·API·SSE 응답은 의도적으로 캐시하지 않습니다. 현재 manifest에는 설치 아이콘이 없어 브라우저별 완전한 설치 자격은 후속 검증 항목입니다.

01

React + TypeScript + Vite PWA

사용자 경험 계층

근거 강도 · 중간

왜 선택했나

인증 뒤에서 동작하는 API 중심 SPA라 SSR 서버보다 클라이언트 상호작용이 중요했습니다. React로 화면 상태를 컴포넌트화하고, TypeScript의 strict 검사로 API·화면 계약을 확인하며, Vite로 정적 번들을 만들어 별도 FastAPI 서버와 책임을 분리했습니다.

무엇을 감수했나

Vue 3 대비 생산성 우위를 실측한 자료는 없고 네이티브 앱과의 정량 비교도 없습니다. 현재 PWA는 manifest·서비스 워커·정적 셸 캐시까지 구현됐지만 설치 아이콘과 브라우저별 설치 자격은 검증이 남았습니다. 고급 기기 API가 핵심이 되면 네이티브 계층도 다시 검토해야 합니다.

30초 문장 · “Vue 3도 가능한 대안이지만 우리 서비스는 SEO용 서버 렌더링이나 네이티브 기기 기능보다 로그인 뒤의 상호작용과 API 계약이 중요했습니다. 그래서 React·strict TypeScript로 화면을 만들고, Vite 정적 빌드와 PWA로 모바일 웹을 배포했습니다.”

02

FastAPI + Pydantic

서비스 API 경계

근거 강도 · 중간 이상

왜 선택했나

규칙 엔진, 수집기, RAG가 모두 Python이므로 같은 런타임에서 API 입력·출력 검증, 비동기 연동, SSE 스트리밍을 연결할 수 있습니다. 계산 모델을 다른 언어로 다시 구현하는 경계를 줄였습니다.

무엇을 감수했나

Django·Flask보다 몇 배 빠르다는 자체 부하테스트는 없습니다. 관리자 화면보다 독립 규칙 엔진과 명시적인 API 계약을 우선한 선택입니다.

30초 문장 · “핵심 계산 엔진과 API를 같은 Python 런타임에 두어 재작성과 직렬화 경계를 줄였고, Pydantic 검증과 OpenAPI, SSE를 함께 활용했습니다.”

03

Python 규칙 엔진

금융 계산의 단일 진실 공급원

근거 강도 · 매우 강함

왜 선택했나

연금계좌 한도, 세액, 배분은 같은 입력에 같은 결과가 필요합니다. Decimal 기반 순수 함수로 계산하고 불변식 테스트로 규칙을 고정하면 결과와 근거를 재현할 수 있습니다.

무엇을 감수했나

자연어 유연성보다 명시적인 규칙 관리 비용을 선택했습니다. 법령과 가정이 바뀌면 버전형 규칙과 테스트를 함께 갱신해야 합니다.

30초 문장 · “LLM이 계산하게 하지 않고 규칙 엔진이 모든 수치를 확정합니다. LLM이 새 숫자를 만들거나 바꾸면 가드가 거부하고 결정론 답변으로 돌아갑니다.”

04

Supabase PostgreSQL + Auth + RLS

데이터와 사용자 소유권

근거 강도 · 중간

왜 선택했나

계좌·대화·투자성향은 관계와 소유권이 분명한 데이터입니다. PostgreSQL 관계형 모델과 Supabase Auth, 행 단위 보안(RLS)을 결합해 사용자별 접근을 DB 계층에서도 차단했습니다.

무엇을 감수했나

서비스 역할 키의 권한이 크므로 브라우저 노출을 금지하고, 테이블 접근 권한인 GRANT와 사용자 행 권한인 RLS를 별도로 검증해야 합니다. Firebase와 정량 비교한 자료는 없습니다.

30초 문장 · “관계형 데이터와 사용자별 소유권을 한 플랫폼에서 관리하고, 실제 두 사용자 Auth/RLS 흐름으로 타 사용자 행 차단을 검증했습니다.”

05

pgvector + BGE-M3 하이브리드 검색

검증 문서 RAG

근거 강도 · 조건부

왜 선택했나

현재 승인 지식 코퍼스가 작고 사용자·권한·검색 메타데이터가 이미 PostgreSQL에 있어 전문검색과 벡터검색을 한 DB에서 결합했습니다. BGE-M3는 로컬 임베딩으로 외부 모델 API 호출 의존을 줄일 수 있습니다.

무엇을 감수했나

BGE-M3는 첫 로드와 2GB 이상 메모리 비용이 있습니다. 모델이 없는 배포에서는 전문검색으로 폴백합니다. 별도 벡터 DB보다 항상 빠르다는 실험이나 한국어 모델 우위 벤치마크는 없습니다.

30초 문장 · “작은 승인 코퍼스와 권한 메타데이터를 PostgreSQL 안에서 함께 관리해 동기화 경계를 줄였고, 임베더가 없을 때도 전문검색으로 서비스가 유지되게 했습니다.”

06

pydantic-ai + Claude

검증 결과의 자연어 설명

근거 강도 · 매우 강함

왜 선택했나

pydantic-ai의 구조화 출력과 도구 계약으로 LLM 역할을 설명과 Q&A에 제한했습니다. 모델 비교에서도 같은 가드 아래 안전성과 숫자 정확도가 같다면 사용자 대기 시간이 짧고 비용이 낮은 모델을 실시간 경로에 둔다는 기준을 적용했습니다.

무엇을 감수했나

외부 모델 호출 지연과 장애가 남습니다. 그래서 응답을 엔진 검증 결과부터 보내고, 내레이션은 교체 이벤트로 전달하며 실패 시 기본 답변을 유지합니다.

30초 문장 · “LLM은 답을 결정하지 않고 검증된 답을 읽기 쉽게 바꿉니다. 실시간 내레이션은 빠른 모델, 저빈도 배치 요약은 상위 모델로 역할을 나눴습니다.”

07

Vercel + Render

발표·검증 단계 배포

근거 강도 · 비용 강함

왜 선택했나

정적 프론트와 API 서버를 분리해 배포 경계를 단순화하고 초기 인프라 비용을 낮췄습니다. Vercel은 프론트를 CDN에, Render는 FastAPI를 실행합니다.

무엇을 감수했나

무료 Render는 유휴 후 콜드 스타트가 있습니다. 프리워밍은 프로세스 내부 첫 호출 비용을 줄일 뿐 플랫폼 재기동 자체를 없애지는 못합니다. 운영 전에는 상시 인스턴스와 부하테스트가 필요합니다.

30초 문장 · “검증 단계에서는 초기 비용을 낮추는 배포 구성을 택했고, 대신 콜드 스타트를 명시적인 운영 전환 과제로 남겼습니다.”

  • Vue 3도 충분한 대안이지만 전환을 정당화할 제품 이익이 없었다고 설명합니다.
  • 속도는 스택 이름이 아니라 실제 측정한 프리워밍·연결 풀 결과로 설명합니다.
  • LLM은 계산자가 아니라 검증 결과의 설명 계층입니다.
  • Auth와 RLS는 실제 사용자 분리 흐름으로 검증했습니다.
  • 운영 전환 시 다시 설계할 비용과 병목을 함께 말합니다.

이렇게 말하지 않습니다

  • “FastAPI가 Django나 Flask보다 몇 배 빠르다.”
  • “pgvector가 별도 벡터 DB보다 항상 싸고 빠르다.”
  • “BGE-M3가 한국어에서 가장 좋다.”
  • “PWA가 네이티브 앱보다 항상 저렴하고 빠르다.”
  • “React가 Vue 3보다 성능과 생산성이 항상 높다.”
  • “무료 인프라에서도 운영 성능 문제가 없다.”

07 · FOLLOW-UP Q&A

심사위원 꼬리질문 대응

왜 Vue 3가 아니라 React인가요?

Vue 3도 TypeScript와 Vite를 지원해 기능상 충분한 대안입니다. 다만 이번 서비스는 React 기반 컴포넌트·라우팅·테스트 흐름으로 상태가 많은 인증형 SPA를 구현할 수 있었고, Vue SFC와 Composition API로 바꿔 얻는 추가 제품 가치가 없었습니다. React의 보편적 우위를 주장하는 선택이 아니라 팀과 구현 경계에 맞춘 선택입니다.

왜 Next.js가 아니라 Vite SPA인가요?

공개 페이지의 SEO나 서버 렌더링이 핵심이면 Next.js가 유리합니다. 이 서비스의 핵심 화면은 로그인 뒤에서 동작하고, 서버 계산·인증·SSE는 FastAPI가 이미 담당합니다. Next.js 서버 기능을 더해 실행 경계를 늘리거나 정적 export로 장점을 제한하기보다, Vite가 만든 정적 프론트와 FastAPI의 경계를 유지했습니다.

왜 Flutter 앱이 아니라 PWA인가요?

이번 단계의 전달 채널은 설치 심사 없는 URL과 모바일 브라우저 시연이고, 앱스토어 배포나 고급 기기 API는 요구사항이 아니었습니다. PWA 구조는 standalone manifest와 정적 셸 캐시를 제공하되 API와 개인정보는 캐시하지 않습니다. 현재 완전한 설치 자격 검증은 남아 있고, 네이티브 기능이 핵심이 되면 Flutter나 React Native를 다시 비교합니다.

왜 LLM이 아니라 규칙 엔진이 계산하나요?

연금 한도와 세액은 같은 입력에 같은 결과가 필요하고 근거를 재현할 수 있어야 합니다. 규칙 엔진이 수치를 확정하고 LLM은 그 결과만 설명하게 해 생성형 모델의 숫자 변형 위험을 줄였습니다.

왜 Firebase가 아니라 Supabase인가요?

계좌·보유자산·성향·대화는 관계가 강하고 사용자별 소유권이 명확합니다. PostgreSQL 관계형 모델과 RLS를 한 플랫폼에서 운영하는 점이 요구사항에 맞았습니다. Firebase와 정량 비교한 결과는 없습니다.

왜 별도 벡터 DB를 쓰지 않았나요?

현재 승인 코퍼스가 작고 검색 메타데이터와 권한 데이터가 이미 PostgreSQL에 있습니다. 이 규모에서는 별도 동기화 경계를 만들지 않는 편이 단순했습니다. 규모와 트래픽이 커지면 별도 검색 계층을 재검토합니다.

Claude에 종속된 구조 아닌가요?

엔진 결과와 검증 가드는 모델 밖에 있고 pydantic-ai 계약 뒤에 모델을 둡니다. 내레이터가 실패해도 결정론 답변이 유지되며, 같은 가드 아래 다른 모델을 비교할 수 있는 구조입니다.

무료 배포 구성이 실서비스에도 적합한가요?

아닙니다. 발표와 검증 단계의 초기 비용을 낮춘 선택입니다. 운영 전에는 상시 인스턴스, 부하테스트, 실제 토큰 비용과 캐시 적중률 측정이 필요합니다.
