선정 논리

React상태가 많은 화면을 재사용 가능한 컴포넌트와 단방향 데이터 흐름으로 구성

React + TS
+ Vite PWA		 상호작용이 많은 API 기반 SPA, 컴포넌트 테스트, 정적 웹 배포 높음 · 선택 기존 JavaScript 생태계 안에서 화면·라우팅·SSE 상태를 구성하고, 타입 검사와 정적 배포를 FastAPI와 분리할 수 있었습니다. 네이티브 기능이 핵심이 되면 React Native 등 앱 계층을 별도로 검토
Vue 3 + TS
+ Vite		 점진 도입, Single-File Component, Composition API 기반 SPA 높음 · 대안 가능 Vue 3도 TypeScript·Vite·PWA 요구를 충족합니다. 다만 같은 제품 기능을 위해 React 컴포넌트·JSX·Testing Library 흐름을 SFC·Vue 테스트 흐름으로 바꿀 만큼의 추가 이익이 없었습니다. 새 프로젝트이고 팀의 주력 경험과 공통 UI 자산이 Vue일 때
Next.js 공개 콘텐츠 SEO, SSR·SSG, 서버 컴포넌트와 웹 BFF가 필요한 서비스 중간 핵심 화면이 로그인 뒤의 클라이언트 상호작용이고 서버 계산·인증 API는 FastAPI가 소유합니다. Next.js의 서버 기능을 쓰면 Node 실행 경계가 늘고, 정적 export만 쓰면 핵심 장점을 거의 활용하지 못합니다. 공개 연금 콘텐츠의 검색 유입, 서버 렌더링 또는 프론트 전용 BFF가 핵심이 될 때
Flutter iOS·Android·Web을 한 Dart 코드베이스로 제공하고 앱 UI 일관성이 중요한 경우 조건부 이번 범위는 모바일 브라우저와 URL 시연이 우선이고 앱스토어 배포·고급 기기 API가 필요하지 않았습니다. Dart·Flutter 빌드 체계를 추가할 이유보다 기존 웹 표준과 TypeScript를 유지할 이익이 컸습니다. 스토어 배포, 네이티브 기기 기능, 모바일 앱과 웹의 단일 UI 코드가 핵심이 될 때

중요: Vue 3나 Next.js가 열등해서 제외한 것이 아닙니다. 이번 백엔드 경계와 전달 채널에서 활용하지 않을 기능과 전환 비용을 줄인 선택입니다. PWA도 전체 오프라인 앱을 뜻하지 않으며, 개인정보·API·SSE 응답은 의도적으로 캐시하지 않습니다. 현재 manifest에는 설치 아이콘이 없어 브라우저별 완전한 설치 자격은 후속 검증 항목입니다.

30초 문장 · “Vue 3도 가능한 대안이지만 우리 서비스는 SEO용 서버 렌더링이나 네이티브 기기 기능보다 로그인 뒤의 상호작용과 API 계약이 중요했습니다. 그래서 React·strict TypeScript로 화면을 만들고, Vite 정적 빌드와 PWA로 모바일 웹을 배포했습니다.”

Python 규칙 엔진

왜 선택했나

연금계좌 한도, 세액, 배분은 같은 입력에 같은 결과가 필요합니다. Decimal 기반 순수 함수로 계산하고 불변식 테스트로 규칙을 고정하면 결과와 근거를 재현할 수 있습니다.

08 · FOLLOW-UP Q&A

심사위원 꼬리질문 대응

왜 Vue 3가 아니라 React인가요?

Vue 3도 TypeScript와 Vite를 지원해 기능상 충분한 대안입니다. 다만 이번 서비스는 React 기반 컴포넌트·라우팅·테스트 흐름으로 상태가 많은 인증형 SPA를 구현할 수 있었고, Vue SFC와 Composition API로 바꿔 얻는 추가 제품 가치가 없었습니다. React의 보편적 우위를 주장하는 선택이 아니라 팀과 구현 경계에 맞춘 선택입니다.

왜 Next.js가 아니라 Vite SPA인가요?

공개 페이지의 SEO나 서버 렌더링이 핵심이면 Next.js가 유리합니다. 이 서비스의 핵심 화면은 로그인 뒤에서 동작하고, 서버 계산·인증·SSE는 FastAPI가 이미 담당합니다. Next.js 서버 기능을 더해 실행 경계를 늘리거나 정적 export로 장점을 제한하기보다, Vite가 만든 정적 프론트와 FastAPI의 경계를 유지했습니다.

왜 Flutter 앱이 아니라 PWA인가요?

이번 단계의 전달 채널은 설치 심사 없는 URL과 모바일 브라우저 시연이고, 앱스토어 배포나 고급 기기 API는 요구사항이 아니었습니다. PWA 구조는 standalone manifest와 정적 셸 캐시를 제공하되 API와 개인정보는 캐시하지 않습니다. 현재 완전한 설치 자격 검증은 남아 있고, 네이티브 기능이 핵심이 되면 Flutter나 React Native를 다시 비교합니다.

왜 Django·Flask·NestJS가 아니라 FastAPI인가요?

성능 순위 때문에 고른 것이 아닙니다. 계산 엔진·수집기·RAG가 Python이고 API에는 Pydantic 검증, OpenAPI, SSE가 필요했습니다. FastAPI는 이 경계를 같은 타입과 런타임으로 연결합니다. Django 관리자·ORM이 핵심이면 DRF, 아주 작은 API면 Flask, 백엔드를 TypeScript로 통일한다면 NestJS가 더 적합할 수 있습니다.

왜 Drools나 OPA 같은 규칙 엔진을 쓰지 않았나요?

Drools·DMN은 다수의 결정표를 현업이 관리할 때, OPA는 여러 서비스의 허용·거부 정책을 통합할 때 강합니다. 현재 핵심은 Decimal 금액, 시계열, 자산배분 계산이어서 Python 순수 함수와 불변식 테스트가 더 직접적입니다. 규칙 수와 비개발자 승인 흐름이 커지면 DMN을, 서비스 공통 정책이 생기면 OPA를 재검토합니다.

왜 LLM이 아니라 규칙 엔진이 계산하나요?

연금 한도와 세액은 같은 입력에 같은 결과가 필요하고 근거를 재현할 수 있어야 합니다. 규칙 엔진이 수치를 확정하고 LLM은 그 결과만 설명하게 해 생성형 모델의 숫자 변형 위험을 줄였습니다.

왜 Firebase·Amplify·Appwrite가 아니라 Supabase인가요?

계좌·보유자산·성향·대화는 관계가 강하고 사용자별 소유권이 명확합니다. PostgreSQL의 SQL·외래키·마이그레이션과 Auth 연계 RLS, 전문검색·pgvector를 한 데이터 경계에서 쓰는 점이 맞았습니다. Firestore의 문서 동기화, Amplify의 AWS 통합, Appwrite의 자체 호스팅이 핵심이면 선택이 달라질 수 있으며 실제 견적 비교는 없습니다.

왜 Pinecone·Qdrant 같은 별도 벡터 DB를 쓰지 않았나요?

현재 승인 코퍼스가 작고 출처·승인 상태·리뷰 기한이 PostgreSQL에 있습니다. pgvector와 전문검색을 같은 트랜잭션에 두면 별도 인덱스의 적재·삭제·권한 동기화가 없습니다. 벡터 규모와 부하가 병목으로 측정되면 Pinecone·Qdrant·Elasticsearch를 같은 평가셋으로 다시 비교합니다.

왜 BGE-M3이고 multilingual-e5나 외부 임베딩 API가 아닌가요?

BGE-M3는 로컬 실행, 다국어, 1024차원, 긴 입력과 향후 여러 검색 방식 확장이 가능해 선택했습니다. 다만 현재 구현은 dense만 사용하고 Render에서는 선택 의존성이 빠질 수 있습니다. multilingual-e5나 호스팅 API와 한국어 금융 검색 정확도를 비교하지 않았으므로 우월성을 주장하지 않으며, 검색 평가셋이 생기면 재선정합니다.

왜 LangChain·LangGraph·LlamaIndex가 아니라 pydantic-ai인가요?

현재 LLM은 짧은 분류와 재서술만 하고 순서와 계산은 결정론 코드가 소유합니다. 그래서 Pydantic 출력·도구 검증과 공급자 교체 경계만 제공하는 pydantic-ai가 작게 맞았습니다. 장기 실행·중단·승인은 LangGraph, 다양한 문서 적재와 인덱스 추상화는 LlamaIndex가 더 적합할 수 있습니다.

왜 Claude나 GPT가 아니라 Gemini Flash-Lite인가요?

같은 10개 질문과 같은 가드로 5개 모델을 비교했을 때 숫자 정확도와 가드 통과율은 같았습니다. Gemini 3.5 Flash-Lite가 p50 1.16초, p95 1.28초로 가장 짧고 계산상 호출비도 가장 낮아 현재 실시간 기본값으로 뒀습니다. 표본은 모델당 10회뿐이고 문체 보정이 필요하므로 절대적 모델 우위가 아니라 현재 경로의 선택입니다.

특정 LLM 공급자에 종속된 구조 아닌가요?

엔진 결과와 검증 가드는 모델 밖에 있고 pydantic-ai 계약 뒤에 Google·Anthropic 공급자를 둡니다. 내레이터가 실패해도 결정론 답변이 유지되며, 다섯 모델이 같은 입력과 가드에서 동작하는 것을 확인했습니다. 공급자별 옵션과 문체 차이는 남아 있어 완전 무비용 교체를 뜻하지는 않습니다.

왜 Railway나 AWS가 아니라 Vercel·Render인가요?

Vite 정적 프론트와 FastAPI 장기 실행 서버를 현재 코드 경계 그대로 나누고 초기 운영 설정을 줄이기 위해서입니다. Railway는 두 서비스를 한 프로젝트로 모으는 강한 대안이고, AWS App Runner는 IAM·VPC·자동 확장이 필요한 운영 단계에 적합합니다. 아직 동일 트래픽의 비용·지연 비교가 없어 현재 배포를 우월하다고 말하지 않습니다.

무료 배포 구성이 실서비스에도 적합한가요?

아닙니다. 발표와 검증 단계의 초기 비용을 낮춘 선택입니다. 운영 전에는 상시 인스턴스, 부하테스트, 실제 토큰 비용과 캐시 적중률 측정이 필요합니다.
