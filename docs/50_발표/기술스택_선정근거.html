01

React + TypeScript + Vite PWA

사용자 경험 계층

근거 강도 · 중간

왜 선택했나

제한된 기간에 하나의 웹 코드베이스로 모바일 화면, 설치 경험, LAN 단말 테스트와 빠른 배포를 확보하기 위해서입니다. TypeScript는 API 응답과 화면 계약의 정적 오류를 줄이고 Vite는 개발 반복 경로를 단순화합니다.

무엇을 감수했나

네이티브 앱과의 정량 비교는 없습니다. 푸시, 백그라운드 처리, 기기 API가 핵심이 되면 네이티브 또는 하이브리드 전환을 다시 검토해야 합니다.

30초 문장 · “iOS와 Android를 따로 만들기보다 React PWA 하나로 모바일 경험을 구현했고, TypeScript와 Vite로 화면 계약과 개발 반복 속도를 관리했습니다.”

02

FastAPI + Pydantic

서비스 API 경계

근거 강도 · 중간 이상

왜 선택했나

규칙 엔진, 수집기, RAG가 모두 Python이므로 같은 런타임에서 API 입력·출력 검증, 비동기 연동, SSE 스트리밍을 연결할 수 있습니다. 계산 모델을 다른 언어로 다시 구현하는 경계를 줄였습니다.

무엇을 감수했나

Django·Flask보다 몇 배 빠르다는 자체 부하테스트는 없습니다. 관리자 화면보다 독립 규칙 엔진과 명시적인 API 계약을 우선한 선택입니다.

30초 문장 · “핵심 계산 엔진과 API를 같은 Python 런타임에 두어 재작성과 직렬화 경계를 줄였고, Pydantic 검증과 OpenAPI, SSE를 함께 활용했습니다.”

03

Python 규칙 엔진

금융 계산의 단일 진실 공급원

근거 강도 · 매우 강함

왜 선택했나

연금계좌 한도, 세액, 배분은 같은 입력에 같은 결과가 필요합니다. Decimal 기반 순수 함수로 계산하고 불변식 테스트로 규칙을 고정하면 결과와 근거를 재현할 수 있습니다.

무엇을 감수했나

자연어 유연성보다 명시적인 규칙 관리 비용을 선택했습니다. 법령과 가정이 바뀌면 버전형 규칙과 테스트를 함께 갱신해야 합니다.

30초 문장 · “LLM이 계산하게 하지 않고 규칙 엔진이 모든 수치를 확정합니다. LLM이 새 숫자를 만들거나 바꾸면 가드가 거부하고 결정론 답변으로 돌아갑니다.”

04

Supabase PostgreSQL + Auth + RLS

데이터와 사용자 소유권

근거 강도 · 중간

왜 선택했나

계좌·대화·투자성향은 관계와 소유권이 분명한 데이터입니다. PostgreSQL 관계형 모델과 Supabase Auth, 행 단위 보안(RLS)을 결합해 사용자별 접근을 DB 계층에서도 차단했습니다.

무엇을 감수했나

서비스 역할 키의 권한이 크므로 브라우저 노출을 금지하고, 테이블 접근 권한인 GRANT와 사용자 행 권한인 RLS를 별도로 검증해야 합니다. Firebase와 정량 비교한 자료는 없습니다.

30초 문장 · “관계형 데이터와 사용자별 소유권을 한 플랫폼에서 관리하고, 실제 두 사용자 Auth/RLS 흐름으로 타 사용자 행 차단을 검증했습니다.”

05

pgvector + BGE-M3 하이브리드 검색

검증 문서 RAG

근거 강도 · 조건부

왜 선택했나

현재 승인 지식 코퍼스가 작고 사용자·권한·검색 메타데이터가 이미 PostgreSQL에 있어 전문검색과 벡터검색을 한 DB에서 결합했습니다. BGE-M3는 로컬 임베딩으로 외부 모델 API 호출 의존을 줄일 수 있습니다.

무엇을 감수했나

BGE-M3는 첫 로드와 2GB 이상 메모리 비용이 있습니다. 모델이 없는 배포에서는 전문검색으로 폴백합니다. 별도 벡터 DB보다 항상 빠르다는 실험이나 한국어 모델 우위 벤치마크는 없습니다.

30초 문장 · “작은 승인 코퍼스와 권한 메타데이터를 PostgreSQL 안에서 함께 관리해 동기화 경계를 줄였고, 임베더가 없을 때도 전문검색으로 서비스가 유지되게 했습니다.”

06

pydantic-ai + Claude

검증 결과의 자연어 설명

근거 강도 · 매우 강함

왜 선택했나

pydantic-ai의 구조화 출력과 도구 계약으로 LLM 역할을 설명과 Q&A에 제한했습니다. 모델 비교에서도 같은 가드 아래 안전성과 숫자 정확도가 같다면 사용자 대기 시간이 짧고 비용이 낮은 모델을 실시간 경로에 둔다는 기준을 적용했습니다.

무엇을 감수했나

외부 모델 호출 지연과 장애가 남습니다. 그래서 응답을 엔진 검증 결과부터 보내고, 내레이션은 교체 이벤트로 전달하며 실패 시 기본 답변을 유지합니다.

30초 문장 · “LLM은 답을 결정하지 않고 검증된 답을 읽기 쉽게 바꿉니다. 실시간 내레이션은 빠른 모델, 저빈도 배치 요약은 상위 모델로 역할을 나눴습니다.”

07

Vercel + Render

발표·검증 단계 배포

근거 강도 · 비용 강함

왜 선택했나

정적 프론트와 API 서버를 분리해 배포 경계를 단순화하고 초기 인프라 비용을 낮췄습니다. Vercel은 프론트를 CDN에, Render는 FastAPI를 실행합니다.

무엇을 감수했나

무료 Render는 유휴 후 콜드 스타트가 있습니다. 프리워밍은 프로세스 내부 첫 호출 비용을 줄일 뿐 플랫폼 재기동 자체를 없애지는 못합니다. 운영 전에는 상시 인스턴스와 부하테스트가 필요합니다.

30초 문장 · “검증 단계에서는 초기 비용을 낮추는 배포 구성을 택했고, 대신 콜드 스타트를 명시적인 운영 전환 과제로 남겼습니다.”

06 · FOLLOW-UP Q&A

심사위원 꼬리질문 대응

왜 LLM이 아니라 규칙 엔진이 계산하나요?

연금 한도와 세액은 같은 입력에 같은 결과가 필요하고 근거를 재현할 수 있어야 합니다. 규칙 엔진이 수치를 확정하고 LLM은 그 결과만 설명하게 해 생성형 모델의 숫자 변형 위험을 줄였습니다.

왜 Firebase가 아니라 Supabase인가요?

계좌·보유자산·성향·대화는 관계가 강하고 사용자별 소유권이 명확합니다. PostgreSQL 관계형 모델과 RLS를 한 플랫폼에서 운영하는 점이 요구사항에 맞았습니다. Firebase와 정량 비교한 결과는 없습니다.

왜 별도 벡터 DB를 쓰지 않았나요?

현재 승인 코퍼스가 작고 검색 메타데이터와 권한 데이터가 이미 PostgreSQL에 있습니다. 이 규모에서는 별도 동기화 경계를 만들지 않는 편이 단순했습니다. 규모와 트래픽이 커지면 별도 검색 계층을 재검토합니다.

Claude에 종속된 구조 아닌가요?

엔진 결과와 검증 가드는 모델 밖에 있고 pydantic-ai 계약 뒤에 모델을 둡니다. 내레이터가 실패해도 결정론 답변이 유지되며, 같은 가드 아래 다른 모델을 비교할 수 있는 구조입니다.

무료 배포 구성이 실서비스에도 적합한가요?

아닙니다. 발표와 검증 단계의 초기 비용을 낮춘 선택입니다. 운영 전에는 상시 인스턴스, 부하테스트, 실제 토큰 비용과 캐시 적중률 측정이 필요합니다.
