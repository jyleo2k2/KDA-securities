각 기술의 절대 우열보다, 연금 규칙·데이터·AI 설명을 한 서비스에서 안정적으로 연결하는 데 맞춘 선택입니다.

React + TypeScript + Vite PWA→ FastAPI + Python→ Supabase PostgreSQL+ pydantic-ai + Gemini

선택과 이유

영역 선택 비교 대상 선정 근거와 한계
프론트엔드 React + TypeScript + Vite PWA Vue 3, Next.js, Flutter API 중심 모바일 웹에 필요한 컴포넌트 생태계와 타입 안정성, 빠른 개발 서버를 확보했습니다. SSR·SEO나 네이티브 기기 기능이 핵심 요구는 아니어서 Next.js·Flutter의 추가 복잡도를 택하지 않았습니다.현재 PWA 설치 아이콘 등 최종 설치 요건은 별도 보완이 필요합니다.
백엔드 Python + FastAPI + Pydantic Node.js/NestJS, Spring Boot 연금 규칙, 데이터 처리, RAG, AI 에이전트를 같은 Python 런타임에서 다룹니다. 다른 언어도 가능하지만 핵심 계산을 재작성하거나 언어 간 API 경계를 하나 더 운영해야 합니다.
판단과 AI 규칙 엔진 + pydantic-ai + Gemini LLM 단독, LangChain/LangGraph 수치 판단은 Python 규칙 엔진이 맡고, pydantic-ai는 구조화된 에이전트 연결, Gemini는 설명과 문답만 맡습니다. 계산 재현성과 AI 활용을 분리한 구조입니다.
데이터베이스 Supabase PostgreSQL + Auth + RLS Firebase, AWS Amplify, 직접 운영 PostgreSQL 계좌·보유자산처럼 관계가 강한 데이터를 정규화하고 SQL·외래키로 무결성을 관리합니다. Vercel 프론트 배포에는 영속 DB 프로세스를 포함하지 않으므로 외부 관리형 PostgreSQL인 Supabase에 DB를 두었습니다.
검색 pgvector + BGE-M3 Pinecone, Qdrant 승인 문서와 메타데이터가 이미 PostgreSQL에 있어 벡터 검색도 같은 데이터 경계에 두었습니다.임베딩 실행 환경이 없을 때는 전문 검색 폴백을 사용합니다.
배포 Vercel + Render + Supabase 단일 서버, AWS 직접 구성 정적 프론트, Python API·에이전트, 영속 DB를 각 역할에 맞는 관리형 환경으로 분리했습니다.무료 인스턴스의 초기 기동 지연은 운영 비용과 함께 재검토 대상입니다.

30초 발표 문장

프론트엔드

로그인 후 API 데이터를 다루는 모바일 웹이어서 React·TypeScript로 화면과 타입을 관리하고, Vite로 개발·빌드를 단순화했습니다.

백엔드와 AI

연금 규칙부터 데이터 처리, RAG, 에이전트까지 Python 생태계에 있어 FastAPI와 pydantic-ai를 같은 환경에 두었습니다.

DB와 배포

관계형 데이터를 PostgreSQL로 정규화했고, Vercel 밖의 관리형 Supabase에 DB를 두어 Auth·RLS·pgvector까지 함께 운영합니다.

예상 질문

왜 Node.js나 Spring 대신 Python인가요?

AI라서 무조건 Python을 고른 것이 아닙니다. 현재 핵심인 규칙 계산·데이터 처리·검색·에이전트가 Python에 모여 있어, FastAPI를 쓰면 재작성과 언어 간 통신 비용을 줄일 수 있기 때문입니다.

왜 Firebase가 아니라 Supabase인가요?

계좌·자산·전략은 관계와 제약이 중요합니다. 문서 중심 DB보다 PostgreSQL의 정규화, 조인, 외래키가 모델에 더 잘 맞고 Auth·RLS도 함께 사용할 수 있습니다.

왜 Vercel 안에 DB를 넣지 않았나요?

Vercel은 프론트 배포를 담당하며 애플리케이션과 함께 장시간 실행되는 영속 DB 프로세스를 두는 구조가 아닙니다. 따라서 외부 관리형 DB인 Supabase에 연결했습니다.

왜 LLM이 계산하지 않나요?

연금 한도와 포트폴리오 수치는 같은 입력에 같은 결과가 필요합니다. 계산은 검증 가능한 규칙 엔진에 두고 LLM은 결과를 이해하기 쉽게 설명합니다.

왜 Vue 3나 Next.js가 아닌가요?

둘 다 가능한 선택입니다. 다만 팀이 React 기반 컴포넌트와 테스트를 이미 갖췄고, 이 서비스는 공개 검색 페이지보다 인증 후 API 화면이 중심이라 React SPA 구성이 충분했습니다.

이렇게 말하기

  • 요구사항과 기존 코드에 가장 잘 맞았다.
  • Python 한 환경으로 계산·데이터·에이전트를 연결했다.
  • 프론트와 영속 DB의 배포 역할을 분리했다.

  • Python이 AI 백엔드에 항상 더 좋다.
  • Vercel은 DB를 사용할 수 없다.
  • Supabase가 언제나 더 싸고 안전하다.
