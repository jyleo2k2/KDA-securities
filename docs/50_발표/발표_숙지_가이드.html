01 · IDENTITY

가장 먼저 맞춰야 할 한 문장

발표자마다 표현이 달라도 아래 의미는 같아야 합니다.

DC형·IRP·연금저축의 계좌 규칙과 자산구성을 규칙 엔진으로 계산하고, LLM이 검증된 결과를 쉽게 설명해 사용자가 스스로 운용 결정을 내리도록 돕는 연금계좌 운용 가이드입니다.

02 · SIX ANCHORS

어떤 질문에서도 돌아올 여섯 축

A1

문제는 무관심보다 정보 부족

관심은 있지만 운용 방법을 모르는 이용자가 핵심 대상입니다. 조회 기능이나 자동화만으로 방치가 해결되지 않는 이유를 여기서 설명합니다.

A2

계산과 설명을 분리

규칙 엔진이 수치를 결정하고 LLM은 설명만 합니다. 이 구조가 금융 정확성과 설명 가능성의 중심입니다.

A3

세 계좌 규칙을 섞지 않음

DC형·IRP의 일반 위험자산 한도와 연금저축의 상품 적격성 규칙을 계좌별로 적용합니다.

A4

데이터 경계를 유지

시장·제도·상품은 공식 원천, 뉴스는 메타데이터와 파생 요약, RAG는 검증 문서, 사용자 계좌는 서비스 시나리오 구조로 분리합니다.

A5

조회와 일임 사이의 설명 계층

서비스가 주문을 대신하지 않습니다. 통합 진단과 근거 설명을 제공하고 실제 선택과 실행은 이용자가 합니다.

A6

한계도 설계의 일부

미래 수익을 보장하지 않고, 비교 실험이 없는 기술은 우월하다고 말하지 않으며, 실서비스 전환 과제를 분리해 공개합니다.

03 · NUMBER ANCHORS

숫자는 분모와 기준을 함께 말합니다

아래 숫자는 발표 개요의 핵심 앵커입니다. 최신 기준일과 정확한 출처는 원문 슬라이드 노트를 우선합니다.

04 · TALK TRACK

발표는 이 순서로 연결합니다

OPEN

문제 정의

“연금이 없는 것이 아니라 운용 방법을 몰라 방치되는 것이 문제입니다.” 방치 통계에서 정보부족형 페르소나로 연결합니다.

WHY US

시장 빈칸

마이데이터 조회와 로보어드바이저 일임 사이에, 계좌를 진단하고 이유를 설명해 이용자 실행으로 잇는 계층이 비어 있다고 정의합니다.

DATA

공식 근거

FSS·KRX·KIS·KIND·DART·법령과 NAVER 뉴스의 역할을 구분하고, 원본·기준일·해시·정규화 결과를 연결한다고 설명합니다.

MODEL

규칙 엔진

예측 모델의 정확도 경쟁이 아니라 계좌 규칙과 계산 불변식을 검증하는 문제로 바꿨다는 점을 강조합니다.

AI

LLM 통제

엔진 답변 → 숫자·출처 검증 → LLM 재서술 → 실패 시 결정론 답변 유지 순서로 설명합니다.

DEMO

사용자 경험

로그인과 계좌 흐름 뒤에 홈, 챗봇, 전략, 계산기가 같은 사용자·성향·계좌 문맥으로 이어지는 장면을 보여줍니다.

VALUE

비즈니스 가치

방치 계좌의 운용지시를 돕고, 실물이전과 연금 고객 유치에서 설명 가능한 진단 도구가 될 수 있다고 연결합니다.

CLOSE

한계와 다음 단계

실계좌 연동, 운영 부하, 비용 계측, 실서비스 규제 절차를 다음 단계로 분리해 과장 없이 마칩니다.

05 · DEMO RUNBOOK

시연은 기능 목록이 아니라 한 사용자 여정입니다

각 화면에서 “무엇을 보여주는지”보다 “앞 단계의 정보가 다음 판단에 어떻게 이어지는지”를 말합니다.

1 · 진입

로그인 → 계좌 연동 동의 → 투자정보 입력. 사용자와 설문 문맥이 생성되는 지점을 보여줍니다.

2 · 통합 홈

계좌·보유자산과 투자성향이 한 화면에서 연결되는 모습을 보여줍니다.

3 · 챗봇

계좌 차이 또는 전략 질문을 입력하고, 결론·근거·출처·후속 질문 흐름을 확인합니다.

4 · 확장 기능

MY투자 전략, 타 고객 참고, 연금계산기 중 하나를 골라 같은 데이터 계약이 이어짐을 보여줍니다.

시연 멘트 · “이 화면이 추천의 끝이 아닙니다. 사용자가 왜 이런 결과가 나왔는지 챗봇에 이어 묻고, 전략과 계산 결과를 비교한 뒤 공식 채널에서 직접 실행하도록 돕는 흐름입니다.”

06 · CLAIM BOUNDARIES

서비스 범위와 표현 경계

반드시 말할 것

  • 자문·정보 제공형이며 실제 주문은 이용자가 직접 실행합니다.
  • 일임 구조가 아니고 미래 수익을 예측하거나 보장하지 않습니다.
  • DC형·IRP와 연금저축의 계좌 규칙을 분리합니다.
  • 모든 계산은 규칙 엔진이 하고 LLM은 설명만 합니다.
  • 공식 데이터와 사용자 데이터의 내부 경계를 유지합니다.

피해야 할 주장

  • “AI가 알아서 가장 좋은 상품을 골라 줍니다.”
  • “이 전략으로 미래 수익이 보장됩니다.”
  • “연금저축도 위험자산 한도가 70%입니다.”
  • “현재 화면이 실제 금융사 계좌를 이미 이전하거나 주문합니다.”
  • 비교 실험이 없는 기술을 “가장 빠르다” 또는 “가장 싸다”고 단정합니다.

07 · Q&A DRILL

답변은 네 단계로 맞춥니다

결론부터 말하고, 선택 이유와 프로젝트 근거를 붙인 뒤 한계를 닫습니다.

1 · 결론한 문장으로 직접 답변
2 · 이유요구사항과 선택 연결
3 · 근거코드·테스트·실측 제시
4 · 한계미검증과 다음 단계
왜 LLM이 직접 포트폴리오를 만들지 않나요?
결론금융 계산은 규칙 엔진이 합니다.
이유같은 입력에 같은 결과가 필요합니다.
근거Decimal 순수 함수와 숫자 검증 가드가 있습니다.
한계규칙 변경 시 버전과 테스트를 갱신해야 합니다.
이 서비스는 투자자문인가요, 투자권유인가요?
결론현재는 자문·정보 제공형 운용 가이드입니다.
이유계좌 원리와 비교·시뮬레이션·자문형 콘텐츠를 제공합니다.
근거상품 선택과 주문은 이용자가 공식 채널에서 직접 합니다.
한계실서비스화 시 등록·적합성·설명의무를 재검토합니다.
추천 근거를 어떻게 검증하나요?
결론수치와 출처를 응답 계약으로 연결합니다.
이유설명만 그럴듯하고 근거가 없는 상태를 막기 위해서입니다.
근거숫자는 NumericEvidence, 문장은 출처 ID와 연결됩니다.
한계외부 원천의 단위와 갱신 상태도 계속 감사해야 합니다.
왜 FastAPI와 Supabase를 골랐나요?
결론Python 계산과 관계형 소유권 모델에 맞았습니다.
이유엔진 재작성 경계를 줄이고 Auth·RLS를 통합했습니다.
근거Pydantic 계약과 원격 Auth/RLS E2E를 검증했습니다.
한계대안 대비 부하·비용 비교는 아직 없습니다.
실제 계좌 데이터인가요?
결론시장·제도·상품은 공식 데이터이고 사용자 계좌는 연동 구조를 검증하는 사전구성 데이터입니다.
이유데이터 종류를 섞지 않고 실계좌 연동 계약을 먼저 구현했습니다.
근거시장 원천, 뉴스, RAG, 사용자 계좌를 별도 저장·처리합니다.
한계현재 금융사 마이데이터 실연동과 주문 실행은 없습니다.
가장 큰 기술적 한계는 무엇인가요?
결론검증 단계 인프라와 운영 계측이 아직 제한적입니다.
이유무료 인스턴스 콜드 스타트와 외부 LLM 지연이 있습니다.
근거프리워밍과 캐시를 적용했지만 운영 SLA는 아닙니다.
한계상시 인스턴스, 부하테스트, 실제 비용 계측이 필요합니다.
