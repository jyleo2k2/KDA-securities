# 금융권 규제 및 컴플라이언스 고려사항

> 문서 버전: v1.0  
> 기준일: 2026-07-13  
> 적용 대상: DC형 퇴직연금·IRP·연금저축계좌 운용 가이드  
> 상태: 기획·프로토타입 단계 사전 점검

> [!IMPORTANT]
> 이 문서는 프로젝트 설계와 개발을 위한 사전 컴플라이언스 점검 자료이며 법률의견서가 아니다. 실제 출시 전에는 서비스 제공 주체의 준법감시인·법무·개인정보보호·정보보호 부서가 최신 법령, 감독규정, 유권해석, 인허가·등록 업무 범위를 다시 확인해야 한다.

## 1. 요약 결론

현재 기획서의 **목데이터 기반 교육·의사결정 지원 MVP** 범위에서는 명백한 법 위반 요소가 확인되지 않는다. 현재 위험도는 **낮음~관리 가능**으로 판단한다.

이 판단은 다음 경계를 모두 지킨다는 전제에서만 유효하다.

- 실제 금융회사 계좌를 연결하지 않는다.
- 실제 주문·매매·자동 리밸런싱을 실행하지 않는다.
- 특정 ETF·펀드·보험상품의 개인화된 매수·매도 추천을 하지 않는다.
- 개인별 확정 절세액이나 세금 최적화 결과를 제공하지 않는다.
- 사용자 계좌 데이터는 시나리오 계좌 데이터만 사용한다.
- 계산과 제약 검사는 규칙 엔진이 수행하고, LLM은 검증된 결과를 설명한다.

위 경계는 [프로젝트 기획서 §6.11](../10_기획/기획서.md#611-mvp-제외-기능)과 [공통 AI 규칙](../team/_공통_AI규칙.md)에 반영되어 있다.

다만 다음 기능은 규제 수준을 크게 높인다.

1. 실제 자산·투자성향에 따른 구체적 목표 비중 또는 상품 추천
2. 실계좌·타 금융회사 계좌 통합조회
3. 사용자 승인 후 원탭 주문 또는 계좌 이전
4. 자동 리밸런싱·자동매매
5. 실제 개인정보·개인신용정보를 외부 생성형 AI에 전달
6. 개인별 세금·연금수령·인출 순서 최적화

화면에 `교육용`, `참고용`, `투자 책임은 본인에게 있음`이라고 표시하더라도 **실제 기능의 내용이 개인화된 투자판단 자문이라면 규제 성격은 달라지지 않는다.**

|---|---:|---:|---|
| 계좌별 역할·제도·한도 설명 | 포함 | 낮음 | 최신 공식 출처와 기준일 표시 |
| 시나리오 계좌 기반 상태 진단 | 포함 | 낮음 | 출처와 기준일 관리 |

| 개인별 확정 절세액·세금 최적화 | 제외 | 주의~높음 | 세무대리·세무자문 영역과 경계 설정 필요 |

### 2.1 안전한 정보제공 예시

> IRP는 위험자산 투자한도가 적용될 수 있습니다. 주식형과 채권형 자산군을 비교할 때는 변동성, 수수료, 투자기간과 중도인출 제약을 함께 확인해야 합니다.

### 2.2 상용화 전 법률 검토가 필요한 예시

> 고객님의 나이·잔액·투자성향을 고려하면 A ETF를 40%, B 펀드를 30% 매수하고 C 상품을 매도하는 것이 적합합니다.

두 번째 예시는 이용자의 정보에 따라 종목·수량·취득·처분 판단을 제시하므로 개인화된 투자자문 또는 투자권유로 판단될 가능성이 높다.

## 3. 자본시장법: 투자자문과 투자일임의 경계

### 3.1 투자자문업 해당 가능성

자본시장법상 투자자문업은 금융투자상품 등의 가치 또는 종류·종목·취득·처분·수량·가격·시기 등에 관한 투자판단 자문에 응하는 것을 영업으로 하는 행위다. 금융투자업은 이익을 목적으로 계속적·반복적으로 행하는 것을 전제로 하며, 미등록 투자자문업·투자일임업은 금지된다.

현재와 같은 비공개 교육용 프로토타입은 영업성과 개인화 수준이 낮아 위험이 작다. 그러나 다음 조건이 결합되면 투자자문업 해당 가능성이 커진다.

- 실제 고객의 연령, 소득, 잔액, 보유종목, 투자성향을 이용한다.
- 고객별로 다른 ETF·펀드·보험상품 또는 매매 비중을 제시한다.
- Q&A에서 고객의 질문에 맞춰 1:1 매수·매도 판단을 제공한다.
- 무료 서비스라도 금융상품 판매·계좌 유치·수수료 수익과 연결된다.
- 동일 기능을 공개적으로 계속·반복 제공한다.

불특정 다수를 대상으로 한 개별성 없는 단방향 정보와 고객별 양방향 투자상담은 구분해야 한다. `교육용`이라는 명칭보다 실제 입력·출력·사업구조가 우선한다.

### 3.2 사용자 승인과 투자일임

사용자가 매 거래를 명시적으로 승인하면 시스템이 투자판단과 집행을 전권 위임받는 전형적인 투자일임 구조와 구별하는 데 도움이 된다. 그러나 사용자 승인은 다음 의무까지 제거하지 않는다.

- 승인 전에 제공한 개인화 추천의 투자자문 해당 가능성
- 금융상품 판매·권유에 대한 적합성·설명의무
- 주문 처리에 관한 투자중개·전자금융 통제
- 추천·설명·승인·주문 기록 보관
- 부당권유·손실보전·수익보장 금지

### 3.3 키움증권 제공 시 확인 사항

키움증권은 공식 연혁상 투자자문업 및 투자일임업 인가 이력을 공개하고 있다. 그러나 회사가 관련 인허가 이력을 보유했다는 사실만으로 신규 AI 서비스가 자동 승인되는 것은 아니다. 출시 전 다음을 확인해야 한다.

- 현재 유효한 투자자문·투자일임 **등록업무 단위와 투자자 유형**
- 서비스 계약의 법적 주체와 책임 부서
- 기존 투자자문 계약·약관 안에서 제공 가능한 기능인지
- 퇴직연금사업자 업무와 투자자문업의 결합 방식
- 준법감시인, 상품위원회, 정보보호위원회 등의 내부 승인
- 외부 AI·알고리즘 사업자에게 위탁할 업무와 책임 범위

### 3.4 로보어드바이저 테스트베드

모든 교육용 계산기나 규칙 엔진이 자동으로 로보어드바이저 테스트베드 대상이 되는 것은 아니다. 전자적 투자조언장치를 사용해 실제 투자자문·투자일임을 제공하는 경우 다음 요건을 검토한다.

- 투자자 성향 분석 기능
- 특정 종목·자산에 편중되지 않는 자문
- 유지·보수 전문인력
- 해킹·재해 대비와 복구체계
- 알고리즘 설명·변경관리·성능검증
- 코스콤 테스트베드 통과 여부
- 퇴직연금 로보일임인 경우 혁신금융서비스 지정·부가조건

`상품제시`, `자문`, `일임`, `테스트베드 통과`, `혁신금융서비스 지정`, `실제 출시`는 서로 다른 상태이므로 문서와 발표에서 혼용하지 않는다.

## 4. 금융소비자보호법: 판매원칙과 증적

개인화 추천이 실제 금융상품 권유 또는 자문으로 발전하면 단순히 성향 밖 상품을 차단하는 것만으로 충분하지 않다.

### 4.1 적합성·적정성

실서비스에서는 필요 범위에 따라 다음 정보를 파악하고 이용자 확인을 받아 유지·관리해야 한다.

- 일반·전문 금융소비자 구분
- 연령, 재산상황, 소득과 부채
- 금융상품 이해도와 투자경험
- 투자 목적과 투자 예정기간
- 원금손실 감수능력
- 연금수령 예정시기와 유동성 필요
- 기존 투자자정보확인서의 유효기간과 변경 여부

퇴직연금 위험자산 70% 한도 준수는 **계좌 규칙 준수**일 뿐, 해당 상품이 그 고객에게 적합하다는 판단을 대신하지 않는다.

### 4.2 설명의무

`추천 근거 3개` 또는 `출처 칩`은 좋은 설명 장치지만 설명의무 전체를 충족한다고 단정할 수 없다. 실제 권유·자문 단계에서는 다음을 이용자가 이해할 수 있게 제공하고, 필요한 증적을 남겨야 한다.

- 상품 구조와 투자대상
- 원금손실 가능성과 최대손실 가능성
- 변동성·환율·금리·신용·유동성 위험
- 보수·수수료·중도해지 비용
- 환매·매도·중도인출 제한
- 세제혜택 조건과 추징 가능성
- 과거 실적이 미래 수익을 보장하지 않는다는 사실
- 추천 근거, 대안, 주요 불이익

### 4.3 부당권유·불공정영업 방지

다음 표현과 동작을 금지한다.

- 수익률·시장 방향을 확정적으로 표현
- 원금 또는 손실 회복을 보장하거나 암시
- 일부 유리한 기간만 선택한 백테스트 제시
- 위험보다 혜택을 훨씬 크게 표시
- 사용자의 거절을 어렵게 하는 반복 팝업·다크패턴
- 성향에 맞지 않는 상품에 `추가 동의`만 받아 반복 권유
- 제휴수수료나 자사 이해관계를 숨긴 추천 순위

### 4.4 광고·발표자료

서비스 소개, 앱스토어 문구, 데모 영상, 발표자료도 금융상품 또는 금융업무 광고로 평가될 수 있다. 다음 문구는 사용하지 않는다.

- `AI가 최적의 연금 포트폴리오를 찾아드립니다.`
- `안전하게 연 8% 수익을 달성합니다.`
- `법적 한도를 지킨 완벽한 포트폴리오입니다.`
- `방치된 연금을 손실 없이 회복합니다.`

권장 표현은 다음과 같다.

- `공식 규칙과 사용자가 선택한 가정에 따른 교육용 예시입니다.`
- `실제 수익률과 세금은 시장 상황과 개인 조건에 따라 달라질 수 있습니다.`
- `특정 금융상품의 매수·매도 지시가 아닙니다.`

다만 면책 문구는 기능 자체가 투자자문·권유에 해당할 때 이를 배제하는 수단이 아니다.

## 5. 퇴직연금·연금저축 규칙

### 5.1 DC·IRP

- DC·IRP의 위험자산 투자한도와 상품별 예외를 규칙 엔진에 반영한다.
- 상품명만으로 위험자산 여부를 추정하지 않고 공식 분류를 사용한다.
- 디폴트옵션 상품은 승인 상품과 위험등급을 기준일별로 관리한다.
- 사용자가 운용방법을 스스로 선택한다는 원칙과 사업자의 정보제공 의무를 구분한다.
- 중도인출, 연금 외 수령, 이전, 압류·담보 제한 등은 별도 규칙으로 관리한다.

### 5.2 연금저축계좌

DC·IRP 규칙을 연금저축계좌에 그대로 적용하지 않는다. 연금저축펀드·연금저축보험 등 상품 유형에 따라 적용 법률, 판매 주체, 수수료 구조, 보장 여부, 중도해지 효과가 다르다.

보험상품을 구체적으로 비교·추천하거나 계약 체결로 연결할 경우 보험업법상 보험모집 자격·설명의무와 금융소비자보호법상 판매규제를 별도로 검토한다. MVP에서는 보험상품의 구조와 차이를 교육하는 수준에 머문다.

### 5.3 규칙 데이터 거버넌스

모든 규칙은 다음 필드를 갖는 버전 데이터로 관리한다.

| 필드 | 설명 |
|---|---|
| `rule_id` | 규칙 고유 식별자 |
| `account_type` | DC, IRP, 연금저축 구분 |
| `effective_from/to` | 시행 시작일·종료일 |
| `source_url` | 법령·감독규정·공식 안내 원문 |
| `verified_at` | 마지막 검증일 |
| `verified_by` | 검증 담당자 |
| `logic_version` | 엔진 구현 버전 |
| `exception` | TDF·디폴트옵션 등 예외 |
| `status` | 적용·예정·폐지·확인 필요 |

법령 변경을 감지하면 기존 진단 결과를 자동으로 유효하지 않은 결과로 표시하고 재계산한다.

## 6. 개인정보·신용정보·마이데이터

### 6.1 현재 MVP

목데이터만 사용하더라도 사용자가 채팅창에 실제 계좌번호·주민등록번호·보유내역을 입력할 수 있다. 다음을 MVP부터 적용한다.

- 실명·계좌번호·주민등록번호 입력 금지 안내
- 계좌번호·전화번호·이메일·주민등록번호 형태의 입력 마스킹
- 입력 데이터의 로컬·서버 로그 저장 여부 명시
- 데모 종료 후 입력·대화 기록 자동 삭제
- 목데이터에는 실제 고객과 유사한 식별정보를 사용하지 않음

### 6.2 실계좌 연결 시

실제 금융계좌와 보유상품 정보는 개인정보이면서 개인신용정보에 해당할 수 있다. 타 금융기관 정보를 모아 조회·분석하는 기능은 본인신용정보관리업(마이데이터) 허가 또는 허가 사업자와의 적법한 제휴 구조를 검토한다.

확인 항목은 다음과 같다.

- 누가 개인정보처리자·신용정보제공이용자·마이데이터 사업자인지
- 수집 목적과 최소 필요 항목
- 필수·선택 동의 분리
- 제3자 제공과 처리위탁 구분
- 보유기간과 파기 시점
- 전송요구권 철회와 연결 해제
- 조회 목적 데이터와 자문·마케팅 목적 데이터의 분리
- 계열사·제휴사 결합 이용 여부

### 6.3 외부 LLM·클라우드

실제 고객정보를 외부 생성형 AI API에 전송하기 전 다음을 모두 확인한다.

- 입력 데이터가 모델 학습에 사용되는지
- 요청·응답과 장애 로그의 보관 위치·기간
- 국내외 데이터 처리 리전
- 국외이전의 법적 근거와 고지·동의 요건
- 재위탁자 목록과 변경 통지
- 데이터 삭제 및 계약 종료 후 반환·파기
- 암호화, 키 관리, 접근통제, 관리자 로그
- 프롬프트 인젝션에 의한 정보 유출 방지
- 제공사 모델 변경 시 재평가 절차

상용화 전 원칙은 **LLM에 고객 식별정보를 보내지 않는 것**이다. 필요한 경우 고객 식별자와 계좌번호를 제거하고, 엔진이 계산한 최소한의 비식별 결과만 LLM에 전달한다.

### 6.4 자동화된 결정

현재 교육용 안내는 통상 이용자의 권리·의무를 결정하지 않는다. 그러나 향후 AI 결과가 다음 기능에 사용되면 개인정보보호법상 자동화된 결정에 대한 설명·거부·인적 개입 절차를 검토한다.

- 금융상품 가입 또는 거래 가능 여부 결정
- 투자성향 등급 확정
- 상품 접근 제한
- 수수료·혜택 차등
- 계좌 개설·이전·인출 승인 또는 거절

## 7. 생성형 AI·모델 리스크 관리

### 7.1 역할 분리

- 규칙 엔진: 계좌 규칙, 한도, 적립·수익률·세액 관련 수치 계산
- 검증 콘텐츠: 제도, 상품 유형, 공식 출처와 기준일
- LLM: 엔진 결과의 자연어 설명과 허용 범위 내 Q&A
- 사람: 규칙 승인, 예외 판단, 최종 금융 의사결정과 책임

LLM이 엔진 결과를 수정하거나 새로운 수치·수익률·상품을 생성하지 못하게 한다.

### 7.2 이용자 고지

공개·상용 서비스에서는 다음을 표시한다.

- 생성형 AI가 사용된다는 사실
- AI가 생성한 답변이라는 표시
- 수치 계산 주체와 데이터 기준일
- AI 답변의 한계와 오류 신고 방법
- 필요한 경우 사람 상담으로 전환하는 경로

### 7.3 모델 변경관리

모델명·버전·시스템 프롬프트·RAG 문서·도구 스키마 중 하나라도 변경되면 회귀 테스트를 수행한다.

필수 테스트는 다음과 같다.

- 특정 상품 추천을 유도하는 우회 질문
- 수익 보장·손실 회복 요구
- 성향 밖 상품 요청
- 규정 시행일이 다른 질문
- DC·IRP·연금저축 규칙 혼동
- 목데이터를 실제 데이터로 오인시키는 질문
- 프롬프트 인젝션·시스템 지시 탈취
- 개인정보·계좌정보 출력 요구
- 계산 도구 미응답·잘못된 응답
- 출처가 없는 숫자 생성

### 7.4 모니터링 지표

| 지표 | 목표 |
|---|---:|
| 엔진과 답변 수치 불일치 | 0건 |
| 계좌 규칙 위반 예시 | 0건 |
| 출처 없는 법·세제 수치 | 0건 |
| 개인화 특정 상품 매수 지시 | 0건(MVP) |
| 실제·목데이터 혼동 | 0건 |
| 개인정보 마스킹 실패 | 0건 |
| 위험·가정 고지 누락 | 0건 |

## 8. 원탭 주문·자동운용·전자금융

### 8.1 원탭 주문

향후 사용자가 제안을 확인하고 주문하는 기능을 추가한다면 반드시 인가된 금융회사의 정식 주문시스템 안에서 처리한다.

- 주문 직전 상품명·종목·수량·가격·예상금액 재확인
- 위험자산 한도와 거래 가능 여부 재검사
- 주문 전 중요 위험·수수료 고지
- 사용자 인증과 명시적 최종 승인
- 추천 결과와 실제 주문 사이 변경사항 표시
- 중복 주문·재전송 방지
- 주문 오류·정정·취소·민원 처리
- 추천·설명·확인·승인·주문·체결 로그 연결

`확인` 버튼과 `주문` 버튼을 혼동시키거나, 추천 확인만으로 주문이 실행되는 UX를 금지한다.

### 8.2 자동 리밸런싱

사용자에게 개별 주문 확인을 받지 않고 알고리즘이 종목·비중·시점을 정해 매매하면 투자일임업 해당 가능성이 매우 높다. 다음 검토가 끝나기 전에는 구현하지 않는다.

- 투자일임업 등록업무 단위
- 퇴직연금 로보일임 규제특례·혁신금융서비스 지정
- RA 테스트베드 및 부가조건
- 일임계약, 알고리즘 설명, 해지·중단 절차
- 장애 시 수동 전환·비상 정지
- 알고리즘 편중·성과·손실 모니터링
- 모델 또는 알고리즘 변경에 대한 사전 승인

### 8.3 전자금융·보안

실제 거래 단계에서는 다음을 준비한다.

- 전자금융거래기록 생성·보존·파기
- 인증·접근매체 보호
- 이상거래탐지와 계정 탈취 방지
- 취약점 분석, 침해사고 대응, 재해복구
- 거래 오류 정정과 분쟁처리 절차
- 외부 API 장애 시 주문 차단과 상태 확인
- 운영·개발·테스트 환경 및 권한 분리

계좌 개설, 자금 이체, 금융상품 계약까지 확장할 경우 고객확인·금융실명·자금세탁방지 의무도 별도로 검토한다.

## 9. 세금·수령·인출 안내

일반적인 세제 규칙과 명시된 가정에 따른 계산 예시는 가능하지만, 다음 기능은 세무상담·자문 또는 사실상 세무대리로 평가될 가능성을 검토해야 한다.

- 고객의 전체 소득·공제·가족관계를 반영한 확정 절세액
- `가장 세금이 적은` 인출·이전 순서 확정
- 신고서·경정청구서 자동 작성 또는 제출
- 고객별 과세 여부에 대한 확정적 결론
- 세무당국 대응 또는 신고 대행

향후 인출 단계 기능은 다음 원칙을 적용한다.

- 계산 결과를 `가정에 따른 예상`으로 표시
- 기준연도·세법 조문·공식 출처 표시
- 퇴직소득, 연금소득, 기타소득을 구분
- 세법 개정 시 기존 결과 만료 처리
- 복잡한 사례는 세무 전문가 확인으로 전환

## 10. 데이터·콘텐츠·지식재산권

공식 공개 데이터라도 자유로운 재배포·상업적 이용이 항상 허용되는 것은 아니다.

- 통합연금포털·KRX·금융회사 API 이용약관 확인
- 출처·기준일·가공 여부 표시
- 호출량·캐시·재배포 제한 준수
- 상품 설명서·리서치 보고서의 장문 복제 금지
- 뉴스·리서치·경쟁사 화면 캡처의 저작권 확인
- 오픈소스 라이브러리·모델·데이터셋 라이선스 목록 관리
- 데이터 수정·삭제 요청과 오류 정정 절차 마련

상품 수익률·수수료·위험등급은 스냅샷 기준일을 저장하여 사후에 어떤 데이터로 결과가 만들어졌는지 재현할 수 있어야 한다.

## 11. 향후 추가로 고려해야 할 운영 사항

### 11.1 책임과 조직

- 서비스 오너, 규칙 오너, 모델 오너, 데이터 오너를 구분한다.
- 준법감시·법무·개인정보·정보보호·소비자보호 부서의 승인 지점을 문서화한다.
- LLM 답변 사고가 발생했을 때 중단 권한과 보고 책임자를 지정한다.
- 개발자 개인 판단으로 법·세제 규칙을 운영 반영하지 않는다.

### 11.2 취약 금융소비자

연금 서비스는 고령자와 금융이해도가 낮은 이용자를 포함하므로 다음을 고려한다.

- 전문용어 풀이와 단계별 위험 설명
- 큰 글씨·명확한 대비·스크린리더 등 접근성
- 중요한 선택 전 숙려 화면
- 고령자·저이해도 이용자의 고위험 상품 전환 시 추가 확인
- 손실을 만회하려는 이용자에게 공격적 전환을 유도하지 않음
- 가족·대리인 기능 도입 시 권한과 개인정보 범위 확인

### 11.3 이해상충

키움 또는 제휴사의 상품을 우선 노출한다면 다음을 공개하고 통제한다.

- 추천 순위 산정 기준
- 자사·계열사 상품 여부
- 판매보수·제휴수수료 등 경제적 이해관계
- 동일 조건의 대안 상품 존재 여부
- 추천 알고리즘에서 수익성 지표와 고객 이익 지표의 분리

### 11.4 민원·분쟁·오류 정정

- AI 답변 신고 버튼
- 잘못된 규칙·수치의 정정과 이용자 통지
- 영향을 받은 이용자·결과 범위를 식별하는 기능
- 사람 상담과 금융감독원 분쟁조정 안내
- 사고 원인, 수정, 재발 방지 조치 기록
- 중대한 오류 시 기능 비활성화·롤백 절차

### 11.5 공급업체·모델 위험

- 외부 LLM·클라우드·데이터 API의 재무·보안·서비스 지속성 평가
- 장애·가격변경·서비스 종료에 대비한 대체 모델과 수동 모드
- 공급업체 약관 변경 모니터링
- 하위 처리자·국외 리전 변경 시 사전 검토
- 모델 업데이트가 답변 정책을 약화시키는지 정기 점검

### 11.6 법령·규정 변경관리

- 법령과 감독규정별 담당자를 지정한다.
- 최소 월 1회, 출시 직전, 법령 개정 공포 시 재검증한다.
- 변경 예정·시행 중·폐지 규칙을 구분한다.
- 규칙의 법률 검토일과 다음 검토기한을 기록한다.
- 문서·화면·테스트·엔진 규칙이 같은 버전을 참조하도록 한다.

## 12. 단계별 출시 게이트

### Gate A — 아카데미 데모

다음 조건을 충족하면 진행 가능하다.

- 목데이터만 사용
- 회원가입·실명·계좌번호 수집 없음
- 특정 상품 개인화 추천 없음
- 실제 주문·계좌 연결 없음
- 가정·출처·AI 생성·교육용 표시
- 금지 질문과 개인정보 입력 차단 테스트 통과

### Gate B — 외부 공개 베타

Gate A에 더해 다음이 필요하다.

- 이용약관·개인정보처리방침
- 개인정보 수집 최소화와 파기 정책
- AI 생성 표시와 오류 신고 기능
- 콘텐츠·광고 사전심의
- 모델·규칙 변경관리와 운영 모니터링
- 준법감시·법무·정보보호 사전 검토

### Gate C — 실제 키움 고객·실계좌 진단

Gate B에 더해 다음이 필요하다.

- 키움증권 내부 서비스 주체와 책임 부서 확정
- 개인정보·신용정보 처리 흐름도 승인
- 마이데이터 또는 자사 계좌 조회 권한 확인
- 실제 계좌 데이터의 LLM 전달 차단·최소화
- 투자자문 해당 여부와 계약구조 검토
- 규칙·상품 데이터의 운영 품질 보증

### Gate D — 개인화 상품 제안

Gate C에 더해 다음이 필요하다.

- 투자자문 등록업무 단위 확인
- 금소법상 적합성·설명의무·기록관리 구현
- RA 해당 여부와 테스트베드 확인
- 이해상충·추천 순위·광고 심사
- 사람 상담·이의제기·분쟁처리 체계

### Gate E — 원탭 주문

Gate D에 더해 다음이 필요하다.

- 인가된 주문시스템 연동
- 주문 전 재확인·인증·한도검사
- 주문·체결·오류·취소 기록
- 전자금융 보안·재해복구·민원 절차
- 추천 결과와 주문 사이 변경사항 표시

### Gate F — 자동 리밸런싱·일임

다음이 완료되기 전에는 **No-Go**다.

- 투자일임업 범위와 계약구조 확정
- 퇴직연금 로보일임 관련 규제특례 확인
- 테스트베드·보안·알고리즘 검증
- 비상정지·해지·수동개입 체계
- 감독당국·준법감시·법무의 최종 확인

## 13. 개발 완료 기준

MVP는 다음 조건을 모두 만족해야 컴플라이언스 관점에서 완료로 본다.

- [ ] 실제 주문·계좌 연결 코드와 버튼이 없다.
- [ ] 특정 종목의 개인화 매수·매도 지시가 생성되지 않는다.
- [ ] 모든 계산 수치가 규칙 엔진 결과와 일치한다.
- [ ] 모든 법·세제·한도 수치에 출처와 기준일이 있다.
- [ ] DC·IRP·연금저축 규칙이 분리되어 있다.
- [ ] 계좌 관련 수치의 출처와 기준일이 표시된다.
- [ ] 개인정보 패턴 입력이 마스킹 또는 차단된다.
- [ ] 생성형 AI 사용과 AI 생성 결과가 표시된다.
- [ ] 손실 가능성·가정·한계가 혜택과 같은 수준으로 표시된다.
- [ ] 금지 질문·프롬프트 인젝션·도구 장애 테스트를 통과한다.
- [ ] 규칙·모델·출처 버전으로 결과를 재현할 수 있다.
- [ ] 오류 신고와 서비스 중단 경로가 정의되어 있다.

## 14. 기존 프로젝트 문서에서 보완할 표현

다음 표현은 규제상 단정이 강하므로 후속 수정이 필요하다.

| 기존 표현 | 보완 방향 |
|---|---|
| `자문형은 원래 합법` | 개인화되지 않은 교육·정보제공과 등록된 주체의 투자자문을 구분 |
| `사용자 승인 = 일임 규제 해소` | 일임과 구별될 수 있으나 자문·권유·판매·전자금융 의무는 남는다고 명시 |
| `근거 명시가 곧 설명의무 이행` | 근거 표시는 설명의무의 일부이며 위험·비용·손실·제약 설명과 증적이 추가로 필요 |
| `적합성 검증 100% 자동화` | 규칙 엔진으로 일부 통제 가능하나 정보 파악·확인·예외·인적 개입이 필요 |
| `프로토타입은 법 위반 리스크가 사실상 없음` | 현재 폐쇄형 목데이터 범위에서 위험이 낮다고 표현 |
| `고객 포트폴리오 제시 = 항상 테스트베드 필요` | 전자적 투자조언장치로 실제 자문·일임을 제공하는 경우 해당 여부를 검토 |

우선 검토 대상은 [pension-market-research.md §5-1](../20_리서치/시장_경쟁.md#5-1-규제-검토-2번-코파일럿-모델)과 [pension-focus-rationale.md §9](../20_리서치/왜_연금인가.md#9-법적-리스크-비교--연금-코파일럿-vs-전체-자산-라우팅-2026-07-12-추가)이다.
